## Why

GitHub Issue: #104

RVSEC's violation reports cannot be read. In the published dataset 72.93 % of the 97,018 records carry the literal `unknown` as their message (70,760 rows, 19 distinct messages in the whole corpus) and 8,843 more read `but found .` with an empty observed value; the post-repair Study-03 trial (`experimento-comp162`, 19,664 rows) is worse in the first ratio at 79.91 %. The mechanical cause is measured and small — `message == 'unknown'` if and only if the report site used the three-argument `ErrorDescription` constructor (`ErrorDescription.java:34-36`), which is 25 of the 51 report sites of the `jca` set — but three families of defects around it turn readable reports into wrong ones: the dexlib2 weaver ignores positional `args()` arity when it merges advices into one wrapper (a residue of gh100's D-B1 merge that gh100 does not record); the transport path from `ErrorCollector` to `errors.csv` escapes nothing, fabricates fields and drops lines silently at ten points; and the `jca` automata carry messages whose text contradicts the guarding condition or the real allow-list, plus structural defects nobody catalogued. Because the `@fail` handler names neither the offending event nor the observed value, and the dedupe identity (`ErrorSummary` = spec, error, class, method, location) discards exactly the information the message would carry, per-event attribution is impossible today for any consumer of the record — including the analyses this thesis publishes.

Illegibility is not the only cost of the frozen specifications: on Android they are also wrong about what the platform offers, and the size of that error is measured. In the ase-journal corpus the tier of findings that survives primary-source evidence is **11,409 events over 84 misuses — 18.5 % of the 454 misuses of the corpus** — and every one of them is a value the platform genuinely supports which the `.mop` allow-list does not list:

| specification / `ErrorType` / observed value | events | apps | misuses |
|---|---|---|---|
| `SSLContextSpec` / `UnsafeProtocol` / `TLS` | 8,648 | 60 | 65 |
| `KeyStoreSpec` / `InvalidKeyStoreType` / `AndroidKeyStore` | 2,005 | 11 | 12 |
| `TrustManagerFactorySpec` / `UnsafeAlgorithm` / `X509` | 643 | 3 | 5 |
| `CipherSpec` / `UnsafeAlgorithm` / `RSA/ECB/OAEPWithSHA1AndMGF1Padding` | 109 | 1 | 1 |
| `SignatureSpec` / `UnsafeAlgorithm` / `SHA256WITHRSA` | 4 | 1 | 1 |

The whole tier is fixed to one platform context — **API 30 / Android 11, Conscrypt branch `android11-release`** — and the corresponding MetaCrySL rules already exist, generated, under `MetaCrySL/generated/api30/`. Two of the five rows fall out of a straight transcription of those rules: api30 `KeyStore` declares `{AndroidKeyStore, PKCS12, BKS, BouncyCastle, AndroidCAStore}`, which clears the 2,005 events, and api30 `SSLContext` declares `{Default, TLSv1.2, TLSv1.1, SSL, TLSv1, TLS, TLSv1.3}`, which clears the 8,648. The other three do not, and that is the reason this change carries a normalisation rule as a first-class item rather than as a detail.

`jca` is frozen (gh101 D-S0, `INV-INS-109`) and the derived Android set that gh101 left under the name `jca_android` was judged NOT READY by the 2026-08-08 audit, so neither can receive a repair. This change therefore **archives that derived set** — `git mv rvsec-mop/src/main/resources/jca_android rvsec-mop/src/main/resources/jca_android_bug_predicate/`, a directory no CLI value selects any more — and **rebinds the name `jca_android` to a successor set seeded from the frozen `jca` Java set**, which is where every specification-side repair lands; every runtime, weaver and transport repair lands in the shared code both sets execute on. The enumeration of specification sets does not grow: it keeps its four values (`jca`, `jca_android`, `generic`, `custom`), and the successor is reached by the name the derived set used to answer to. The `generic` and `generic_new` sets (145 of the 191 `.mop` files, none of which passes through `ErrorCollector`) are a written non-goal.

## What Changes

- **The name `jca_android` rebound to a new set (S)**: `rvsec-mop/src/main/resources/jca_android/` is rebuilt from the frozen `jca` seed, and the derived set that held the name is archived by `git mv` to `rvsec-mop/src/main/resources/jca_android_bug_predicate/`, which no `--specification-set` value selects. Nothing is added to the enumeration — `--specification-set jca_android` already existed and now resolves to the successor set — and the archived directory is read by no repair task, only by the differential harness's self-test. The set carries its own divergence record, conformance record and alias table in `data/jca_android/`; the frozen `jca` and its freeze gate stay untouched. The set has **21 specifications, not 23**: two of `jca`'s files exist only to propagate predicates (`RandomStringPassword.mop`, `SecretKeySpec.mop`) and have nothing left to do once predicates are gone. The oracle of the set is the **already-generated MetaCrySL api30 rules** in `MetaCrySL/generated/api30/`; MetaCrySL itself is not modified by this change, and any place where the generated rule is judged defective is recorded as a divergence instead of being fixed upstream.
- **Allow-lists by literal transcription (S)**: every value list in the set is transcribed literally from the `CONSTRAINTS` block of the corresponding api30 rule — no editorial additions, no carry-over of lists the rule does not declare. A comparison of 74 constants between today's `jca` `.mop` files and api30 gives the size of the move: 30 constants the rule declares and the `.mop` ignores, 14 identical, 13 the `.mop` tests with no basis in the rule, 7 where the `.mop` is more permissive, 7 divergent, 3 where the `.mop` is more restrictive. Four consequences are decided rather than discovered: `SecretKeySpecSpec`'s algorithm allow-list **disappears** (api30 declares nothing about `alg`, so the list has no basis); the `CipherSpec` allow-list **stays in Java**, in a **new class** under `rvsec-core/.../jca/util/` transcribed from `generated/api30/Cipher.cryptsl`, because `CipherTransformationUtil` belongs to the frozen `jca` and `AndroidCipherTransformationUtil` belongs to the archived `jca_android_bug_predicate` and neither may be altered; and `EC` **is added** to the `KeyPairGenerator` allow-list as the first of the two registered exceptions to literal transcription, with the reason written into the divergence record — `samples/jca/android/11plus/KeyPairGenerator.ref:2` declares `define algorithm = {"EC"};` but `samples/jca/base/KeyPairGenerator.cryptsl:27` writes the list as a literal (`alg in {"DH","DSA","RSA"}`) instead of `alg in ${algorithm}`, so the refinement is discarded in silence and the generated rule leaves its own `alg in {"EC"} => keySize in {256}` clause unreachable. Transcribing that literally would fabricate exactly the class of specification artefact this change exists to remove, since `EC` is the algorithm Android recommends for `AndroidKeyStore`. The second and last exception is `SignatureSpec`: `generated/api30/Signature.cryptsl` lists twenty algorithms and exactly one ECDSA among them — `SHA224withECDSA`, the only ECDSA any tier touched, and it is the `20plus` tier — while Conscrypt registers aliases pointing at `SHA1withECDSA`, `SHA256withECDSA`, `SHA384withECDSA` and `SHA512withECDSA` (`OpenSSLProvider.java:270,271,286,293,300`); an alias can only point at an algorithm the provider registers, so the four provably exist on API 30 and the four are added with their own divergence entry. Without them `SHA256withECDSA` — the pairing Android recommends for EC keys in `AndroidKeyStore`, and a value the `jca` `.mop` already accepted — would become a false positive. Both exceptions obey one asymmetric rule, and that rule governs every later question about a list: **where the api30 rule admits a value, the set admits it**, whatever the frozen `jca` thought of it, and the cost of that half is measured — 5,892 of the 6,048 `MessageDigestSpec` / `UnsafeAlgorithm` rows of the published dataset (3,552 `MD5` plus 2,340 `SHA-1`/`SHA1`/`SHA`) stop being reported, 97.4 % of that specification's output and 6.1 % of the 97,018 rows of the corpus, entered in the conformance record as a declared loss; **where the api30 rule omits what the platform provably carries, the set adds it**, with a divergence entry citing a platform source. The set never removes what api30 permits.
- **No `REQUIRES`, no predicates (S)**: the successor set carries no predicate clause and therefore never touches `ExecutionContext`. The cost is measured, not assumed. Of the 24 events in `jca` that read a predicate, **13 use it only as a guard** inside `condition()`, so removing it is a net gain — today those guards silence the specification. **11 accuse on the strength of a predicate** and lose detection: 6 total losses (`IvParameterSpec c3/c4`, `PBEKeySpecSpec err2/err3`, `SecureRandomSpec setSeed3`, `GCMParameterSpecSpec:33`), 2 partial (`PBEParameterSpecSpec c3`, `SecretKeySpecSpec c3`, whose allow-list half survives) and 3 cross-specification key-provenance checks (`CipherSpec i2`, `MacSpec i1/i2`, on `GENERATED_KEY`) that **already did not work on Android** — the ase-journal records that keys from `AndroidKeyStore`, Tink and `KeyGenParameterSpec` never carry `GENERATED_KEY`, over 11,620 events / 80 misuses / 25 apps. Removal also deletes 9 `remove(Property)` sites, against only **2 `NEGATES` clauses in the whole of api30**, which is the measure of how much of the predicate graph was ever grounded in the rule. Every removed site is written to `data/jca_android/predicate_removal.csv`; the file name is load-bearing, because gh101's `predicate_omissions.csv` records a different thing — a `Property` written and never read — and the two records must never be used interchangeably.
- **Declared normalisation rule (S)**: value comparison in the set is **case-insensitive**, and each specification carries a declared alias table derived from Conscrypt `android11-release` with a per-entry source pointer. Without it, literal transcription leaves roughly 3,000 measured events uncorrected even with the right list: `X509` (643 events) is Conscrypt's alias for `PKIX` (`OpenSSLProvider.java:90`), not an algorithm, and api30 `TrustManagerFactory` declares `{PKIX}` alone; `SHA256WITHRSA` (4 events) differs from api30's `SHA256withRSA` only in case; and the `SHA1`/`SHA` → `SHA-1` and `SHA256` → `SHA-256` aliases (`OpenSSLProvider.java:115-116` and `:124`) fragment 2,340 events over 22 misuses across three spellings. Those two pointers correct the ase-journal's `docs/20260806_owasp_cwe_mapping_report.md`, which cites `:101-107` for `X509` and `:131-132,140` for the digests — `:101-102` is `AlgorithmParameters` DESEDE/TDEA, `:131-132` is `SHA-512`/`SHA512` and `:140` is `KeyGenerator.ARC4`, which is not an alias at all; that report's own CSV and annex already carry the correct `:89-90`. The table has **114** relevant rows: the provider declares 175 `Alg.Alias.*` registrations, 158 of them in services this set specifies, and 114 of those reach an entry of an api30 allow-list — Signature 39, Mac 24, KeyGenerator 23, MessageDigest 12, AlgorithmParameters 5, KeyPairGenerator 5, Cipher 4, TrustManagerFactory 1, SecretKeyFactory 1. The fifth measured value of the tier, `RSA/ECB/OAEPWithSHA1AndMGF1Padding` (109 events), is **not** closed by this rule and gets no row: the observed spelling carries no hyphen in `SHA1`, api30 declares `OAEPwithSHA-1andMGF1Padding`, and Conscrypt registers only hyphenated spellings (`:338`, and the alias at `:339-340`), so there is no provider line a row could cite and no reason to weaken the per-entry pointer requirement for one value. Since `CipherSpec.g1` is an `after … returning(Cipher c)` advice, the 109 calls returned a `Cipher` — behavioural proof that another platform provider accepts the spelling, the candidate being the Bouncy Castle build Android ships — so the case is entered in the divergence record with its evidence labelled **behavioural**, and naming that provider is execution work. The rule also removes an inconsistency the set inherits: comparison is case-sensitive in 6 specifications (`Mac`, `Signature`, `SecureRandom`, `KeyGenerator`, `TrustManagerFactory`, `KeyManagerFactory`) and `.toUpperCase()`-normalised in 3 (`MessageDigest`, `SSLContext`, `SecretKeySpec`).
- **Event name from the generator (G)**: `rv-monitor` gains a `__EVENTNAME` macro — expanded to a string literal inside an event body, and inside a `@fail` handler to the name of the event that last transitioned the monitor. This is information the generated monitor already holds and throws away: it packs the event index into `pairValue` (or keeps it in `RVM_lastevent`), and the generator writes the matching names as *comments* in `terminateInternal`. Emitting them as a table costs two substitution sites and one array, instead of 134 hand-written bookkeeping lines per specification set, and it cannot produce a wrong name because the table and the indices come from one iteration. The freeze is on the specification sources, not on generated monitors — published measurements reproduce by pinning the toolchain.
- **Legible messages (E1)**: every three-argument report site of the set receives a fourth argument; the 17 `but found` sites interpolate the event argument instead of a monitor field; the messages whose text lies are corrected as a precondition — `PBEKeySpecSpec:50` and `PBEParameterSpecSpec:50` promise `>= 1000` while the guard tests `10000` and api30 declares `>= 10000`; `MessageDigestSpec:58,70,92` list 3 entries where the real list has 6; `CipherSpec:61,76` name transformations the Java allow-list does not implement. Every envelope takes its `ev=` from `__EVENTNAME`. Message envelope grammar v1: `v=1 code=<SPEC>-<KIND>-<NN> ev=<event> obj=<SimpleClass> val='<observed>' exp='<expected>' msg='<text>'` — no `st=`, no `\n`, no `:::` inside values; commas allowed (the parser rejoins field 7). `ErrorType` gains **`ForbiddenMethod`** and nothing else: `FORBIDDEN` is not a predicate, it is what `PBEKeySpecSpec f1/f2` encode, and today they report `InvalidSequenceOfMethodCalls`, which is the wrong type. `RequiredPredicate` is deliberately not added, since the set has no predicates. The catalogued wrong types are corrected in the same pass: `PBEParameterSpecSpec:49` (`UnsafeAlgorithm` → `UnsatisfiedConstraint`) and `PBEKeySpecSpec:24,30` (`InvalidSequenceOfMethodCalls` → `ForbiddenMethod`).
- **Weaver `args()` arity (E2) — counter only**: `WrapperEmitter` measures, in the grouping loop where the concrete overload's parameter count is known, how many advices a positional-arity rule *would* exclude (arity read from `ArgsPC.types()`, so `..` is honoured; an advice with no `args()` clause never counts — 44 of the frozen descriptor's 115 advices, among them the **25** `after` advices that take parameters and declare no `args()`, none of which is a constructor advice; the counter's denominator is the 48 `after` non-constructor advices that do declare one, while 9 `before`-with-`args()` and 14 `after`-on-constructor advices sit outside the wrapper path altogether — 48 + 44 + 9 + 14 = 115), and publishes the figure as `advicesExcludedByArity` in the results JSON. **Nothing is filtered and no woven behaviour changes.** The counter exists so the size of the defect is on record and measurable across runs before any filtering decision is taken; the root repair — a binding-form check in `PointcutMatcher` — stays recorded as future work.
- **Honest transport (E3)**: the logcat `ErrorCollector` escapes the message and guards `null`; the CSV collector and the logcat collector agree; `logcat_parser` counts every discarded or continuation line, replaces fabricated fields with explicit sentinels (`error_type=UNSPECIFIED`, `source=UNSPECIFIED:0`), treats an unclosed quote as a truncated record, and no longer scrambles a Format-1 line whose regex fails into the comma path; `unique_msg` is built in exactly one place; the `ViolationRecorder` frame filter no longer lets a monitor frame with a `null` file name become the reported location. **BREAKING** for consumers that regex the free text of `message` (`ase-journal/.../owasp_cwe_mapping_gen.py`, `experimento-gov/scripts/consolidate_gov.py`, `validator/oracles/cryptoapp-oracle.yaml`): the consumer matrix names each and its migration.
- **Validation toolkit (EV)**: the structural gates that are computable on the transition tables become pytest over the generated monitor of any set (G-2a inertia, G-2b′ redundancy at q0, G-2c dead states, G-2d sink is not `fail`, G-6′ event-name injectivity), joined by a `.mop` lint (undeclared or duplicate ERE symbol, unbalanced parentheses, no hand-written event-name bookkeeping — the generator emits the name), a message-property gate (every report site four-argument, numeric literals of a message equal to those of its guard), an **allow-list conformance gate (G-CONF)** that compares each specification's value lists against the `CONSTRAINTS` of its api30 rule — reading the new Java class for `Cipher` and the `.mop` for every other specification — and fails on any difference not entered in the divergence record, a **predicate-absence gate (G-PRED)** that fails on any `REQUIRES`/predicate read or `ExecutionContext` reference in the set, and a **differential harness** that generates monitors from two snapshots of a set and replays the same traces through both, so a repair that moves a defect instead of removing it is seen. Two corrections to the gate list inherited from the lineage: G-2b is not adopted (it is not computable on the artefact — minimisation merges the state it needs — and its absorbing-state repair was already rejected in gh101 D-S9), and **G-2 as an orphan-event check is wrong as stated**. Its "18 orphan events" are not defects: 17 of the 18 are the correct encoding of `CONSTRAINTS`/`REQUIRES`/`FORBIDDEN`, which by definition do not appear in the `ORDER`. The only true orphan is `MessageDigestSpec:73 reset`. G-2 therefore needs the CrySL rule as an input to be meaningful; in its place this change adds the safe gate **G-ERE** — every symbol cited in the `ere` has an event declaration — which catches the `GCMParameterSpecSpec` phantom with zero false positives.
- **Automata and pointcuts (E4)**: scope reduced to the 7 structural defects that are confirmed against the api30 rule, all of them in `jca_android` and each entered in the divergence record — (1) `GCMParameterSpecSpec:33` names its event `c1` where the rule declares `c1` and `c2` and the generated monitor has no `c2` at all (a one-token repair); (2) `SecretKeySpecSpec:27-30` has an extra parenthesis in the `condition`; (3) `MessageDigestSpec:73` declares `reset` with an empty body and no CrySL clause behind it, so it is dead; (4) `KeyPairGeneratorSpec:26` leaves `String algorithm` uninitialised; (5) dead pointcuts at `SignatureSpec:99,:106` and `SSLContextSpec:64` (return type); (6) `KeyPairGeneratorSpec:71-72` is an unreachable branch; (7) `KeyGeneratorSpec:47` and `MessageDigestSpec:55` test `contains(currentAlgorithmInstance)` instead of `contains(alg)`, so the argument just received is never evaluated. The replay of gh101's 51 `layer-2` hunks and 42 `predicate-graph` hunks is **dropped**: the allow-list transcription and the predicate removal already subsume the value-side of that work, and the predicate side no longer exists.
- **Predicates (E5) — removed from the change**, with the reason on record: gh101 landed 42 predicate hunks and the audit's gate G7 still failed 19 of 22 specifications with roughly 5 clean live edges, and 2 of the 3 defects the audit attributes to gh101 itself were predicate edits. A third attempt at the same graph is not a repair with a measurable end; dropping predicates from the successor set is (see the measured cost above).
- **Identity (E6)** — **BREAKING**: `ev` and `code` enter the `ErrorSummary` dedupe identity, `unique_msg` and `errors.csv` (new columns `code`, `event`); the count discontinuity against every published dedupe number is declared and measured, and it must be non-zero.
- **Baseline (E0)**: the residual budget of the E3 trial is measured through `aperv_tool.analysis.violations.read_errors_csv` and a declared separate reader for the 10-column article dataset; the definitions (mute row, site as 4-tuple on comp162 and 3-tuple on the article, the nine-prefix third-party classifier, comp162 as 8 disjoint shards) are registered as freeze items before any number is published, every number with numerator and denominator.

## Capabilities

### New Capabilities

(none — every affected behaviour already has a spec)

### Modified Capabilities

- `instrumentation`: `jca_android` becomes a first-class specification set of 21 specifications (INV-INS-09, Specification Set Support); the message envelope contract of a violation report and the four-argument rule for report sites; the `__EVENTNAME` macro the generator expands and the message-property gate; **allow-list conformance** — every value list transcribed from the `CONSTRAINTS` of the matching `MetaCrySL/generated/api30/` rule, compared case-insensitively through a declared Conscrypt `android11-release` alias table, with every deviation (the `EC` exception, the four ECDSA signature algorithms, the dropped `SecretKeySpec` list) in the divergence record and the `Cipher` list read from its own Java class; **predicate absence** — the set declares no `REQUIRES` clause, reads no predicate and references no `ExecutionContext`, and gate G-PRED enforces it; the weaver's counter-only `advicesExcludedByArity` measurement; the structural gates and the `ere`-symbol declaration gate (G-ERE) as executable pytest for any set; the differential harness; the divergence and conformance records of the successor set; the frozen `jca` requirement gains the sentence that the successor `jca_android` is outside the freeze and that the archived `jca_android_bug_predicate` is not a source.
- `experiment`: `specification_set` already accepted `jca_android`; what moves is what the name resolves to — the successor set, by construction, since the mapping derives the directory from the value's own name — while `jca_android_bug_predicate` is rejected as an invalid value even though the directory now exists. The `click.Choice` keeps its four values and gains none (INV-EXP-03 clause f, Just-in-Time Sub-Module Configuration).
- `analysis`: the logcat violation-line grammar (INV-ANA-08): seven comma-separated fields, message last as a `key=value` envelope; sentinels for fabricated fields; continuation and discarded lines counted; unclosed quote is a truncated record; `unique_msg` built once.
- `core`: `RvErrorLog.unique_msg` gains `code` and `event` parts (INV-CORE-25/41) and the discontinuity is declared.
- `platform`: `errors.csv` gains `code` and `event` columns (INV-PLT-19); write failures are counted, not swallowed.
- `campaign-analysis`: `violations.read_errors_csv` and `parse_payload` read the envelope and the new columns; `ERRORS_CSV_HEADER` changes in step with `platform`; `INV-CAN-04` counters extended to the new drop points it can see.
