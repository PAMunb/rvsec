## Why

GitHub Issue: #104

RVSEC's violation reports cannot be read. In the published dataset 72.93 % of the 97,018 records carry the literal `unknown` as their message (70,760 rows, 19 distinct messages in the whole corpus) and 8,843 more read `but found .` with an empty observed value; the post-repair Study-03 trial (`experimento-comp162`, 19,664 rows) is worse in the first ratio at 79.91 %. The mechanical cause is measured and small — `message == 'unknown'` if and only if the report site used the three-argument `ErrorDescription` constructor (`ErrorDescription.java:34-36`), which is 25 of the 51 report sites of the `jca` set — but three families of defects around it turn readable reports into wrong ones: the dexlib2 weaver ignores positional `args()` arity when it merges advices into one wrapper (a residue of gh100's D-B1 merge that gh100 does not record); the transport path from `ErrorCollector` to `errors.csv` escapes nothing, fabricates fields and drops lines silently at ten points; and the `jca` automata carry messages whose text contradicts the guarding condition or the real allow-list, plus structural defects nobody catalogued. Because the `@fail` handler names neither the offending event nor the observed value, and the dedupe identity (`ErrorSummary` = spec, error, class, method, location) discards exactly the information the message would carry, per-event attribution is impossible today for any consumer of the record — including the analyses this thesis publishes.

Illegibility is not the only cost of the frozen specifications: on Android they are also wrong about what the platform offers, and the size of that error is measured. In the ase-journal corpus the tier of findings that survives primary-source evidence is **11,409 events over 84 misuses — 18.5 % of the 454 misuses of the corpus** — and every one of them is a value the platform genuinely supports which the `.mop` allow-list does not list:

| specification / `ErrorType` / observed value | events | apps | misuses |
|---|---|---|---|
| `SSLContextSpec` / `UnsafeProtocol` / `TLS` | 8,648 | 60 | 65 |
| `KeyStoreSpec` / `InvalidKeyStoreType` / `AndroidKeyStore` | 2,005 | 11 | 12 |
| `TrustManagerFactorySpec` / `UnsafeAlgorithm` / `X509` | 643 | 3 | 5 |
| `CipherSpec` / `UnsafeAlgorithm` / `RSA/ECB/OAEPWithSHA1AndMGF1Padding` | 109 | 1 | 1 |
| `SignatureSpec` / `UnsafeAlgorithm` / `SHA256WITHRSA` | 4 | 1 | 1 |

The whole tier is fixed to one platform context — **API 30 / Android 11, Conscrypt branch `android11-release`** — and the corresponding MetaCrySL rules already exist, generated, under `MetaCrySL/generated/api30/`. Two of the five rows fall out of a straight transcription of those rules: api30 `KeyStore` declares `{AndroidKeyStore, PKCS12, BKS, BouncyCastle, AndroidCAStore}`, which clears the 2,005 events, and api30 `SSLContext` declares `{Default, TLSv1.2, TLSv1.1, SSL, TLSv1, TLS, TLSv1.3}`, which clears the 8,648. The other three do not, and that is the reason this change carries a normalisation rule as a first-class item rather than as a detail.

`jca` is frozen (gh101 D-S0, `INV-INS-109`) and the derived Android set that gh101 left under the name `jca_android` was judged NOT READY by the 2026-08-08 audit, so neither can receive a repair. This change therefore **archives that derived set** — `git mv rvsec-mop/src/main/resources/jca_android rvsec-mop/src/main/resources/jca_android_bug_predicate/`, a directory no CLI value selects any more — and **rebinds the name `jca_android` to a successor set seeded from the frozen `jca` Java set**, which is where every specification-side repair lands; every runtime, weaver and transport repair lands in the shared code both sets execute on. The enumeration of specification sets does not grow: it keeps its four values (`jca`, `jca_android`, `generic`, `custom`), and the successor is reached by the name the derived set used to answer to. The `generic` and `generic_new` sets (145 of the 191 `.mop` files, none of which passes through `ErrorCollector`) are a written non-goal.

## What Changes

- **The name `jca_android` rebound to a new set (S)**: `rvsec-mop/src/main/resources/jca_android/` is rebuilt from the frozen `jca` seed, and the derived set that held the name is archived by `git mv` to `rvsec-mop/src/main/resources/jca_android_bug_predicate/`, which no `--specification-set` value selects. Nothing is added to the enumeration — `--specification-set jca_android` already existed and now resolves to the successor set — and the archived directory is edited by no task and read only as a control — by the differential harness's self-test, by the generator group's regeneration diff (tasks 3.0/3.5/3.8) and by the gh101 gate scripts once task 2.13 repoints them at it. The set carries its own divergence record, conformance record and alias table in `data/jca_android/`; the frozen `jca` and its freeze gate stay untouched. The set has **21 specifications, not 23**: two of `jca`'s files exist only to propagate predicates (`RandomStringPassword.mop`, `SecretKeySpec.mop`) and have nothing left to do once predicates are gone. The oracle of the set is the **already-generated MetaCrySL api30 rules** in `MetaCrySL/generated/api30/`; MetaCrySL itself is not modified by this change, and any place where the generated rule is judged defective is recorded as a divergence instead of being fixed upstream.
- **Allow-lists by literal transcription (S)**: every value list in the set is transcribed literally from the `CONSTRAINTS` block of the corresponding api30 rule — no editorial additions, no carry-over of lists the rule does not declare. A comparison of 74 constants between today's `jca` `.mop` files and api30 gives the size of the move: 30 constants the rule declares and the `.mop` ignores, 14 identical, 13 the `.mop` tests with no basis in the rule, 7 where the `.mop` is more permissive, 7 divergent, 3 where the `.mop` is more restrictive — a summary carried over from the pivot analysis; no row-level table exists in the tree yet, so these six counts are provisional until task 2.15 commits `data/jca_android/constraint_table.csv`, and the committed table, not this sentence, is what G-CONF reproduces. Four consequences are decided rather than discovered: `SecretKeySpecSpec`'s algorithm allow-list **disappears** (api30 declares nothing about `alg`, so the list has no basis); the `CipherSpec` allow-list **stays in Java**, in a **new class** under `rvsec-core/.../jca/util/` transcribed from `generated/api30/Cipher.cryptsl`, because `CipherTransformationUtil` belongs to the frozen `jca` and `AndroidCipherTransformationUtil` belongs to the archived `jca_android_bug_predicate` and neither may be altered; and `EC` **is kept** in the `KeyPairGenerator` allow-list — the seed already carries it (`KeyPairGeneratorSpec.mop:22`, `validate` at `:34`) and the literal transcription would remove it, since api30 `KeyPairGenerator.cryptsl:45` lists `{DSA, DH, RSA}` — as the first of the two registered exceptions to literal transcription, kept against the rule with keySize 256 and the reason written into the divergence record — `samples/jca/android/11plus/KeyPairGenerator.ref:2` declares `define algorithm = {"EC"};` but `samples/jca/base/KeyPairGenerator.cryptsl:27` writes the list as a literal (`alg in {"DH","DSA","RSA"}`) instead of `alg in ${algorithm}`, so the refinement is discarded in silence and the generated rule leaves its own `alg in {"EC"} => keySize in {256}` clause unreachable. Removing `EC` on that basis would fabricate exactly the class of specification artefact this change exists to remove, since `EC` is the algorithm Android recommends for `AndroidKeyStore`. The second and last exception is `SignatureSpec`: `generated/api30/Signature.cryptsl` lists twenty algorithms and exactly one ECDSA among them — `SHA224withECDSA`, the only ECDSA any tier touched, and it is the `20plus` tier — while Conscrypt registers aliases pointing at `SHA1withECDSA`, `SHA256withECDSA`, `SHA384withECDSA` and `SHA512withECDSA` (`OpenSSLProvider.java:270,271,286,293,300`); an alias can only point at an algorithm the provider registers, so the four provably exist on API 30 and the four are added with their own divergence entry. Without them `SHA256withECDSA` — the pairing Android recommends for EC keys in `AndroidKeyStore`, and a value the `jca` `.mop` already accepted — would become a false positive. Both exceptions obey one asymmetric rule, and that rule governs every later question about a list: **where the api30 rule admits a value, the set admits it**, whatever the frozen `jca` thought of it, and the cost of that half is measured — 5,892 of the 6,048 `MessageDigestSpec` / `UnsafeAlgorithm` rows of the published dataset (3,552 `MD5` plus 2,340 `SHA-1`/`SHA1`/`SHA`) stop being reported, 97.4 % of that specification's `UnsafeAlgorithm` reports (36.4 % of all its 16,183 reports) and 6.1 % of the 97,018 rows of the corpus, entered in the conformance record as a declared loss — in `jca_android` the `UnsafeAlgorithm` type (KIND `ALG`) therefore means "value outside the api30 allow-list of the platform", not "cryptographically insecure": MD5 and SHA-1 are admitted by the api30 `MessageDigest` rule and are no longer reported, and the `ErrorType` name is kept for continuity with `jca` with the meaning shift declared, not hidden; **where the api30 rule omits what the platform provably carries, the set adds it**, with a divergence entry citing a platform source. The set never removes what api30 permits. A third recorded class covers incompleteness in the other direction: a `CONSTRAINTS` clause the rule declares and this change does not begin to check becomes a **`deferred-constant`** row of the conformance record naming the clause and the reason it is deferred, because transcribing a check the set has never run changes what is accused with no before/after evidence behind it — the 30 such constants are enumerated by `constraint_table.csv` and none may be skipped in silence.
- **No `REQUIRES`, no predicates (S)**: the successor set carries no predicate clause and therefore never touches `ExecutionContext`. The cost is measured, not assumed. Of the 21 events that read a predicate (all of them inside `condition()`, spread over 8 of the 21 files the seed keeps), **10 use it only as a guard**, so removing it is a net gain — today those guards silence the specification. **11 accuse on the strength of a predicate** and lose detection: 7 total losses (`IvParameterSpec c3/c4`, `PBEKeySpecSpec err2/err3`, `SecureRandomSpec c3/setSeed3` — `c3` stores the object and reports nothing itself, but its transition row is all-`fail`, `{3,3,3,3}` at `MultiSpec_1RuntimeMonitor.java:7899`, so every firing accuses through `@fail` — and `SecretKeySpecSpec c3`, whose predicate half goes here and whose allow-list half goes with the api30 transcription, because the rule declares nothing about `alg`), 1 partial (`PBEParameterSpecSpec c3`, whose iteration-count half survives) and 3 cross-specification key-provenance checks (`CipherSpec i2`, `MacSpec i1/i2`, on `GENERATED_KEY`) that **already did not work on Android** — the ase-journal records that keys from `AndroidKeyStore`, Tink and `KeyGenParameterSpec` never carry `GENERATED_KEY`, over 11,620 events / 80 misuses / 25 apps. Removal also deletes 9 `remove(...)` sites — 4 of the deprecated one-argument `remove(Property)`, 5 of the two-argument `remove(Property, Object)` — against only **2 `NEGATES` clauses in the whole of api30**; one of the nine, `PBEKeySpecSpec:72` in `clearPassword`, is exactly what the rule's `NEGATES speccedKey after cP` asks for, and the other eight have no clause behind them, which is the measure of how much of the predicate graph was ever grounded in the rule. Every removed site is written to `data/jca_android/predicate_removal.csv`; the file name is load-bearing, because gh101's `predicate_omissions.csv` records a different thing — a `Property` written and never read — and the two records must never be used interchangeably.
- **Declared normalisation rule (S)**: value comparison in the set is **case-insensitive**, and each specification carries a declared alias table derived from Conscrypt `android11-release` with a per-entry source pointer. Without it, literal transcription leaves roughly 3,000 measured events uncorrected even with the right list: `X509` (643 events) is Conscrypt's alias for `PKIX` (`OpenSSLProvider.java:90`), not an algorithm, and api30 `TrustManagerFactory` declares `{PKIX}` alone; `SHA256WITHRSA` (4 events) differs from api30's `SHA256withRSA` only in case; and the `SHA1`/`SHA` → `SHA-1` and `SHA256` → `SHA-256` aliases (`OpenSSLProvider.java:115-116` and `:124`) fragment 2,340 events over 22 misuses across three spellings. Those two pointers correct the ase-journal's `docs/20260806_owasp_cwe_mapping_report.md`, which cites `:101-107` for `X509` and `:131-132,140` for the digests — `:101-102` is `AlgorithmParameters` DESEDE/TDEA, `:131-132` is `SHA-512`/`SHA512` and `:140` is `KeyGenerator.ARC4`, which is not an alias at all; that report's own CSV and annex already carry the correct `:89-90`. The committed table (`data/jca_android/alias_table.csv`) has **158** rows with an `in_api30_allowlist` flag: the provider declares 175 `Alg.Alias.*` registrations, 158 of them in services a specification covers or api30 declares a rule for — 149 in services one of the 21 specifications covers, and 9 (`AlgorithmParameters` 8, of which 5 `yes` and 3 `no`; `SecretKeyFactory` 1, `yes`) in services with no specification, kept in the table with the flag — and **114** of the 158 reach an entry of an api30 allow-list (44 are `no`) — Signature 39, Mac 24, KeyGenerator 23, MessageDigest 12, AlgorithmParameters 5, KeyPairGenerator 5, Cipher 4, TrustManagerFactory 1, SecretKeyFactory 1 — of which **108** lie in services the 21 specifications cover and resolve at run time, while the 6 `AlgorithmParameters`/`SecretKeyFactory` `yes` rows are flagged against a rule the set does not carry. The fifth measured value of the tier, `RSA/ECB/OAEPWithSHA1AndMGF1Padding` (109 events), is **not** closed by this rule and gets no row: the observed spelling carries no hyphen in `SHA1`, api30 declares `OAEPwithSHA-1andMGF1Padding`, and Conscrypt registers only hyphenated spellings (`:338`, and the alias at `:339-340`), so there is no provider line a row could cite and no reason to weaken the per-entry pointer requirement for one value. Since `CipherSpec.g1` is an `after … returning(Cipher c)` advice, the 109 calls returned a `Cipher` — behavioural proof that another platform provider accepts the spelling, the candidate being the Bouncy Castle build Android ships — so the case is entered in the divergence record with its evidence labelled **behavioural**, and naming that provider is execution work. The rule also removes an inconsistency the set inherits: comparison is case-sensitive in 8 specifications (`Mac`, `Signature`, `SecureRandom`, `KeyGenerator`, `TrustManagerFactory`, `KeyManagerFactory`, `KeyStore`, `KeyPairGenerator`) and `.toUpperCase()`-normalised in 3 (`MessageDigest`, `SSLContext`, `SecretKeySpec`).
- **Event name from the generator (G)**: `rv-monitor` gains a `__EVENTNAME` macro — expanded to a string literal inside an event body, and inside a `@fail` handler to the name of the event that last transitioned the monitor. This is information the generated monitor already holds and throws away: it packs the event index into `pairValue` (or keeps it in `RVM_lastevent`), and the generator writes the matching names as *comments* in `terminateInternal`. Emitting them as a table costs two substitution sites and one array, instead of 134 hand-written bookkeeping lines per specification set, and it cannot produce a wrong name because the table and the indices come from one iteration. The freeze is on the specification sources, not on generated monitors — published measurements reproduce by pinning the toolchain.
- **Exception-safe dispatchers (G)**: the generated monitor takes a single global `ReentrantLock` in every dispatcher — `while (!MultiSpec_1_RVMLock.tryLock()) Thread.yield();` at entry, `unlock()` at exit — and releases it on no path but the normal one. Measured on the frozen control: 134 acquisitions, 134 releases, **zero `finally` blocks in the whole generated file**, one lock shared by every specification (`MultiSpec_1RuntimeMonitor.java:9005`). Any exception raised inside a handler therefore retains the lock permanently, and because every other dispatcher spins on `tryLock()` in a `Thread.yield()` loop, the first exception silently converts the monitored application into a livelock across all specifications — the instrumentation stops reporting and the app stops making progress, with nothing in the record to say why. The path is not hypothetical: `KeyPairGeneratorSpec.mop:29` switches on an uninitialised `String`, and `KeyPairGenerator.getInstance(String, Provider)` has no pointcut, so a `KeyPairGenerator` obtained through that overload reaches `initialize(int)` with `algorithm == null` and `switch(null)` raises. The generator SHALL wrap the guarded region so the lock is released on every exit; nothing else about the dispatcher changes, and the repair is checked by regenerating the frozen `jca` and diffing (the only expected differences are the `try`/`finally` framing, the event-name table and the expanded macro).
- **Legible messages (E1)**: every three-argument report site of the set receives a fourth argument; the 16 `but found` sites that interpolate a monitor field interpolate instead the value read from the target object the event binds (`digest.getAlgorithm()`, `k.getType()`, `ctx.getProtocol()`, `s.getAlgorithm()`, `m.getAlgorithm()`, `c.getAlgorithm()`, `mf.getAlgorithm()`, `k.getAlgorithm()`) — none of the 16 reporting events binds the algorithm, type or protocol argument (only the `getInstance` events do), so the argument form of `SecureRandomSpec:82` does not transfer to them, while every one of them binds the target; the messages whose text lies are corrected as a precondition — `PBEKeySpecSpec:50` and `PBEParameterSpecSpec:50` promise `>= 1000` while the guard tests `10000` and api30 declares `>= 10000`; `MessageDigestSpec:70,92` (and the commented `:58`, un-commented by task 7.4) list 3 entries where the real list has 6; `CipherSpec:61,76` list two accepted transformations and elide the rest with a literal `...`. Every envelope takes its `ev=` from `__EVENTNAME`. Message envelope grammar v1: `v=1 code=<SPEC>-<KIND>-<NN> ev=<event> obj=<SimpleClass> val='<observed>' exp='<expected>' msg='<text>'` — no `st=`, no `\n`, no `:::` inside values; commas allowed (the parser rejoins field 7). `ErrorType` gains **`ForbiddenMethod`** and nothing else: `FORBIDDEN` is not a predicate, it is what `PBEKeySpecSpec f1/f2` encode, and today they report `InvalidSequenceOfMethodCalls`, which is the wrong type. `RequiredPredicate` is deliberately not added, since the set has no predicates. The catalogued wrong types are corrected in the same pass: `PBEParameterSpecSpec:49` (`UnsafeAlgorithm` → `UnsatisfiedConstraint`) and `PBEKeySpecSpec:24,30` (`InvalidSequenceOfMethodCalls` → `ForbiddenMethod`).
- **Weaver `args()` arity (E2) — counter only**: `WrapperEmitter` measures, in the grouping loop where the concrete overload's parameter count is known, how many advices a positional-arity rule *would* exclude (arity read from `ArgsPC.types()`, so `..` is honoured; an advice with no `args()` clause never counts — 44 of the frozen descriptor's 115 advices, among them the **25** `after` advices that take parameters and declare no `args()`, none of which is a constructor advice; the counter's denominator is the 48 `after` non-constructor advices that do declare one, while 9 `before`-with-`args()` and 14 `after`-on-constructor advices sit outside the wrapper path altogether — 48 + 44 + 9 + 14 = 115), and publishes the figure as `advicesExcludedByArity` in the results JSON. **Nothing is filtered and no woven behaviour changes.** The counter exists so the size of the defect is on record and measurable across runs before any filtering decision is taken; the root repair — a binding-form check in `PointcutMatcher` — stays recorded as future work.
- **Honest transport (E3)**: the logcat `ErrorCollector` escapes the message and guards `null`; the CSV collector and the logcat collector agree; `logcat_parser` counts every discarded or continuation line, replaces fabricated fields with explicit sentinels (`error_type=UNSPECIFIED`, `source=UNSPECIFIED:0`), treats an unclosed quote as a truncated record, and no longer scrambles a Format-1 line whose regex fails into the comma path; `unique_msg` is built in exactly one place; the `ViolationRecorder` frame filter no longer lets a monitor frame with a `null` file name become the reported location. **BREAKING** for consumers that regex the free text of `message` (`ase-journal/.../owasp_cwe_mapping_gen.py`, `experimento-gov/scripts/consolidate_gov.py`, `validator/oracles/cryptoapp-oracle.yaml`): the consumer matrix names each and its migration.
- **Validation toolkit (EV)**: the structural gates that are computable on the transition tables become pytest over the generated monitor of any set (G-2a inertia, G-2b′ redundancy at q0, G-2c dead states, G-2d sink is not `fail`, G-6′ event-name injectivity), joined by a `.mop` lint (undeclared or duplicate ERE symbol, unbalanced parentheses, no hand-written event-name bookkeeping — the generator emits the name), a message-property gate (every report site four-argument, numeric literals of a message equal to those of its guard), an **allow-list conformance gate (G-CONF)** that compares each specification's value lists against the `CONSTRAINTS` of its api30 rule — reading the new Java class for `Cipher` and the `.mop` for every other specification — and fails on any difference not entered in the divergence record, a **predicate-absence gate (G-PRED)** that fails on any `REQUIRES`/predicate read or `ExecutionContext` reference in the set, and a **differential harness** that generates monitors from two snapshots of a set and replays the same traces through both, so a repair that moves a defect instead of removing it is seen. Two corrections to the gate list inherited from the lineage: G-2b is not adopted (it is not computable on the artefact — minimisation merges the state it needs — and its absorbing-state repair was already rejected in gh101 D-S9), and **G-2 as an orphan-event check is wrong as stated**. Its "18 orphan events" are not defects: 17 of the 18 are the correct encoding of `CONSTRAINTS`/`REQUIRES`/`FORBIDDEN`, which by definition do not appear in the `ORDER`. The only true orphan is `MessageDigestSpec:74-76 reset` — and calling it dead was itself wrong. It carries no `condition()` to gate it and no place in the `ere`, so the generator gives it the transition row `{4,4,4,4,4}` (`MultiSpec_1RuntimeMonitor.java:6369`) against a `fail` state of 4 (`:6504`), and every `MessageDigest.reset()` the weaver reaches accuses unconditionally, algorithm irrelevant. It is the only orphan of the frozen set that is both unaccounted for by a clause and ungated by a `condition()`; the other two ungated orphans are `PBEKeySpecSpec`'s `f1`/`f2`, which encode a `FORBIDDEN` clause and are supposed to accuse on sight. Two qualifications, both measured on the frozen monitor: the 17 are correct in what they *report* and not in what they *transition to* — every one of them carries an all-`fail` row, so each firing also runs `@fail`, emits a second, unlabelled `InvalidSequenceOfMethodCalls` and `__RESET`s the automaton (the corpus shows the footprint: `SSLContextSpec` 17,510 sequence rows against 2 × 8,802 `UnsafeProtocol`; `TrustManagerFactorySpec` 9,015 against 9,014 `UnsafeAlgorithm`), which is a behavioural matter recorded and deferred, not a G-2 hit; and a strictly mechanical clause mapping leaves not one but three orphans of the frozen `jca` without a clause — `reset`, `PBEKeySpecSpec.err2` (it tests `RANDOMIZED[password]`; the rule requires `randomized[salt]` only) and `SecretKeySpecSpec.c3` (it tests an algorithm list the rule does not declare) — all three absent from `jca_android` by construction, `reset` through E4 and the other two through the predicate removal and the transcription. G-2 therefore needs the CrySL rule as an input to be meaningful; in its place this change adds the safe gate **G-ERE** — every symbol cited in the `ere` has an event declaration — which catches the `GCMParameterSpecSpec` phantom with zero false positives.
- **Automata and pointcuts (E4)**: scope reduced to the structural defects that survive confrontation with the api30 rule, the JDK signature or the generated monitor, all of them in `jca_android` and each entered in the divergence record. Six are repaired: (1) `GCMParameterSpecSpec:34` names its second event `c1` where the rule declares `c1` and `c2` and the generated monitor has no `c2` at all — a one-token repair whose effect is on the gates alone, since the monitor is indexed by the constructed object and its `fail` state is unreachable before and after; (2) `SecretKeySpecSpec:27-30` has an extra parenthesis in the `condition`, which the JavaMOP parser discards in silence (`javamop.jj:1440` captures the pointcut as raw text and `aspectj.jj:49` parses it without requiring `<EOF>`), so the repair is textual and the generated guard is already correct — and Group 2 dissolves the surrounding `condition` entirely, which makes this a check rather than an edit; (3) `MessageDigestSpec:74-76` declares `reset` with an empty body, no clause behind it and **no `condition()`**, so it is not dead but an unconditional accuser — removing it is the one repair of the group that takes accusations away, and it is the repair the archived `jca_android_bug_predicate` had already made; (4) `KeyPairGeneratorSpec:26` leaves `String algorithm` uninitialised — written by the `getInstance` events `g1`/`g2`/`g3` and not by the `init*` events, and first read by the `switch` of `validate()` at `:29`, where a `null` raises `NullPointerException` rather than a false accusation — so the three `initialize` events (`init1`, `init2`, `initError`) are conditioned on `algorithm != null`, which is the only accusation-neutral form: a guard inside `validate()` alone would make `initError` fire (`condition(!validate(keySize))`) and add two reports where the call raises today (D-14 covers what that exception does to the dispatcher lock); (5) the dead pointcuts of `SignatureSpec:99,:106`, whose `sign()` is declared returning `byte` where the API returns `byte[]` and `int` — the only site of the family where the automaton is genuinely broken, because `s1`/`s2` are the sole path to the accepting state of the signing branch and the monitor stalls in state 7 without them; (6) `KeyPairGeneratorSpec:71-72` is an unreachable branch, proven so because `validate()` returns `true` exactly for the members of `safeAlgorithms`, and it is removed with the note that `g3` is the event that could host the rule's `CONSTRAINTS` clause. Two further dead pointcuts are **measured and not repaired**, because reviving them only adds accusations and the corpus cannot size that: `SSLContextSpec:64` (`createSSLEngine` declared `void`), where the CrySL `Engine?` is optional and acceptance already comes from `init`, and `TrustManagerFactorySpec:63` (`getTrustManagers` declared returning `KeyManager[]`, with a `returning(TrustManager[][])` clause), catalogued by the lineage together with its two further defects — the binding `k` instead of the declared parameter `mf`, which sends `gtm1` and `g3` to the empty parameter slice and broadcasts them to every live monitor of the specification, and the double-array `returning` (`data/gh101/divergence_record.csv:101,105-106`) — and which sits in the `fsm` with the transition `{3,0,3,3}` on the specification that carries 18,029 of the corpus's rows. One item is **withdrawn**: the guard of `KeyGeneratorSpec:47` and `MessageDigestSpec:55` testing `contains(currentAlgorithmInstance)` is not a defect, because `g1` is emitted before its sibling in the same wrapper (`MonitorWrappers.java:192-193,357-358`) on the same object-indexed monitor and writes the field first, which makes the field test equivalent to the argument test. The sweep behind the four dead pointcuts covered the return types of all 141 `call(` pointcuts of the 21-file seed against `android-30`, and nothing else; the structural divergences it did not cover and that the frozen monitor proves — non-parametric monitors (`KeyStoreSpec` declares `ks` and binds `k`, the two stream specifications declare no parameter), empty-binding broadcasts (`MacSpec.f2`, `PBEKeySpecSpec.f1/f2`, `SSLContextSpec.unsafe_protocol`, `TrustManagerFactorySpec.g3/gtm1`), `ORDER` clauses the `fsm` narrows (`SecureRandom` `end` without `nextBytes`, `Cipher` `s3` without an `update` loop, `KeyPair` with a mandatory constructor), the `getInstance(String, Provider)` overload bound in no specification, the second `InvalidSequenceOfMethodCalls` every clause-encoding orphan emits through its all-`fail` row, and the DEX-path double fire of `g1`+`g2` on one-argument `getInstance` — are entered as **measured, not repaired** rows of the conformance record with their monitor line and corpus mass, so the successor set inherits them on the record and not in silence. The replay of gh101's 51 `layer-2` hunks and 42 `predicate-graph` hunks stays **dropped**: the allow-list transcription and the predicate removal already subsume the value-side of that work, and the predicate side no longer exists.
- **Predicates — a non-goal (see D-11)**, with the reason on record: gh101 landed 42 predicate hunks and the audit's gate G7 still failed 19 of 22 specifications with roughly 5 clean live edges, and 2 of the 3 defects the audit attributes to gh101 itself were predicate edits.
