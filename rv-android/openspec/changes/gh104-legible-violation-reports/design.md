**The mechanism.** `ErrorDescription.java:34-36` (rvsec-core): the three-argument constructor delegates with the literal `"unknown"`; `toString()` (`:143`) renders `[%s] %s at %s expecting %s`. The logcat `ErrorCollector.java:36-40` emits `getErrorSummary() + "," + getExpecting().trim()` after `errors.add(err)` on a `HashSet` whose identity is `ErrorSummary` (`:73-120`: spec, error, classQualifiedName, methodName, location); the escaping method at `:42-49` is dead code (its call is commented at `:38`). In the frozen `jca` (23 files, 1,912 lines, 134 events): 51 `new ErrorDescription(` = 25 three-argument (21 `@fail` + `IvParameterSpec.mop:48,55` + `PBEKeySpecSpec.mop:24,30`) + 26 four-argument (one commented, `MessageDigestSpec.mop:57-58`); 18 grep hits for `but found` = 16 active field-interpolating sites + `SecureRandomSpec.mop:82` (argument) + the commented `MessageDigestSpec.mop:58` (argument); 21 files with exactly one `@fail`, `RandomStringPassword.mop` and `SecretKeySpec.mop` with none; only `KeyPairGeneratorSpec.mop:110-113` lacks `__RESET`. The generated event method emits the `condition()` guard **before** the `.mop` body (`if ( ! (cond) ) { return false; }`, verified on `KeyManagerFactorySpec.Prop_1_event_g3`), and the body before the transition, so an event that fails its guard neither runs its body nor transitions and cannot be the event that reaches `fail`.

**What the generated monitor already knows.** The monitor tracks the last event itself, in two shapes that coexist in one generated file — 15 classes of the atomic/table shape (`extends AbstractAtomicMonitor`; the event index is packed into `pairValue` as `((lastEvent + 1) << numStateBits) | state` and read back by `getLastEvent()`) and 8 of the non-atomic shape (a plain `RVM_lastevent` field, assigned inline in the event method, with **no** `getLastEvent()` accessor). The generator branches between them already (`BaseMonitor.java:114-118` `isAtomicMoniorUsed()`, `:1044-1048`, default `"RVM_lastevent"` at `MonitorTermination.java:73`). It also holds the event **names**: `MonitorTermination.java:131-133` iterates `this.events` and writes `"case " + event.getIdNum()` followed by `"//" + event.getId()` — index and name, paired, emitted as a comment. The `@fail` body is inlined into `Prop_N_handler_fail()`, a method of that same monitor class, and `__RESET` (`this.reset()`, which zeroes the last event) is substituted *after* the `addError` call, so at report time the offending event is still there. What is missing at runtime is only the index→name table.

**How the `.mop` macros are expanded.** `__RESET`, `__LOC`, `__DEFAULT_MESSAGE`, `__SKIP` and `__ACTIVITY` are plain `replaceAll` on the body text, at three sites of the Java path: `BaseMonitor.java:350-368` (event bodies), `HandlerMethod.java:36-48` (handler bodies, `@fail` among them) and `RawMonitor.java:90-105` (raw-monitor mode). `SuffixMonitor` does not substitute (only a commented `has__LOC` at `:245`); `logicpluginshells/fsm/CFSM.java` and `tfsm/CTFSM.java` are the **C** output (they import `rvmonitor.c.rvc.CSpecification`) and are off this path. `javamop` does not participate: it carries the Java block from `.mop` to `.rvm` verbatim, which is why `__LOC` traverses it today without javamop knowing what it is.

**The oracle, and what it is not.** The MetaCrySL rules already generated under `generated/api30/` are the oracle of this change. They were produced with Java 8 and `rascal-0.19.6.jar` from the MetaCrySL root, config `samples/jca/android/config/Android30.config`; the API level is a directory convention plus the tier list inside the `.config`, and refinement can only ADD (there is no `remove` command). That generation is recorded here for reproducibility only: **MetaCrySL is not edited by this change**, not even where D-10 names a modelling defect in it.

**Constraints inherited.** `jca` frozen at `7e7acb69` (gh101 D-S0; gate `tests/parity/test_gh101_specset_gates.py`, 5 tests, green). The derived Android set of gh101 is NOT READY (audit `audit/20260808_validacao_jca_android/global/juizglobal_relatorio.md:616-619`, 22/22 REPROVADA; G11 records three defects introduced by gh101: `GENCIPHER-EXTRA` task 5.1, `SSL-RANDOMIZED-EXTRA` task 3.2, `KPG initError` placement); its directory is archived as `jca_android_bug_predicate` and the name `jca_android` is rebound to the successor set. `ExecutionContext` is equality-keyed at HEAD (`e204e2a4`, 2026-08-11, reverted gh101 D-S10; gh101's `data/gh101/README.md:308-317` and tasks 4b.1-4b.4 still describe identity keying — stale, noted here, not rewritten); under D-11 the successor set touches `ExecutionContext` at no site at all, so the keying question does not reach it. ## Goals / Non-Goals

**Goals:** every report from `jca_android` names its event and its observed/expected values in a machine-readable envelope; no report says `unknown` or `but found .`; every allow-list of the set is a literal transcription of the `CONSTRAINTS` of the matching api30 rule under one declared normalisation rule, so that the set stops accusing `AndroidKeyStore`, `TLS` and `X509`; the transport counts every discard; the weaver publishes how many advices its merged wrappers fire in violation of positional arity; the gates run as pytest for any set and take the CrySL rule as input where the verdict depends on it; the harness makes moved defects visible; per-event attribution reaches `errors.csv` and the dedupe identity, with the discontinuity declared; the frozen `jca` keeps reproducing.

**Non-Goals, each with the reason it is one:**

- **Predicates.** `jca_android` carries no `REQUIRES` machinery: no `ExecutionContext` read, write or `remove`, no `RequiredPredicate` error type, and no specification whose only job is to propagate a predicate. The reason is measured in D-11: gh101 spent 42 hunks on the predicate graph and the audit's G7 still fails 19 of 22 specifications with roughly five live clean edges; two of the three defects gh101 introduced were predicate edits; and on Android the three cross-spec provenance detections that the removal costs are already inoperative, because keys from `AndroidKeyStore`/Tink/`KeyGenParameterSpec` never carry `GENERATED_KEY` (11,620 events / 80 misuses / 25 apps).
- **Filtering advices by `args()` arity.** The three-clause rule is implemented and evaluated, but no advice is excluded from a merged wrapper; only the count is published (D-6). Changing which advices fire changes which calls are accused — the same class of behavioural risk as the replay below — and this change does not have the before/after device evidence to take it. The counter is what buys that evidence.
- **The behavioural replay of gh101's 94 non-allow-list hunks.** The lineage's D-A(ii) planned to replay them into the successor set. It does not land here (D-1): those repairs are exactly the body of work the 2026-08-08 audit judged 22/22 REPROVADA, three of them are defects gh101 itself introduced, and none of them is on the path to the 11,409 events / 84 misuses the Android allow-lists resolve. The change's own harness and the arity counter are the instruments that would justify reopening it later.
- **MetaCrySL.** The `.cryptsl` sources and the Rascal generator are read, never edited — including at `samples/jca/base/KeyPairGenerator.cryptsl:27`, where D-10 names a modelling defect and prescribes the root fix without performing it.
- **The archived derived set (`jca_android_bug_predicate`).** Not repaired, not extended, not used as the seed, and not selectable; it is renamed and left in the tree so the 2026-08-08 audit keeps its subject.
- **`jca`.** Not unfrozen. The freeze is on the specification sources, not on the generated monitor (D-4).
- **The `generic` and `generic_new` sets** (145 files, `Log.v` path, never ran; 11 `generic` files do not compile — duplicated parameter names — and `FSM358.mop:4,6` has an import collision; recorded as debt, see plan `docs/20260815_javamop_mensagens.md:805-817` WS-8).
- **The absorbing-state repair of the Form-B residue** (rejected, gh101 D-S9) and **G-2b** as the lineage stated it (not computable, D-7).
- **The binding-form arity check in `PointcutMatcher`** (`:268-306`), which leaves both the 9 `before` advices with `args()` and the 14 `after`-on-constructor advices with `args()` outside even the counter's reach — enumerated in D-6, with the consequence that four of them raise report sites E1 makes legible.
- **Re-measuring the published corpus on device** (device validation is one task, on four APKs, not a campaign) and **end-of-trace detection and localisation options** (O-7/O-8).

## Decisions

### D-1 — the successor set is `jca_android`: a new directory, seeded byte-for-byte from the frozen `jca`, targeted at Android API 30

**What was decided and what it replaces.** The lineage's D-A(ii) fixed the lineage of the successor set (`jca` as seed, not the derived Android set) and then added a second clause: E4 would *replay* the 94 non-allow-list hunks that `data/gh101/divergence_record.csv` records between the derived set — archived here as `jca_android_bug_predicate` — and `jca` (106 hunks total: 51 `layer-2-repair`, 42 `predicate-graph`, 1 `cipher-import`, 12 `allow-list`). **The seed clause stands; the replay clause is withdrawn.** The set is named `jca_android`, it is a new directory under `rvsec-mop/src/main/resources/`, it is byte-identical to `jca` at its seed commit, and its declared target is Android API 30 / Android 11 — the platform of the published measurement (`dataset.tex:5`).

**How the name is freed.** The name `jca_android` already belonged to gh101's derived set. Rather than invent a third name and leave three JCA sets on offer, the derived set's directory is renamed to `rvsec-mop/src/main/resources/jca_android_bug_predicate/` and removed from every enumeration, and the successor takes the vacated name. So the `click.Choice` and `valid_spec_sets` keep four values — nothing is appended — and what changes is which directory the second of them resolves to. The archived set is preserved, not deleted: it is the artefact the 2026-08-08 audit assessed, and a reader of that audit needs it to be able to look. It is not selectable, because a set that must not be run in a new campaign should have no value a reader can mistake for an offer; reproducing the audit is done by pointing `RVSEC_HOME` at the commit it was run against. The name states the reason it was set aside — the predicate regime whose defects the audit measured, exactly what D-11 removes rather than repairs — so the reason survives without the change history.

**Why the seed is `jca`, not the derived set.** The derived set is the one that already carries an Android derivation, so it is the obvious seed and it is the wrong one: the 2026-08-08 audit judged it 22/22 REPROVADA (`audit/20260808_validacao_jca_android/global/juizglobal_relatorio.md:616-619`) and named three defects gh101 introduced into it (`GENCIPHER-EXTRA`, `SSL-RANDOMIZED-EXTRA`, the `KPG initError` placement). Seeding from it would start the successor set from a body of text whose per-spec verdicts are failing, with no gate able to tell an inherited defect from a new one. **Why the replay is withdrawn.** Three reasons, in order of weight. (iii) The replay is not on the path to the problem. The evidence tier of the published analysis is 11,409 events / 84 misuses and every one of them is an allow-list verdict; not one of them is fixed by an automaton repair. Spending the change's budget on the 94 hunks would leave the Android allow-lists wrong and the reports still false.

### D-2 — E1 (messages) lands before E4 (allow-lists and structural repairs), with a new written reason

The lineage ordered C-4 → C-3 because "the message names states that C-4 will create". That reason died when `st=` left the envelope (`_lacunas.md:651-666`); the verification (`§6.5`) asks for a new reason or a new order. **Decision: E1 first.** Reasons: (i) E1 is cheap and mechanically verified — 25 four-argument edits and 17 field→argument swaps — and it makes every later repair *readable*: the differential harness (EV) reports the accusing event by name only once `ev=` exists, so E4's before/after evidence is per event instead of per site; (ii) both edit the same `.mop` files, so they never run in parallel per change; they run in parallel **per file** with one owner per file at a time (WORKFLOW §5 locality). The alternative — E4 first — leaves the harness blind during the stage that most needs it.

Under D-4 as revised, the ordering argument no longer rests on E1 installing a bookkeeping invariant that constrains E4: the event name comes from the generator, so E4 adds, renames and removes events with no obligation towards `ev=`. What E4 still inherits from E1 is the `code`/`codes.csv` bijection — an E4 edit that adds or removes a report site adds or removes its row, and the message-property gate holds that. One more inheritance is new: E1 writes the *expected* value of every message from the allow-list of the file it is in, so E4's transcription of that allow-list (D-10) changes the message text too; the message-property gate is what keeps the two in step, and it is why the transcription runs after E1 rather than before it.

### D-3 — the envelope: `key=value`, commas allowed, `\n`/`:::` forbidden, unclosed quote means truncation

Grammar (fixed by the researcher): `v=1 code=<SPEC>-<KIND>-<NN> ev=<event> obj=<SimpleClass> val='<observed>' exp='<expected>' msg='<text>'`. JSON was rejected in the lineage (braces, commas and quotes in a positional line — `FINAL:199`). The lineage's comma prohibition is dropped: 27.06 % of today's messages contain commas (every `String.join(",", …)` allow-list) and all four consumers already rejoin field 7 (`logcat_parser.py:341-350`; `violations.py:140-160` `split(",", 6)`; `clock_logcat_join.py:454-460`; `TraceComparator.parseObserved`). `\n` splits the logcat line (a second RVSEC line with no structure — a fabricated record); `:::` is the `unique_msg` separator. Escaping: `'` → `\'` inside values (zero occurrences today, so the property tests exercise it synthetically); `\n` → `\\n` by the collector. Truncation: `LOGGER_ENTRY_MAX_PAYLOAD` = 4068 bytes on API 30 (`_lacunas.md:229-269`); measured envelope sizes on the trial: median 274 B, p99 391 B, max 696 B — so truncation is not a volume risk, only a pathological-`val` risk; producer caps `val` at 512 characters, and the parser treats an unclosed final quote as a truncated record (`truncated=True`, counted), never as a value. `code` KIND vocabulary: `ORDER` (`@fail`), `ALG` (algorithm outside allow-list), `CONSTR` (argument constraint), `KEYSIZE`, `KSTYPE`, `PROTO`, `FORB` (`ForbiddenMethod`, D-13); `NN` two digits per spec×kind, listed in `codes.csv` (`spec,code,error_type,site_kind,event,file_line`), bijective with the sites (gate). The lineage's eighth kind, `REQ` (`RequiredPredicate`), is dropped with the predicates (D-11) — no site of `jca_android` can emit it.

### D-4 — the event name is emitted by the generator as a `__EVENTNAME` macro, not written by hand in 134 bodies

**Superseded decision, recorded so it is not re-taken.** This design first put the bookkeeping spec-side: `String lastEventName = "";` in every `declarations` block and `lastEventName = "<name>";` as the first statement of all 134 event bodies, rejecting option O-1 (make the generator emit the name) on the grounds that it "would touch `rv-monitor` (radius M) and needs a release". Both halves of that reason are wrong on this tree. `rv-monitor` is the **first module of this very reactor** (`pom.xml`: `<module>rv-monitor</module>`, `br.unb.cic:rvsec-parent:0.9.3-SNAPSHOT`, same repository), built from source by `mvn install` at the root — there is no external artifact and no release to wait for. And this change **already edits `rv-monitor`**: task 5.2 changes `ViolationRecorder.makeRelevantList` in `rv-monitor-rt`. The radius was already entered.

**The researcher's freeze ruling (2026-08-17), which decides this.** The gh101 freeze is on the **specification sources**: `jca/*.mop` and `CipherTransformationUtil.java` byte-identical to `7e7acb69`, which is what the existing gate tests. It does **not** require that a given `.mop` keep generating a byte-identical monitor. Reproducing a published measurement is done by pinning the toolchain — the Docker image or a commit checkout — not by freezing the generator. So a generator change is not a freeze violation and NFR08 is satisfied by the pin, not by the generator standing still. Do not re-derive a stricter freeze from the gate's name.

**Decision: add a `__EVENTNAME` macro to `rv-monitor`, in the two substitution sites of the Java path.**

- In an **event body** (`BaseMonitor.java:350-368`, inside `printEventMethod`, which already holds the `EventDefinition`): expand to the string literal `"<event.getId()>"`. It costs nothing at runtime and needs no field — the name is known at generation time.
- In a **handler body** (`HandlerMethod.java:36-48`, which holds `prop` and the `Monitor`): expand to a lookup of the event name by the index the monitor already carries, shape-aware — `this.getLastEvent()` for the atomic shape, the `RVM_lastevent` field otherwise, reusing the branch at `BaseMonitor.java:1044-1048` and `MonitorTermination.java:73`. Out of range (`-1`, before any event) yields the sentinel `none`.
- The **name table** is emitted once per monitor class, in the `// state declaration` loop of `BaseMonitor.toString()` (`:806-812`) — where the `Prop_N_transition_*` arrays land today — iterating `this.events` (`BaseMonitor.java:122`, populated at `:179` from `rvmSpec.getEvents()`) in `getIdNum()` order. One table per class, not per property: `getIdNum()` is spec-wide, which is why `handleEvent(idnum, …)` and `MonitorTermination`'s switch already share it. Its name is reserved in `RVMNameSpace` beside `RVM_lastevent`.
- `RawMonitor.java:90-105` substitutes the same macros for the raw-monitor mode and gets the same treatment, so no path can leak the literal. A post-generation check fails closed if the string `__EVENTNAME` survives anywhere in the generated Java.

**Why this beats the 134 hand-written lines.** It is written once instead of once per specification set (`jca_android` now, `generic` later). It cannot produce a *wrong* name: the same loop over `this.events` emits both the table and the indices, so the two cannot desynchronise — whereas a hand-written `String[]` in `declarations` would be pinned to generator-assigned indices that any alphabet edit reorders, and a misindexed name is worse than `unknown` because it reads as a fact. It removes an invariant and its enforcement instead of adding them: INV-INS-120 stops being "every body carries a line the lint must police" and becomes a property of the generator, so E4 may add, rename and delete events with no bookkeeping obligation, and events with empty bodies need no body. `javamop` is untouched — `__EVENTNAME` inside a Java block is an identifier to its grammar, exactly as `__LOC` is today.

**Costs accepted.** The generator serves every set (191 `.mop` files), so the change must be additive and the other sets must still generate — checked by regenerating `jca` and the archived `jca_android_bug_predicate` and diffing against the frozen control (the only expected difference is the new table and the expanded macro). The reactor must be rebuilt and the `lib/` jars refreshed, which task 4.6 of the weaver group already does. And the group is new work in a module no other group owns, so it is dispatched in wave 1 and blocks the message group.

**Residues, still declared.** `KeyPairGeneratorSpec` (no `__RESET`) gains one, so the flags cannot survive into a second report with a stale name. The second residue the lineage declared — `KeyGeneratorSpec.g3` and `MessageDigestSpec.g4` testing the monitor field instead of the bound argument, so that two events might pass their guards on one call and let dispatch order decide which name the report carries — **does not exist**. Checked on 2026-08-18: `g1` and its sibling are emitted into the same wrapper with `g1` first (`results/gh101_group8_jca_frozen_control/monitors/mop/MonitorWrappers.java:192-193` and `:357-358`), both resolve the same object-indexed monitor, and `g1`'s body writes the field before the sibling's `condition` is evaluated. The field is initialised to `""` and never `null` (`MultiSpec_1RuntimeMonitor.java:4749,6362`), so the sibling fires exactly when `!contains(alg)` — the two guards are equivalent and the events are mutually exclusive by construction. What remains is a fragility, not a defect: the equivalence rests on declaration order, and a set that reordered the events would change behaviour. It is recorded, not repaired.

### D-6 — the weaver arity rule is a measurement, not a filter: the three clauses are evaluated and counted, no advice is excluded

**What was decided and what it replaces.** The lineage's D-C landed the arity rule as a filter: an advice whose positional `args()` arity is incompatible with the concrete call would be dropped from the merged wrapper. **Decision: implement the rule, evaluate it in the same place, and publish the count — but exclude nothing.** `WrapperEmitter.generate` returns an `EmitResult` carrying `advicesExcludedByArity`, and `BatchRunner.java:199-201` puts it in `counts` beside `wrappersGenerated`. The emitted wrappers are byte-identical to what the weaver emits today, and a parity test asserts exactly that.

**Why measurement and not filtering.** Excluding an advice changes which monitor calls fire, which changes which calls are accused, which changes what the published numbers mean — the same class of behavioural risk as the replay withdrawn in D-1, and this change has no before/after device evidence with which to take it. The number is unknown today: nobody has measured how many advices a merged wrapper fires in violation of positional arity across a real corpus, so the filter would be a blind edit to the instrument. The counter turns that unknown into a per-run figure in the results JSON, alongside the existing `wrappersGenerated`, and the decision to filter becomes a follow-up with data behind it. Note what this costs: the mute-report volume the filter would have removed stays in the corpus for now, and E1's legible envelopes will be attached to some reports that a later filter would delete.

**The mechanism the counter uses.** `WrapperEmitter.generate` groups by `registryKey(cc)` (`:133-136`, `declFqn#method(params)return`) at `:270-273`; `firstCallTarget` (`:507-525`) walks the AST for the first `CallPC` and ignores `ArgsPC`; overload expansion (`:326-403`) is driven by the `call()` param specs only. Nothing reads `args()`, so `TrustManagerFactory.getInstance(String)` fires `g1`, `g2`, `g3` (visible in `results/gh101_group8_jca_frozen_control/monitors/mop/MonitorWrappers.java:538-544`). The three clauses the counter applies (`_lacunas.md:674-684`) are: absent `args()` = no constraint, never counted; the arity is the length of `ArgsPC.types()`, not `names()` (`PointcutExpressionParser.java:243-246` drops the `..`, so `args(transformation, ..)` would otherwise look like fixed arity 1 — reuse `trailingRest`/`headCount` of `PointcutMatcher.java:280-288`); the evaluation happens inside the grouping loop, the only place where the advice and the concrete overload coexist. The lineage's *first* rule ("drop an advice whose `args` list has no trailing `..` and whose length ≠ `cc.paramFqns.size()`", `FINAL:434-438`) is the one to avoid even as a counter: it would have counted every `after` advice that has parameters and no `args()`. The lineage put that population at 16, of which 3 were said to be constructor advices outside the wrapper path. Recounted on the frozen descriptor (`results/gh101_group8_jca_frozen_control/monitors/MultiSpec_1MonitorAspect.json`, 115 advices) on 2026-08-18 the number is **25**, and **none of them is a constructor advice** — a constructor advice carries an empty parameter list, so it was never inside this recount at all. The correction strengthens the argument rather than weakening it: the rule the lineage wrote first would have silenced 25 advices, not 13. Two of the 25 belong to specifications the successor set does not carry (`RandomStringPasswordSpec_gb`, `SecretKeySpec_e1`, deleted under D-11), so a measurement taken on `jca_android` evaluates 23 of them and must say which set it was taken on. Among the remainder `SSLContextSpec_init` and `MessageDigestSpec_update` alone raise 2,629 of the 3,950 legible rows of the trial (66.6 %; 1,466 and 1,163). AspectJ enforces `args` arity itself, so the `ajc` variant needs nothing, and the counter is dexlib2-only. Denominators the lineage published for this (114 after-advices / 79 with `args()`) do not reproduce on the frozen descriptor (97 / 62).

**What the counter can and cannot see, enumerated.** `ArgsPC` is referenced only inside `pointcut-engine` (`ArgsPC`, `PointcutExpression`, `NegationPC`, `PointcutMatcher`, `PointcutExpressionParser`); the whole `advice-emitter` package — `BeforeEmitter`, `AfterEmitter`, `AfterReturningEmitter`, `AfterThrowingEmitter` and `WrapperEmitter` — never reads it. And `PointcutMatcher.matchArgs` short-circuits on the binding form (`if (!ap.hasTypeConstraint()) return Match.empty(ap)`), which is what `args(alg)` and `args(alg, *)` are, so nothing constrains them at match time either. Since the counter runs inside the wrapper grouping loop, and that loop admits only `shouldWrap(a)` = `"after".equals(position)` and skips constructors with an explicit `continue`, the 115 advices of the frozen descriptor split as: **48** `after` non-constructor with `args()` — the counter's whole domain; **44** without `args()` — 35 of them `after` advices, 25 of those 35 declaring parameters; they reach the loop but clause 1 never counts them; **9** `before` with `args()` — never reach the loop, invisible to the counter, already a written non-goal; and **14** `after`-on-constructor with `args()` — never reach the loop either: `DHGenParameterSpecSpec_c1`, `GCMParameterSpecSpec_c1_3`, `GCMParameterSpecSpec_c1_4`, `IvParameterSpecSpec_c1`, `IvParameterSpecSpec_c2`, `KeyPairSpec_c1`, `PBEKeySpecSpec_f1`, `PBEKeySpecSpec_f2`, `PBEKeySpecSpec_c1`, `PBEParameterSpecSpec_c1`, `PBEParameterSpecSpec_c2`, `SecretKeySpecSpec_c1`, `SecretKeySpecSpec_c2`, `SecureRandomSpec_c2`. Four of those fourteen (`IvParameterSpecSpec_c1/c2`, `PBEKeySpecSpec_f1/f2`) are precisely the four non-`@fail` three-argument report sites E1 makes legible, so the residue sits on top of sites this change touches: after E1 those reports name their event and value, and the counter will not even tell us whether an arity rule would have reached them. They are recorded as a non-goal with that consequence stated, not silently left out of the denominator. Reading `advicesExcludedByArity` therefore requires reading this paragraph: it is a count over 48 advices, not over 115.

### D-7 — gates: G-2 is wrong as written and takes the CrySL rule as input; G-ERE is added; G-2b is not adopted; the harness is the missing instrument

**The diagnostic error, and its correction.** The lineage measured 18 orphan events in 10 specifications of the frozen-control monitor — events with no transition row into `fail` from any state — and treated the 18 as 18 defects. Checked against the api30 rules on 2026-08-18, **17 of the 18 are the correct encoding of CrySL clauses that by definition do not belong to the `ORDER`**: `CONSTRAINTS`, `REQUIRES` and `FORBIDDEN` are pointwise predicates over one call, not sequencing constraints, so a specification that encodes them as events with a `condition()` and a report site — and no transition — is doing exactly what the rule says. Only **one** of the 18 is a real orphan: `MessageDigestSpec:74-76`, event `reset`, empty body, no clause behind it in the api30 rule. It is repair (3) of D-1. A second correction, measured on 2026-08-18, matters for what that repair costs: the lineage called `reset` dead, and it is the opposite. The discriminator that separates it from the 17 is not only the missing clause but the missing guard — an orphan with a `condition()` fires only when the condition holds, whereas `reset` has none, so the generator's row `{4,4,4,4,4}` (`MultiSpec_1RuntimeMonitor.java:6369`) against a `fail` of 4 (`:6504`) makes every woven `MessageDigest.reset()` an accusation, and the `__RESET` in the handler returns the monitor to state 0 so the following `digest()` accuses again. Exactly three orphans of the frozen set carry no `condition()`: `reset` and `PBEKeySpecSpec`'s `f1`/`f2`, and the latter two encode a `FORBIDDEN` clause and are meant to accuse on sight. Removing `reset` therefore removes accusations — the only repair of E4 that does — and its magnitude is not derivable from the published corpus, because `errors.csv` carries no event id and its `class`/`method` are the call site: the identifiable ceiling is the 100 rows over 7 call sites of `MessageDigestSpec` that raise `InvalidSequenceOfMethodCalls` and no `UnsafeAlgorithm` at all, inside a universe of 10,135. This is what the differential harness is for.

**Decision: G-2 takes the api30 rule as a second input.** A hit is an event that is orphan in the transition table **and** has no matching clause in `generated/api30/<Spec>.cryptsl`. On the frozen `jca` the gate therefore reports 18 orphans of which 1 is unmatched — the baseline the parametrised test pins, and the shape every extension is checked against. Keeping the old form would have made the gate demand that 17 correct encodings be rewritten, which is how a gate manufactures defects.

**Decision: add G-ERE — every symbol cited in the `ere` has an event declaration.** The name is mnemonic, not numbered: the gates outside the structural family are G-ERE (`ere` symbol declaration), G-CONF (allow-list conformance, INV-INS-127) and G-PRED (predicate absence, INV-INS-128), and a number would suggest an ordering none of them has. It is cheap, it is computed on the `.mop` source rather than the generated monitor, and it has no false positive: a symbol in the regular expression that no `event` declares cannot be anything but an error. On the frozen `jca` it reports exactly one hit, `GCMParameterSpecSpec` (`c2` referenced at `:48`, never declared — because `:33` misnames the event `c1`), which is the defect G-2 was mistakenly credited with catching. The `.mop` lint already computes this check; naming it as a gate is what gives it a baselined expected count next to the others.

**The rest of the family, measured on the frozen-control monitor.** G-2a 1 (`SecretKeySpec.e1` — a spec whose only event never changes state, i.e. a null detector; note that `SecretKeySpec.mop` is deleted from `jca_android` under D-11, so this hit has no successor); G-2b′ 8 (`CipherSpec.g3`, `KeyGeneratorSpec.g3`, `KeyManagerFactorySpec.g3`, `KeyPairGeneratorSpec.g3`, `KeyStoreSpec.g2`, `MacSpec.g3`, `MessageDigestSpec.g4`, `SecretKeySpec.e1`); G-2c 1; G-2d 2 (`SecretKeySpec`, `RandomStringPasswordSpec` have no `fail` category, so "sink = highest index" is not a violation state there — both specifications are deleted under D-11); G-6′ 1 (`GCMParameterSpecSpec`: two `Prop_1_event_c1` methods, one `c1` row). Each is a few lines over the same transition tables `gh101_monitor_transition_check.py` already parses (both monitor shapes, `:36-45`).

**G-2b stays unadopted.** The lineage's G-2b ("out-alphabet of unsafe ⊇ out-alphabet of safe") is not computable: minimisation merges the unsafe state into `start` precisely when the alphabets are equal (`δ(q0,g3)=q0` in `CipherSpec`, `KeyManagerFactorySpec`), and its implied repair — absorption — was rejected in gh101 D-S9 (two repair philosophies; FP traded for FN). Since G-2b′ flags idioms gh101 deliberately copied (`jca_android_bug_predicate/SSLContextSpec.mop:95-101` mirrors `KeyManagerFactorySpec.unsafeAlg`), the gates need an allowlist with reasons (`data/<set>/gate_allowlist.csv`) — a hit is a question, not automatically a defect.

**The harness.** What no static gate does is compare behaviour: gh100's merge turned 12 discarded wrappers into arity-incompatible advices firing (reported as success, `wrappersGenerated 96→84`); gh101's Group 3/3b turned 18 all-`fail` rows into accusations one call later. Hence the differential harness (INV-INS-124), on the JVM (`rvsec-mop/src/test`, created), with traces per spec; its self-test is `TrustManagerFactorySpec` between `jca` and the archived `jca_android_bug_predicate`, because that is the pair where the moved accusation is already known. It is also the instrument whose absence justifies withdrawing the replay (D-1) and the arity filter (D-6): both are behavioural, and this change builds the harness rather than spending it.

Format recognition of `jca` lines is by structure (comma count), so rewriting the messages does not break the parser; the `endswith("went into an error state.")` coupling (`:306`) is a `generic` concern.

### D-9 — E0 reuses `read_errors_csv` and copies the freeze-item and envelope disciplines; it does not live inside `aperv_tool.analysis`

### D-10 — the allow-lists are a literal transcription of the api30 `CONSTRAINTS`, under one declared normalisation rule and with one recorded divergence

**What was decided and what it replaces.** The lineage's D-B chose the oracle *per clause family*: MetaCrySL api30 for availability (Cipher catalogue, keystore types) and CrySL 1.5.2 for recommendation (digest algorithms, TLS protocols), recorded per specification. That rule is withdrawn. **Decision: every allow-list of `jca_android` is the `CONSTRAINTS` set of the matching `generated/api30/<Spec>.cryptsl`, transcribed literally.** One oracle, one anchor, no per-clause judgement call. The reason is that the mixed rule reintroduces the problem the set exists to solve: "recommendation" is exactly the label under which `TLS` and `AndroidKeyStore` were being rejected — a JSE-era preference presented to the developer as a platform fact. If the api30 rule admits a value, the set admits it; if the researcher believes the rule is wrong, the place to say so is the divergence record, not a second anchor.

**How far the current set is from that.** 74 constants were compared between the frozen `jca` `.mop` files and the api30 rules on 2026-08-18: 30 **declared by the rule and ignored by the `.mop`**, 14 identical, 13 **tested by the `.mop` with nothing behind them in the rule**, 7 where the `.mop` is more permissive, 7 divergent, 3 where the `.mop` is more restrictive. Two consequences follow directly from the transcription. `SecretKeySpecSpec`'s algorithm allow-list is in the third category — the rule declares nothing about `alg` — so **the list goes away**. And `SecureRandom`, `KeyManagerFactory` and `TrustManagerFactory` are cases where the api30 rule is the *more restrictive* one and is right: `Windows-PRNG`, `NativePRNG`, `PKCS11` and `SunX509` do not exist on Android.

**The normalisation rule, which the transcription cannot do without.** A literal transcription alone leaves roughly 3,000 of the measured events untouched, because the values the apps actually pass differ from the rule's spelling in case, in punctuation, or by being a Conscrypt alias:

- **`X509` (643 events, 3 apps, 5 misuses)** is not an algorithm at all: it is Conscrypt's alias for `PKIX` (`OpenSSLProvider.java:90`, beside the `PKIX` registration at `:89`; the `mapping_report.md` citation of `:101-107` is wrong — those lines are `AlgorithmParameters` DESEDE/TDEA — and this pointer replaces it). The api30 `TrustManagerFactory` rule declares `{PKIX}` and nothing else, so without an alias table the 643 stay accused after the transcription.
- **`SHA256WITHRSA` (4 events)** — api30 has `SHA256withRSA`; case only.
- **`OAEPWithSHA1AndMGF1Padding` (109 events, 1 app, 1 misuse)** — this one the normalisation rule does **not** close, and that is verified rather than assumed. The observed value is `RSA/ECB/OAEPWithSHA1AndMGF1Padding`, with no hyphen in `SHA1` (218 occurrences in the CSV = 109 events, counted once in `message` and once in `unique_msg`); api30 declares `OAEPwithSHA-1andMGF1Padding`, and Conscrypt registers `RSA/ECB/OAEPWithSHA-1AndMGF1Padding` (`OpenSSLProvider.java:338`) plus the alias `RSA/None/OAEPWithSHA-1AndMGF1Padding` (`:339-340`), all hyphenated — the unhyphenated spelling is registered nowhere in that file. Since `CipherSpec.g1` is an `after … returning(Cipher c)` advice, the 109 calls returned a `Cipher`, so some other platform provider accepts the spelling; the candidate is the Bouncy Castle build Android ships, which is outside this file. **Decision: no alias row.** There is no provider line to cite, and admitting a second class of authority would weaken the per-entry pointer requirement of INV-INS-127 for a single value. The case is entered in the divergence record with its evidence labelled **behavioural**, and naming the provider that resolves it is execution work.
- **`SHA1` / `SHA` / `SHA256`** (Conscrypt `OpenSSLProvider.java:115-116` for `SHA1`/`SHA` → `SHA-1` and `:124` for `SHA256` → `SHA-256`) fragment **2,340 events / 22 misuses** across three spellings of the same two digests. The `mapping_report.md` citation of `:131-132,140` is wrong — `:131-132` is `SHA-512`/`SHA512` and `:140` is `KeyGenerator.ARC4`, which is not an alias — and these pointers replace it.

The comparison the `.mop` files perform today is not uniform either: it is case-sensitive in six specifications (`Mac`, `Signature`, `SecureRandom`, `KeyGenerator`, `TrustManagerFactory`, `KeyManagerFactory`) and passes through `.toUpperCase()` in three (`MessageDigest`, `SSLContext`, `SecretKeySpec`). **Decision: comparison is case-insensitive everywhere in the set, plus an alias table derived from Conscrypt `android11-release` with one source pointer per entry, recorded per specification in `data/jca_android/alias_table.csv`.** 114 of the provider's registered aliases reach an entry of an api30 allow-list, and those are the relevant rows (the `Cipher.GCM` registration is not one of them: `GCM` occurs in the `Cipher` list as a mode of operation, and the alias points at a whole transformation). A transcription without this rule would be literally faithful and practically inert.

**Where the alias table lives and how it is read (decided 2026-08-18, closing the open question this design carried).** `alias_table.csv` is a **file of its own** under `data/jca_android/`, not a column of `conformance_record.csv`: the conformance record answers *which api30 rule a specification transcribes*, one row per specification, and folding 114 alias rows into 21 conformance rows makes both unreadable. Resolution happens **at runtime but not by reading the CSV**: a new utility class under `rvsec-core/.../jca/util/` carries the table **as code**, and each `jca_android` allow-list check **names that class in its call**. This is the same pattern D-b already fixes for the Cipher transformation tables, and it is what satisfies INV-INS-112 — the specification names the utility it calls, nothing selects between tables at runtime, no shared mutable key exists — while leaving the frozen `jca` untouched, since no `jca` specification names the class and therefore no `jca` verdict moves. A test asserts that the in-code table equals the CSV row for row, so the record and the instrument cannot drift.

**Why the aliases are not expanded into the allow-lists instead.** Three reasons, each sufficient. (a) The rule is not expansible: case-insensitive comparison cannot be written as a list, so an expanded allow-list would have to enumerate every spelling of every entry in every case. (b) An expanded list is no longer equal to the api30 clause, so G-CONF has nothing left to compare and the conformance argument — the whole reason the set has a single oracle — collapses. (c) It repeats precisely the defect this change removes: the frozen `jca` already resolves aliases by mixing them into the allow-list, which is why `KeyGeneratorSpec`, `MacSpec` and `SecretKeySpecSpec` carry `HMAC-SHA256`, `HMAC/SHA256` and `PBEWITHHMACSHA-256` as if they were algorithms the platform offers (they are Conscrypt aliases: `HMAC-SHA256`/`HMAC/SHA256` → `HmacSHA256` at `OpenSSLProvider.java:170-171`, `PBEWITHHMACSHA256` → `HmacSHA256` at `:481`), and why nobody can tell from the file which entries came from a rule and which from a provider registration.

**A limit of the table, declared.** Conscrypt is not the only provider on the platform: `AndroidKeyStore` comes from `AndroidKeyStoreProvider` and `BKS`/`BouncyCastle` from Bouncy Castle, and `OpenSSLProvider.java` registers **no** `KeyStore` alias at all. The `KeyStore` allow-list therefore has no alias coverage here, which is recorded as a limit of the table rather than as evidence that none is needed.

**Where the Cipher list lives (D-b).** It stays in Java and does not move into the `.mop`. Consequence: the set needs a **new class** under `rvsec-core/.../jca/util/`, because `CipherTransformationUtil` belongs to the frozen `jca` and `AndroidCipherTransformationUtil` belongs to the archived `jca_android_bug_predicate`, and neither may be edited. Its tables are transcribed from the `CONSTRAINTS` of `generated/api30/Cipher.cryptsl` — where the frozen utility admits two algorithm families (AES, RSA), the api30 rule admits eight. The allow-list conformance gate therefore reads that Java class for `CipherSpec` and the `.mop` files for every other specification.

**The divergence rule, generalised (2026-08-18).** The transcription meets the platform in two directions, and the rule is asymmetric on purpose.

*The api30 rule admits something the frozen `jca` rejected → the set admits it, and the detection is lost.* This is a researcher decision, recorded, not a pending item: the single oracle is what makes the verdicts checkable, and re-narrowing a list because the reviewer prefers a stricter one restores exactly the JSE-era preference-as-fact that produced the `TLS` and `AndroidKeyStore` reports. The largest instance is measured, not estimated. The api30 `MessageDigest` rule admits `MD5` and `SHA-1` and the api30 `Signature` rule admits `MD5withRSA` and `SHA1withRSA`; the published dataset carries **6,048** `MessageDigestSpec` / `UnsafeAlgorithm` rows, of which **3,552** are `MD5` and **2,340** are `SHA-1`, `SHA1` or `SHA` — **5,892 rows**, 97.4 % of that specification's reports and 6.1 % of the corpus's 97,018. Those stop being reported. The number goes into `conformance_record.csv` against `MessageDigestSpec` and `SignatureSpec` so that the silence is legible as a decision.

*The api30 rule omits something the platform demonstrably has → the list receives it, with a divergence entry citing the platform source.* Never the reverse: nothing the rule admits is removed, and nothing is added on preference. Two cases are proved and both are taken.

**Recorded divergence 1: `EC` in `KeyPairGenerator` (D-c).** The api30 `KeyPairGenerator` rule declares `{DSA, DH, RSA}`; `EC` appears only inside the implication `alg in {"EC"} => keySize in {256}`, which is a dead branch because the CONSTRAINTS are conjunctive and the algorithm list already rejects `EC`. This is a MetaCrySL modelling defect, and the evidence says so rather than inferring it: `samples/jca/android/11plus/KeyPairGenerator.ref:2` writes `define algorithm = {"EC"};`, the command that fills a `${algorithm}` hole, but `samples/jca/base/KeyPairGenerator.cryptsl:27` writes the list as a **literal** (`alg in {"DH","DSA","RSA"}`) instead of `alg in ${algorithm}` — so the `define` is discarded in silence. That this is an accident and not an intention is shown by the same `11plus` tier using the same idiom in `KeyGenerator.ref`, where it works, because `base/KeyGenerator.cryptsl:27` has the hole. Only three base specifications hard-code the literal (`KeyManagerFactory`, `KeyPairGenerator`, `TrustManagerFactory`) and only `KeyPairGenerator` has an Android `.ref` trying to extend it. **Decision: `jca_android`'s `KeyPairGenerator` allow-list includes `EC` (keySize 256), and the divergence record carries an entry naming the MetaCrySL defect and stating that the root fix is `alg in ${algorithm}` in the base specification — not performed here, because MetaCrySL is not edited by this change.** The justification is the change's own purpose: `EC` is the algorithm Android documents for `AndroidKeyStore`, so transcribing literally would fabricate exactly the class of spec-artefact this change exists to eliminate.

**Recorded divergence 2: the four ECDSA signature algorithms in `SignatureSpec`.** The api30 `Signature` rule names exactly one ECDSA algorithm, `SHA224withECDSA`, because the only MetaCrySL tier that touches ECDSA is `20plus` and it names that one; the others were never modelled. That `SHA1withECDSA`, `SHA256withECDSA`, `SHA384withECDSA` and `SHA512withECDSA` exist on API 30 is read off the platform rather than inferred: Conscrypt `android11-release` registers `Alg.Alias.Signature` entries whose targets are those names — `OpenSSLProvider.java:270` (`ECDSA`) and `:271` (`ECDSAwithSHA1`) point at `SHA1withECDSA`, `:286` (`SHA256/ECDSA`) at `SHA256withECDSA`, `:293` (`SHA384/ECDSA`) at `SHA384withECDSA`, `:300` (`SHA512/ECDSA`) at `SHA512withECDSA` — and a provider does not register an alias to a service it does not implement. **Decision: the four enter the `SignatureSpec` allow-list, one divergence entry each, citing the Conscrypt line and the modelling gap.** Without them `SHA256withECDSA` becomes a false positive; it is the practice Android documents for EC keys in the `AndroidKeyStore` — the same keys divergence 1 admits — and the frozen `jca` already accepted it, so a literal transcription would make the successor accuse where its own predecessor did not.

### D-11 — the successor set carries no predicates: `ExecutionContext` disappears from it entirely

**What was decided and what it replaces.** The lineage's D-11 was about *how* to report predicates under equality keying — add `RequiredPredicate`, move predicate reads out of `condition()` into event bodies, add missing producers or record them as unclosable. **That decision is withdrawn in full. Decision: `jca_android` contains no predicate machinery at all** — no `ExecutionContext.validate`, no `setProperty`, no `remove(Property)`, no `RequiredPredicate` error type, and no specification that exists only to write a predicate.

**The cost, measured on the frozen `jca`.** Twenty-four events touch a predicate. They split three ways:

- **13 use a predicate only as a guard** inside `condition()`. Removing those is a **gain**, not a loss: today the guard silences the specification whenever the predicate is absent, and the predicate is very often absent for reasons that have nothing to do with the app being correct.
- **11 accuse on the basis of a predicate**, and those accusations are lost: total loss at six sites (`IvParameterSpec c3/c4`, `PBEKeySpecSpec err2/err3`, `SecureRandomSpec setSeed3`, `GCMParameterSpecSpec:33`), partial loss at two (`PBEParameterSpecSpec c3` and `SecretKeySpecSpec c3`, where the allow-list half of the check survives), and three cross-specification key-provenance checks (`CipherSpec i2`, `MacSpec i1/i2`, all reading `GENERATED_KEY`).
- Nine `remove(Property)` sites disappear — against **two** `NEGATES` clauses in the whole of api30, which is the measure of how much of that machinery the rules actually ask for.

Two specifications are pure propagators — they write a predicate and accuse nothing — so they cease to exist: `RandomStringPassword.mop` and `SecretKeySpec.mop`. The set is born with **21 specifications**.

**Why the three provenance losses are cheaper than they look.** The `ase-journal` analysis records that keys obtained from `AndroidKeyStore`, from Tink or through `KeyGenParameterSpec` never carry `GENERATED_KEY` — 11,620 events / 80 misuses / 25 apps. On Android those three checks were already inoperative; removing them costs detections that were not happening.

**Why not repair the predicate graph instead.** Because it has been tried, at scale, and the result is on record. gh101 spent **42 hunks** on the predicate graph, and the 2026-08-08 audit's gate G7 still fails **19 of 22** specifications, with roughly five live clean edges in the whole set. Two of the three defects the audit attributes to gh101 are predicate edits (`GENCIPHER-EXTRA`, the `GENERATED_CIPHER` reads added to `CipherInputStreamSpec`/`CipherOutputStreamSpec`; `SSL-RANDOMIZED-EXTRA`, the `RANDOMIZED` read added to `SSLContextSpec.init`). A cross-specification dataflow abstraction implemented as a shared mutable map, keyed by object equality, over a monitor set that observes only the calls the weaver instrumented, is a construct whose failure mode is silent: a missing producer turns an accusation off and nothing reports that it did. Removing it makes the set smaller, its verdicts local, and its gates decidable.

**What is recorded instead of repaired.** `data/jca_android/predicate_removal.csv` carries one row per removed site: the file and line, its class (guard / total loss / partial loss / provenance), and the accusation it used to raise. That record — not a repair task — is what a future change reads if the predicate question is reopened. The `ExecutionContext` keying ruling (equality, `e204e2a4`) is noted in `data/jca_android/README.md` as moot for this set, since the set references `ExecutionContext` at no site. A grep gate enforces the absence.

### D-12 — process: one `tasks.md`, per-group execution files, six parallel first-wave subagents

`openspec/schemas/rv-sdd/schema.yaml:162-164` tracks `tasks.md` and only `- [ ]` lines (`:120,:124`); `docs/WORKFLOW.md:443` needs the checkbox ticked immediately after each task for resume; `:1049-1060` detects the artifact by `tasks.md` existing. **Decision: `tasks.md` holds every checkbox and the dispatch hints (HTML comment at the top, `schema.yaml:151-152`, template `tasks.md:1-6`); each group heading points to `tasks/<GROUP>.md`, which holds the file inventory, per-site table, commands, expected values and the subagent brief. A subagent reads only its group file; the orchestrator reads only `tasks.md`.** This is additive — the schema forbids nothing in the change directory — and keeps subagent context small (3–15 files each, `WORKFLOW.md:331`).

Groups by independence and locality. **Wave 1, six disjoint file sets, six subagents:** E0 (docs + scripts) ∥ S (rv-experiment, the rename of the derived set to `jca_android_bug_predicate/`, and the new `jca_android/` directory) ∥ G (`rv-monitor/rv-monitor`, the generator) ∥ E2 (Java dexlib2) ∥ E3 (collectors + Python consumers, including `rv-monitor/rv-monitor-rt`, a different submodule from G) ∥ EV (new test and script files). **Then:** E1 (messages) after S and G, two subagents on disjoint file halves; E4 after EV and E1, per file with one owner at a time; E6 (identity) after E3 and E1, may overlap E4; integration last.

Two group sizes changed with the pivot and are stated so the dispatch is not read from the old plan. **E2 is smaller**: it implements and plumbs a counter, with a parity assertion that the emitted wrappers do not change (D-6) — no behavioural edit, no re-weave decision. **E4 is the set-content group and carries seven repair items** — the seven structural repairs enumerated in D-1 — plus the api30 allow-list transcription of D-10 (the `.mop` allow-lists, the new Cipher utility class, `alias_table.csv` and `conformance_record.csv`) and the predicate removal of D-11 (deletions in every touched file, two file deletions, `predicate_removal.csv`). **The predicate group is gone**: `tasks/E5-predicates.md` is deleted, because there is nothing left to repair once the machinery is removed rather than fixed.

Critical path: S → G → E1 → E4 → integration. E0, E2, E3, EV and E6 are off it. gh100 7.5/7.6 are closed (2026-08-16), so E2 has no process dependency left.

### D-13 — `ErrorType` gains `ForbiddenMethod`, and the mislabelled sites are corrected with it

An `ErrorType` is not a taxonomy for the report writer; it is the first thing the developer reads and it tells them where to look. Today `PBEKeySpecSpec.mop:24,30` report `InvalidSequenceOfMethodCalls` for a **forbidden constructor** — a developer reading that goes looking for a call they forgot to make, when the truth is that the call they *did* make must not exist at all. CrySL says this in its own vocabulary: `FORBIDDEN` is a clause of its own, and it is not a predicate — which matters here, because D-11 removes the predicates and this type survives that removal untouched.

**Decision: add `ForbiddenMethod` to `rvsec-core`'s `ErrorType`. Do not add `RequiredPredicate`** — the lineage planned both, but with D-11 no site of `jca_android` can raise one, and an error type no specification emits is dead vocabulary that the next reader will assume is live.

The same edit corrects the `ErrorType`s the census already catalogued as wrong:

| site | today | correct | why |
|---|---|---|---|
| `PBEKeySpecSpec.mop:24` | `InvalidSequenceOfMethodCalls` | `ForbiddenMethod` | CrySL `FORBIDDEN` constructor; nothing about ordering is wrong |
| `PBEKeySpecSpec.mop:30` | `InvalidSequenceOfMethodCalls` | `ForbiddenMethod` | idem |
| `PBEParameterSpecSpec.mop:49` | `UnsafeAlgorithm` | `UnsatisfiedConstraint` | the condition tests an iteration count, not an algorithm |

This supersedes the earlier plan for `PBEKeySpecSpec:24,30`, which mapped them to `UnsatisfiedConstraint`; that is closer than the current value but still wrong, because it sends the developer to check an argument when the constructor itself is the finding. `codes.csv` keeps the KIND `FORB` for these two sites; the `REQ` kind is dropped from the vocabulary (D-3). The message-property gate checks the type against the site kind (INV-INS-121), so a future edit cannot silently reintroduce the mismatch.

### D-14 — the generated dispatcher releases its lock on every exit

**The measurement.** The generated monitor serialises every event through one global lock. Each of the 134 dispatchers opens with `while (!MultiSpec_1_RVMLock.tryLock()) { Thread.yield(); }` and closes with `MultiSpec_1_RVMLock.unlock()`, and the file contains **zero** `finally` blocks — 134 acquisitions, 134 releases, none of them protected (`results/gh101_group8_jca_frozen_control/monitors/MultiSpec_1RuntimeMonitor.java:9005` declares the single `ReentrantLock`; measured 2026-08-18). The consequence is not a slow path or a lost report. An exception raised anywhere between acquisition and release — in a `condition()`, in an event body, in a `@fail` handler — leaves the lock held by a thread that has already unwound past it, and since every other dispatcher of every other specification spins on `tryLock()` inside a `Thread.yield()` loop rather than blocking, the monitored application does not deadlock quietly: it burns CPU forever on the next monitored call, with no exception surfacing and no record written. One instrumented app in that state produces a run that looks like a timeout.

**The path is reachable in the frozen set.** `KeyPairGeneratorSpec.mop:29` switches on `algorithm`, a field written only by the `getInstance` events; `KeyPairGenerator.getInstance(String, Provider)` carries no pointcut (`MultiSpec_1MonitorAspect.aj:357,365` bind only the one- and two-argument overloads), so a generator obtained through that overload arrives at `initialize(int)` with the field still `null` and `switch(null)` raises `NullPointerException` inside the guarded region. Repair (4) of D-1 closes that particular door; it does not close the class, because any future `condition()` or handler can raise.

**Decision: the generator emits the guarded region so the lock is released on every exit.** This is a generator repair, not a specification repair, so it lands in the `__EVENTNAME` group (G) where `rv-monitor` is already open and no other group owns the module — not in E4, which touches `.mop` files only. It is behaviour-preserving on every path that does not throw, which is what makes it checkable: regenerating the frozen `jca` and the archived `jca_android_bug_predicate` must diff against the frozen control in the framing, the event-name table and the expanded macro, and in nothing else.

**Why it is inside this change rather than an issue of its own.** The researcher decided it on 2026-08-18. The argument that carried it is that this change already reopens the generator, already rebuilds the reactor and refreshes `lib/`, and already regenerates and diffs both sets — so the marginal cost is the emitter edit and one test, while the marginal cost of deferring is that every device-side task of this change, E6 included, runs on an instrument that can hang without saying so. The invariant is INV-INS-129, and the scope is exactly the dispatcher framing: no change to which advice fires, to the lock's identity, or to the spin loop.

## API Design

### `WrapperEmitter.generate(descriptor, monitorDir[, index]) -> EmitResult`
`EmitResult { List<WrapperEntry> wrappers; int advicesExcludedByArity; }`. Precondition: descriptor parsed. Postcondition: **`wrappers` is exactly what the emitter produced before this change** — no advice is excluded — and `advicesExcludedByArity` is the number of admitted advices whose positional `args()` arity is incompatible with the concrete call under the three clauses of D-6 (advices with no `args()` clause are never counted). `BatchRunner` writes `counts["advicesExcludedByArity"]`. The name says "excluded" because it counts what a filter would exclude; the filter is a follow-up, not this change.

### `ErrorCollector.addError(ErrorDescription err)` (logcat)
Emits one line `summary + "," + escape(expecting)`; `expecting == null` → sentinel envelope; `escape`: `\n`→`\\n`. Never throws for a `null` message.

### `_parse_error_message(message: str) -> RvErrorLog | None` and `LogcatRepository.parser_diagnostics: ParserDiagnostics`
`RvErrorLog` gains `code, event, obj, val, exp, msg: str | None`, `truncated: bool`; every `None` return increments exactly one counter; `parse_logcat_file` re-raises after logging the line number.

### `RvErrorLog.unique_msg -> str`
`f"{class_full_name}:::{method}:::{spec}:::{error_type}:::{code or 'UNSPECIFIED'}:::{event or 'UNSPECIFIED'}:::{message}"` — the only constructor.

### `violations.read_errors_csv(path) -> (rows, CsvDiagnostics)`; `parse_payload(payload) -> ViolationEvent`
13-column header or `ValueError`; seven `:::` parts or `unique_msg_unparsed += 1`; envelope keys parsed; unclosed quote → `shape_ok=False`, `envelope_truncated += 1`.

### `gh104_gates.py run(monitor_java: Path, mop_dir: Path, crysl_dir: Path, allowlist: Path) -> GateReport`; `gh104_diff_harness.py run(set_a: Path, set_b: Path, traces: Path, out: Path)`
`crysl_dir` is `generated/api30/`, read-only: G-2 needs it to tell a correct `CONSTRAINTS`/`REQUIRES`/`FORBIDDEN` encoding from a real orphan, and the allow-list conformance gate needs it to compare transcriptions. `mop_dir` is what G-ERE and the lint read. Both entry points need `RVSEC_HOME`; generation happens in a scratch dir off tmpfs; the harness returns per-trace verdicts (`accused`, `event`, `envelope`) for both snapshots and a `moved`/`removed`/`unchanged` classification.

## Data Flow

## Risks / Trade-offs

- [E1 and E4 edit the same `.mop` files] → per-file ownership, never per-change parallelism; the message-property gate holds the `codes.csv` bijection and the message-vs-allow-list agreement across E4's transcription.
- [The generator serves all 191 `.mop` files, not only `jca_android`] → group G is additive (a new macro and a new table; no existing emission changes), and its acceptance regenerates `jca` and the archived `jca_android_bug_predicate` and diffs against the frozen control, where the only admissible differences are the new table and the expanded macro. The 11 `generic` files that do not compile today stay broken for their own reason and are not a regression signal.
- [Group G blocks E1, and no other group owns `rv-monitor/rv-monitor`] → G is dispatched in wave 1 alongside E0/S/E2/E3/EV; it is small (two substitution sites, one table, one reserved name) and its own tests do not need a device or a full campaign.
- [`CipherSpec` sits at the generator ceiling with 17 events and no re-budget in this change] → every `CipherSpec` task declares its event count after the edit; adding an event requires removing one, and the transcription of the api30 Cipher catalogue lands in the new Java utility class, not as new events.
- [The transcription silences accusations the published analysis counted] → that is the point, and it is exactly why it must be measured: the harness runs before/after on every touched file, and the conformance record names, per specification, which api30 clause each allow-list came from. The 11,409 events / 84 misuses that stop being reported are a declared consequence, not a regression, and so are the 5,892 `MessageDigestSpec` rows the api30 rule's admission of `MD5` and `SHA-1` silences (D-10), and any report comparing counts across `jca`, the archived `jca_android_bug_predicate` and `jca_android` carries that caveat.
- [Literal transcription without normalisation would be inert] → the alias table and the case-insensitive comparison are part of the same tasks as the transcription, not a follow-up; G-CONF fails an alias row with no source pointer. Normalisation is **not** implemented by expanding the allow-lists — that would make the lists unequal to the api30 clauses and leave G-CONF nothing to compare — but by a new utility class in `rvsec-core` that each `jca_android` check names (D-10). It is new shared code, so INV-INS-112 applies and is satisfied the same way the Cipher tables are: no `jca` specification names the class, so the frozen set cannot observe it, and nothing selects between tables at runtime.
- [Removing the predicates removes 11 accusations] → 6 total, 2 partial, 3 provenance; the three provenance checks are already inoperative on Android (`GENERATED_KEY` never set for `AndroidKeyStore`/Tink/`KeyGenParameterSpec` keys, 11,620 events / 80 misuses / 25 apps), and every removed site is recorded in `predicate_removal.csv` with the accusation it used to raise, so reopening the question later does not require re-deriving the inventory.
- [Not replaying gh101's 94 hunks leaves known automaton defects in the successor set] → accepted and bounded: the six structural repairs of D-1 are the subset confirmed against the api30 rules, and the harness plus the CrySL-aware G-2 are what a follow-up would use to take the rest with evidence. The alternative — replaying repairs whose set was judged 22/22 REPROVADA — imports defects the gates cannot attribute.
- [Not filtering by arity leaves the merged wrappers firing incompatible advices] → accepted, and now visible: `advicesExcludedByArity` is published per run, over a domain of 48 advices that D-6 states explicitly so the number is not read as a fraction of 115.
- [G-2b′ flags deliberate idioms] → allowlist with reasons; a hit is a question. The Form-B residue (13 specifications per `frozen_set_debt.md:246`; its own enumeration yields 14–15 — the count is not authoritative) stays recorded, not gated.
- [The identity change creates two eras of every dedupe number] → declared, measured (must be non-zero), E6 last and device-side; reports carry the era.
- [Consumers regexing free text break] → consumer matrix names each; the article scripts are declared frozen (they read the published dataset, which does not change).
- [Two monitor shapes carry the last event differently — `pairValue`/`getLastEvent()` in 15 classes, the `RVM_lastevent` field in 8] → the handler expansion reuses the branch the generator already has (`BaseMonitor.java:1044-1048`, `MonitorTermination.java:73`); a unit test covers one specification of each shape, and the fail-closed check catches any path that leaks an unexpanded `__EVENTNAME`.
- [The `KeyManagerFactorySpec` 296 rows have two candidate causes the record cannot separate] → E1's `ev=` is what separates them; the harness reads it; no gain is credited to E2 for those rows.
- [Device validation] → one task, four APKs from the published campaign (`com.owncloud.android_48000100`, `eu.opencloud.android_9`, `de.luhmer.owncloudnewsreader_196`, `com.etesync.syncadapter_20700` — the ones gh101 task 8.1 used), via `rv-experiment run`, never by hand; the change is complete without it being green, but not without it being run and its result recorded.
- [gh56-smoke monitors predate the freeze] → oracles are always `results/gh101_group8_jca_frozen_control/monitors/` (transition tables identical to gh56-smoke; `KeyManagerFactorySpec.init` guard polarity differs there).
