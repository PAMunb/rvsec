## Context

GitHub Issue: #104. Proposal: `proposal.md`. This design is written so that someone with none of the session's context can execute the tasks months later; every number in it was measured against the artefact it names — the report-path numbers on 2026-08-16, the CrySL-conformance and pivot numbers on 2026-08-18 — and every claim carries the file and line it was read from. Historical analysis lives in `docs/20260816_javamop_mensagens_verificacao.md` (the adversarial verification of the 2026-08-15 lineage), `docs/20260815_javamop_mensagens_FINAL.md` (the design document it corrects), `data/gh101/frozen_set_debt.md`, `openspec/changes/archive/2026-08-16-gh101-jca-spec-conformance/design.md` (D-S0..D-S14, notably D-S9 and D-S10) and `openspec/changes/gh100-weaver-emission-fidelity/design.md` (D-B1). Those documents are not to be edited; they are the record of what was found when it was found.

**The problem, measured.** Published dataset `ase-journal/dataset/results/errors.csv` (10 columns, no `source`): 97,018 rows, 19 distinct messages, 70,760 `unknown` = 72.93 %; 8,843 rows end in `but found .` (TrustManagerFactorySpec 8,371, SignatureSpec 234, MessageDigestSpec 156, SSLContextSpec 51, MacSpec 31). Study-03 trial `experimento-comp162/results/*/*/errors.csv` (8 disjoint shards — 112 distinct APKs, 3 tools × 3 repetitions each, not 8 replicas; 11 columns): 19,664 rows, 15,714 `unknown` = 79.91 %, 296 mute sites of which 101 also emit legible rows (3,950 rows) and 12 emit two error types in lockstep (838 rows, all `IvParameterSpecSpec`); per-spec mute volume SSLContext 2,916 · SecureRandom 2,882 · TMF 2,855 · MessageDigest 2,008 · Cipher 1,461 · KeyStore 1,136. Third-party attribution reproduces at 85.44 % (82,890 rows) only under nine prefixes: `okhttp3.`, `com.google.`, `kotlin.`, `io.ktor.`, `org.bouncycastle.`, `androidx.`, `org.conscrypt.`, `okio.`, `org.spongycastle.` (seven vendors give 78.49 %, +`okio.` 82.67 %).

**The second problem, measured on the same corpus: the set says the wrong thing about Android.** The tier of the published analysis that has primary-source evidence — `ase-journal`, `docs/20260806_owasp_cwe_mapping_report.md` — is **11,409 events / 84 misuses (18.5 % of 454)**, and every one of them is an allow-list verdict the frozen `jca` reaches because its allow-lists were written for the JSE JCA, not for the platform the APKs run on:

The declared context of the measurement is **API 30 / Android 11**, Conscrypt branch `android11-release` (`dataset.tex:5`; `mapping_report.md:622-648`). On that platform `AndroidKeyStore` is the keystore type Google documents, `TLS` is the protocol name `SSLContext.getInstance` takes, and `X509` is Conscrypt's own alias for `PKIX`. A legible message that says `AndroidKeyStore is not a safe keystore type` is a *worse* artefact than `unknown`, because it is a false accusation stated with authority. This is why the change's target set is Android-targeted from its first commit and not a general-purpose successor.

**The mechanism.** `ErrorDescription.java:34-36` (rvsec-core): the three-argument constructor delegates with the literal `"unknown"`; `toString()` (`:143`) renders `[%s] %s at %s expecting %s`. The logcat `ErrorCollector.java:36-42` emits `getErrorSummary() + "," + getExpecting().trim()` after `errors.add(err)` on a `HashSet` whose identity is `ErrorSummary` (`:73-120`: spec, error, classQualifiedName, methodName, location); the escaping method `escapeSpecialCharacters` at `:44-51` is dead code (its call is commented at `:39`). In the frozen `jca` (23 files, 1,912 lines, 134 events): 51 `new ErrorDescription(` = 25 three-argument (21 `@fail` + `IvParameterSpec.mop:48,55` + `PBEKeySpecSpec.mop:24,30`) + 26 four-argument (one commented, `MessageDigestSpec.mop:57-58`); 18 grep hits for `but found` = 16 active field-interpolating sites + `SecureRandomSpec.mop:82` (argument) + the commented `MessageDigestSpec.mop:58` (argument); 21 files with exactly one `@fail`, `RandomStringPassword.mop` and `SecretKeySpec.mop` with none; only `KeyPairGeneratorSpec.mop:110-113` lacks `__RESET`. The generated event method emits the `condition()` guard **before** the `.mop` body (`if ( ! (cond) ) { return false; }`, verified on `KeyManagerFactorySpec.Prop_1_event_g3`), and the body before the transition, so an event that fails its guard neither runs its body nor transitions and cannot be the event that reaches `fail`.

**What the generated monitor already knows.** The monitor tracks the last event itself, in two shapes that coexist in one generated file — 15 classes of the atomic/table shape (`extends AbstractAtomicMonitor`; the event index is packed into `pairValue` as `((lastEvent + 1) << numStateBits) | state` and read back by `getLastEvent()` — which returns the packed `lastEvent + 1`, not `lastEvent`; D-4 decodes it) and 8 of the non-atomic shape (a plain `RVM_lastevent` field, assigned inline in the event method — `BaseMonitor.java:425-428` — and **inherited**, together with a `public final int getLastEvent()` accessor, from the runtime's `AbstractSynchronizedMonitor.java:5,21`; the generator declares neither). So `this.getLastEvent()` resolves in **both** shapes — generated in the atomic one, inherited in the other — and is declared on `IMonitor.java:19`; the raw field `RVM_lastevent`, by contrast, exists only in the non-atomic shape. The generator branches between the shapes where it emits the *termination* code (`BaseMonitor.java:114-118` `isAtomicMoniorUsed()`, `:1044-1048`, default `"RVM_lastevent"` at `MonitorTermination.java:73`), but note when that branch is decidable: `isAtomicMoniorUsed()` throws `IllegalStateException` until `checkIfAtomicMonitorCanBeEnabled()` has run (`:115`, `:145`), which happens at the top of `toString()` (`:665`) — **after** the `HandlerMethod` objects are constructed in `initialize` (`:226`). It also holds the event **names**: `MonitorTermination.java:131-133` iterates `this.events` and writes `"case " + event.getIdNum()` followed by `"//" + event.getId()` — index and name, paired, emitted as a comment. The `@fail` body is inlined into `Prop_N_handler_fail()`, a method of that same monitor class, and `__RESET` (`this.reset()`, which zeroes the last event) is substituted *after* the `addError` call, so at report time the offending event is still there. What is missing at runtime is only the index→name table.

**How the `.mop` macros are expanded.** `__RESET`, `__LOC`, `__DEFAULT_MESSAGE`, `__SKIP` and `__ACTIVITY` are plain `replaceAll` on the body text, at three sites of the Java path: `BaseMonitor.java:350-368` (event bodies), `HandlerMethod.java:36-48` (handler bodies, `@fail` among them) and `RawMonitor.java:90-105` (raw-monitor mode). `SuffixMonitor` does not substitute (only a commented `has__LOC` at `:245`); `logicpluginshells/fsm/CFSM.java` and `tfsm/CTFSM.java` are the **C** output (they import `rvmonitor.c.rvc.CSpecification`) and are off this path. `javamop` does not participate: it carries the Java block from `.mop` to `.rvm` verbatim, which is why `__LOC` traverses it today without javamop knowing what it is.

**The oracle, and what it is not.** The MetaCrySL rules already generated under `generated/api30/` are the oracle of this change. They were produced with Java 8 and `rascal-0.19.6.jar` from the MetaCrySL root, config `samples/jca/android/config/Android30.config`; the API level is a directory convention plus the tier list inside the `.config`, and refinement can only ADD (there is no `remove` command). That generation is recorded here for reproducibility only: **MetaCrySL is not edited by this change**, not even where D-10 names a modelling defect in it.

**Constraints inherited.** `jca` frozen at `7e7acb69` (gh101 D-S0; gate `tests/parity/test_gh101_specset_gates.py`, 5 tests, green). The derived Android set of gh101 is NOT READY (audit `audit/20260808_validacao_jca_android/global/juizglobal_relatorio.md:616-619`, 22/22 REPROVADA — 22 of the 23 files were in the audit's scope, the 23rd being the `@fail`-less propagator `RandomStringPassword`; G11 records three defects introduced by gh101: `GENCIPHER-EXTRA` task 5.1, `SSL-RANDOMIZED-EXTRA` task 3.2, `KPG initError` placement); its directory is archived as `jca_android_bug_predicate` and the name `jca_android` is rebound to the successor set. `ExecutionContext` is equality-keyed at HEAD (`e204e2a4`, 2026-08-11, reverted gh101 D-S10; gh101's `data/gh101/README.md:308-317` and tasks 4b.1-4b.4 still describe identity keying — stale, noted here, not rewritten); under D-11 as revised the successor set carries the seed's `ExecutionContext` sites unchanged, so the keying question reaches it exactly as it reaches the frozen `jca` — and is not re-opened here. Generator ceiling: `n × (2ⁿ − 1)` coenable sets; 17 events generate in 53 s / 3.3 GB, 18 raise `StackOverflowError` in `EnableSet.parseSets` (`data/gh101/README.md:546-553`, INV-INS-115); `jca/CipherSpec.mop` has 17 events. gh100's `INV-INS-109/110` were renumbered to 116/117 on 2026-08-16 (`ceb03a9e`) so that the ids cited here carry the gh101 meaning; this change's new invariants run INV-INS-118 to INV-INS-129. No emulator is ever run by hand; anything device-side is a task that calls `rv-experiment run`.

**Researcher decisions this design encodes (the report-path decisions taken 2026-08-15/16, the set-content decisions taken 2026-08-18; neither is re-opened here).** The report path: `st=` is out of the envelope; `ev` enters the dedupe identity (E6 exists); the event name comes from the generator, not from 134 hand-written lines; `generic`/`generic_new` are a written non-goal. The set content, decided 2026-08-18 after the CrySL conformance census: the successor set is **`jca_android`**, a new directory seeded byte-for-byte from the frozen `jca` and targeted at Android API 30. The name is **rebound, not added**: the directory that held gh101's derived set is renamed to `jca_android_bug_predicate` and stops being selectable, so the enumeration of specification sets keeps its four values (`jca`, `jca_android`, `generic`, `custom`) and the successor is reached by the name the derived set used to answer to. Its allow-lists are the literal `CONSTRAINTS` of the api30 rules under a declared normalisation; it carries **the seed's predicates unchanged**; the weaver arity work lands as a **counter, not a filter**; the behavioural replay of gh101's 94 non-allow-list hunks does not land in this change.

## Goals / Non-Goals

**Goals:** every report from `jca_android` names its event and its observed/expected values in a machine-readable envelope; no report says `unknown` or `but found .`; every allow-list of the set is a literal transcription of the `CONSTRAINTS` of the matching api30 rule under one declared normalisation rule, so that the set stops accusing `AndroidKeyStore`, `TLS` and `X509`; the transport counts every discard; the weaver publishes how many advices its merged wrappers fire in violation of positional arity; the gates run as pytest for any set and take the CrySL rule as input where the verdict depends on it; the harness makes moved defects visible; per-event attribution reaches `errors.csv` and the dedupe identity, with the discontinuity declared; the frozen `jca` keeps reproducing.

**Non-Goals, each with the reason it is one:**

- **Repairing the predicate graph.** The successor set carries the seed's predicate machinery unchanged — every `REQUIRES` clause, `ExecutionContext` call and accepting-state site — and repairs none of it. The reason is measured in D-11: gh101 spent 42 hunks on that graph and the audit's G7 still fails 19 of 22 specifications with roughly five live clean edges, and two of the three defects gh101 introduced were predicate edits. Removing the graph instead was considered and withdrawn in the same decision: it is the largest behavioural change the set could take, deleting detection at 11 of 21 predicate-reading events, and this change has no evidence to spend on it. Correct wiring is a change of its own, whose prerequisite is the differential harness built here.
- **Filtering advices by `args()` arity.** The three-clause rule is implemented and evaluated, but no advice is excluded from a merged wrapper; only the count is published (D-6). Changing which advices fire changes which calls are accused — the same class of behavioural risk as the replay below — and this change does not have the before/after device evidence to take it. The counter is what buys that evidence.
- **The behavioural replay of gh101's 94 non-allow-list hunks.** The lineage's D-A(ii) planned to replay them into the successor set. It does not land here (D-1): those repairs are exactly the body of work the 2026-08-08 audit judged 22/22 REPROVADA, three of them are defects gh101 itself introduced, and none of them is on the path to the 11,409 events / 84 misuses the Android allow-lists resolve. The change's own harness and the arity counter are the instruments that would justify reopening it later. Three of E4's six structural repairs — 8.1 (`c1`→`c2` in `GCMParameterSpecSpec`), 8.3 (the `reset` event of `MessageDigestSpec`) and 8.5 (the `sign()` return types of `SignatureSpec`) — coincide with hunks gh101's divergence record also carries; they land not because gh101 made them but because each is justified here on its own evidence — the api30 rule, the `android-30` `javap` signature or the frozen-control monitor (D-1) — and each carries mandatory harness evidence (task 8.9). Coincidence with a gh101 hunk is not the replay.
- **MetaCrySL.** The `.cryptsl` sources and the Rascal generator are read, never edited — including at `samples/jca/base/KeyPairGenerator.cryptsl:27`, where D-10 names a modelling defect and prescribes the root fix without performing it.
- **The archived derived set (`jca_android_bug_predicate`).** Not repaired, not extended, not used as the seed, and not selectable; it is renamed and left in the tree so the 2026-08-08 audit keeps its subject.
- **`jca`.** Not unfrozen. The freeze is on the specification sources, not on the generated monitor (D-4).
- **The `generic` and `generic_new` sets** (145 files, `Log.v` path, never ran; 11 `generic` files do not compile — duplicated parameter names — and `FSM358.mop:4,6` has an import collision; recorded as debt, see plan `docs/20260815_javamop_mensagens.md:805-817` WS-8).

- **The binding-form arity check in `PointcutMatcher`** (`:268-306`), which leaves both the 9 `before` advices with `args()` and the 14 `after`-on-constructor advices with `args()` outside even the counter's reach — enumerated in D-6, with the consequence that two of them (`PBEKeySpecSpec_f1/f2`) raise report sites E1 makes legible.

## Decisions

### D-1 — the successor set is `jca_android`: a new directory, seeded byte-for-byte from the frozen `jca`, targeted at Android API 30

**What was decided and what it replaces.** The lineage's D-A(ii) fixed the lineage of the successor set (`jca` as seed, not the derived Android set) and then added a second clause: E4 would *replay* the 94 non-allow-list hunks that `data/gh101/divergence_record.csv` records between the derived set — archived here as `jca_android_bug_predicate` — and `jca` (106 hunks total: 51 `layer-2-repair`, 42 `predicate-graph`, 1 `cipher-import`, 12 `allow-list`). **The seed clause stands; the replay clause is withdrawn.** The set is named `jca_android`, it is a new directory under `rvsec-mop/src/main/resources/`, it is byte-identical to `jca` at its seed commit, and its declared target is Android API 30 / Android 11 — the platform of the published measurement (`dataset.tex:5`).

**How the name is freed.** The name `jca_android` already belonged to gh101's derived set. Rather than invent a third name and leave three JCA sets on offer, the derived set's directory is renamed to `rvsec-mop/src/main/resources/jca_android_bug_predicate/` and removed from every enumeration, and the successor takes the vacated name. So the `click.Choice` and `valid_spec_sets` keep four values — nothing is appended — and what changes is which directory the second of them resolves to. The archived set is preserved, not deleted: it is the artefact the 2026-08-08 audit assessed, and a reader of that audit needs it to be able to look. It is not selectable, because a set that must not be run in a new campaign should have no value a reader can mistake for an offer; reproducing the audit is done by pointing `RVSEC_HOME` at the commit it was run against. The name states the reason it was set aside — the predicate regime whose defects the audit measured, exactly what D-11 removes rather than repairs — so the reason survives without the change history.

**Why the seed is `jca`, not the derived set.** The derived set is the one that already carries an Android derivation, so it is the obvious seed and it is the wrong one: the 2026-08-08 audit judged it 22/22 REPROVADA (`audit/20260808_validacao_jca_android/global/juizglobal_relatorio.md:616-619`) and named three defects gh101 introduced into it (`GENCIPHER-EXTRA`, `SSL-RANDOMIZED-EXTRA`, the `KPG initError` placement). Seeding from it would start the successor set from a body of text whose per-spec verdicts are failing, with no gate able to tell an inherited defect from a new one. Seeding from `jca` starts from text whose behaviour is published, measured and frozen, so every divergence from it is a hunk this change wrote and must justify.

**Why the replay is withdrawn.** Three reasons, in order of weight. (i) The replay imports the same failing verdicts: the 94 hunks are the layer-2 and predicate-graph repairs the audit was assessing when it reproved the set, and 42 of them belong to the predicate graph this change removes outright (D-11). (ii) The replay is behavioural — every one of those hunks changes which call is accused, which is the class of change that needs the differential harness to have run first; the harness is built by this change, so the replay cannot be its own justification. (iii) The replay is not on the path to the problem. The evidence tier of the published analysis is 11,409 events / 84 misuses and every one of them is an allow-list verdict; not one of them is fixed by an automaton repair. Spending the change's budget on the 94 hunks would leave the Android allow-lists wrong and the reports still false.

**What the set carries instead.** Two bodies of work, both small and both mechanically checkable:

1. **The allow-lists, transcribed literally from the api30 `CONSTRAINTS`** (D-10), with one declared normalisation rule and the recorded divergences D-10 enumerates (`EC`, the four ECDSA algorithms, the `deferred-constant` rows and the behavioural OAEP entry).
2. **Six structural repairs, two measured sites and one withdrawal**, each confirmed against the api30 rule, the JDK signature or the generated monitor before being written down, and each re-confirmed on 2026-08-18 against the frozen-control monitor and the published corpus. **Six are repaired**: (1) `GCMParameterSpecSpec:34` declares its second event under the name `c1`, so the generated monitor merges two transition rows and the `c2` the rule declares does not exist — one token, and the gates are the whole of its effect, because the monitor is indexed by the constructed object, each monitor sees at most one event and the `fail` state is unreachable both before and after (`MultiSpec_1RuntimeMonitor.java:4232,4284,4301` — this and every bare generated-monitor line in this design is read from `results/gh101_group8_jca_frozen_control/monitors/`); (2) `SecretKeySpecSpec:27-30` has a stray parenthesis in its `condition`, which the parser discards without diagnostic, so the generated guard is already the intended one (`:7726`) and the repair is textual — Group 2's transcription removes the algorithm list (task 2.4) while the predicate conjunct stays (D-11), so the `condition` survives and the surplus parenthesis with it — the repair is the one-token textual edit; (3) `MessageDigestSpec:74-76` declares an event `reset` with an empty body and no CrySL clause behind it, and — unlike the 17 orphans that G-2 must clear — **no `condition()` either**, so its generated row is `{4,4,4,4,4}` against a `fail` of 4 and every woven `reset()` accuses unconditionally (D-7); ### D-2 — E1 (messages) lands after S (seed, allow-list transcription) and before E4 (structural repairs), with a new written reason

The lineage ordered C-4 → C-3 because "the message names states that C-4 will create". That reason died when `st=` left the envelope (`_lacunas.md:651-666`); the verification (`§6.5`) asks for a new reason or a new order. **Decision: E1 first.** Reasons: (i) E1 is cheap and mechanically verified — 25 four-argument edits on the `jca` seed (23 once S removes the predicate-only sites; task 7.2 recounts from the files and writes the count to `data/jca_android/README.md` — of the seed's 51 `new ErrorDescription(` sites, 50 are live and the 51st is the commented `g4` report of `MessageDigestSpec:57-58`, which E1 leaves commented) and 16 field→target-getter swaps — and it makes every later repair *readable*: the differential harness (EV) reports the accusing event by name only once `ev=` exists, so E4's before/after evidence is per event instead of per site; (ii) both edit the same `.mop` files, so E4 starts only after E1 (and EV) are complete — no per-file interleaving of the two groups; inside E4 there is one owner per file at a time (WORKFLOW §5 locality). The alternative — E4 first — leaves the harness blind during the stage that most needs it.

Under D-4 as revised, the ordering argument no longer rests on E1 installing a bookkeeping invariant that constrains E4: the event name comes from the generator, so E4 adds, renames and removes events with no obligation towards `ev=`. What E4 still inherits from E1 is the `code`/`codes.csv` bijection — an E4 edit that adds or removes a report site adds or removes its row, and the message-property gate holds that. One more inheritance runs the other way: S transcribes every allow-list from api30 (D-10) before E1, so E1 writes the *expected* value of each message from the list as transcribed, and the message-property gate holds the two together thereafter.

**What E1 declares and does not repair: the guard-on-field, value-from-getter pattern.** Nine report sites test the monitor's own field in their `condition()` and, after E1, print the value the bound object reports: `MessageDigestSpec:68`, `CipherSpec:59`, `SignatureSpec:56`, `SSLContextSpec:56`, `TrustManagerFactorySpec:55` and the same idiom in `KeyManagerFactorySpec`, `MacSpec`, `KeyStoreSpec` and `KeyGeneratorSpec`. For an object whose `getInstance` was never observed — the 156 `MessageDigestSpec` rows ending in `but found .` (Guava `clone()`, kmp-tor) are that case — the field is `""`, the guard fires, and the envelope reads `val='SHA-256' exp='…SHA-256…'`: a self-contradicting envelope that the numeric-literal check of the message gate does not see. E1 **declares** the case — one row in `data/jca_android/conformance_record.csv` and one harness trace per site with no observed `getInstance` — and the message gate (task 6.8) and the harness report (task 6.9) flag every envelope whose `val` is a member of `exp`. E1 does not **repair** it: guarding on the bound argument or the getter changes which calls are accused (the object with no observed `getInstance` stops being accused), and a change of that class is measured, not slipped into a group whose acceptance is harness `unchanged`. The repair is E4 task 8.16, expected class `removed` only for traces whose object has no observed `getInstance`; any other class reverts that site and records it. This is what keeps "E1 does not touch automata" true, together with the two other items that leave E1 for E4 (8.14, 8.15; D-4 "Residues").

### D-3 — the envelope: `key=value`, commas allowed, `\n`/`:::` forbidden, unclosed quote means truncation

Grammar (fixed by the researcher): `v=1 code=<SPEC>-<KIND>-<NN> ev=<event> obj=<SimpleClass> val='<observed>' exp='<expected>' msg='<text>'`. JSON was rejected in the lineage (braces, commas and quotes in a positional line — `FINAL:199`). The lineage's comma prohibition is dropped: 27.06 % of today's messages contain commas (every `String.join(",", …)` allow-list) and all four consumers already rejoin field 7 (`logcat_parser.py:341-350`; `violations.py:140-160` `split(",", 6)`; `clock_logcat_join.py:454-460`; `TraceComparator.parseObserved`). `\n` splits the logcat line (a second RVSEC line with no structure — a fabricated record); `:::` is the `unique_msg` separator. Escaping: `'` → `\'` inside values (zero occurrences today, so the property tests exercise it synthetically); `\n` → `\\n` by the collector. Truncation: `LOGGER_ENTRY_MAX_PAYLOAD` = 4068 bytes on API 30 (`_lacunas.md:229-269`); measured envelope sizes on the trial: median 274 B, p99 391 B, max 696 B — so truncation is not a volume risk, only a pathological-`val` risk; producer caps `val` at 512 characters, and the parser treats an unclosed final quote as a truncated record (`truncated=True`, counted), never as a value. `code` KIND vocabulary: `ORDER` (`@fail`), `ALG` (algorithm outside allow-list), `CONSTR` (argument constraint), `KEYSIZE`, `KSTYPE`, `PROTO`, `FORB` (`ForbiddenMethod`, D-13); `<SPEC>` is the specification's file name without its `Spec` suffix, in upper case — `MESSAGEDIGEST`, `TRUSTMANAGERFACTORY`, `GCMPARAMETERSPEC`, `PBEKEYSPEC` — one token per file of the successor set, derived mechanically so that no abbreviation table exists for two sessions to disagree on (no `TMF`, `MD` or `GCM` shorthands); `codes.csv` keeps its header, the token is not a new column. `NN` two digits per spec×kind, listed in `codes.csv` (`spec,code,error_type,site_kind,event,file_line`), bijective with the sites (gate). The lineage's eighth kind, `REQ` (`RequiredPredicate`), is dropped with the predicates (D-11) — no site of `jca_android` can emit it.

### D-4 — the event name is emitted by the generator as a `__EVENTNAME` macro, not written by hand in 134 bodies

**Superseded decision, recorded so it is not re-taken.** This design first put the bookkeeping spec-side: `String lastEventName = "";` in every `declarations` block and `lastEventName = "<name>";` as the first statement of all 134 event bodies, rejecting option O-1 (make the generator emit the name) on the grounds that it "would touch `rv-monitor` (radius M) and needs a release". Both halves of that reason are wrong on this tree. `rv-monitor` is the **first module of this very reactor** (`pom.xml`: `<module>rv-monitor</module>`, `br.unb.cic:rvsec-parent:0.9.3-SNAPSHOT`, same repository), built from source by `mvn install` at the root — there is no external artifact and no release to wait for. And this change **already edits `rv-monitor`**: task 5.2 changes `ViolationRecorder.makeRelevantList` in `rv-monitor-rt`. The radius was already entered.

**The researcher's freeze ruling (2026-08-17), which decides this.** The gh101 freeze is on the **specification sources**: `jca/*.mop` and `CipherTransformationUtil.java` byte-identical to `7e7acb69`, which is what the existing gate tests. It does **not** require that a given `.mop` keep generating a byte-identical monitor. Reproducing a published measurement is done by pinning the toolchain — the Docker image or a commit checkout, **and the JDK** — not by freezing the generator. The JDK is load-bearing and was measured on 2026-08-19: the state numbering a generated monitor carries depends on the JDK that ran the generation, because the ERE-to-FSM conversion of the logic repository returns its states in a different order, so the frozen control regenerates byte-identically under JDK 25 and shows 347 differing state-label lines under JDK 21. The automata are isomorphic and no verdict moves — the constraint is on byte-comparison, not on correctness — but a diff against an existing control must name the JDK that produced it (`data/gh104/evidence/g_regeneration.md`). So a generator change is not a freeze violation and NFR08 is satisfied by the pin, not by the generator standing still. Do not re-derive a stricter freeze from the gate's name.

**Decision: add a `__EVENTNAME` macro to `rv-monitor`, in the two substitution sites of the Java path.**

- In an **event body** (`BaseMonitor.java:350-368`, inside `printEventMethod`, which already holds the `EventDefinition`): expand to the string literal `"<event.getId()>"`. It costs nothing at runtime and needs no field — the name is known at generation time.
- In a **handler body** (`HandlerMethod.java:36-48`, which holds `prop` and the `Monitor`): expand to the call `RVM_eventName()` — a per-class helper the generator emits into `BaseMonitor.toString()` beside the name table, after `checkIfAtomicMonitorCanBeEnabled()` has run (`:665`), where `isAtomicMoniorUsed()` is legal — never to a direct table lookup. The helper reads **`this.getLastEvent()`, which both shapes provide** — generated in the atomic shape, inherited from `AbstractSynchronizedMonitor.java:21` in the other (Context, "What the generated monitor already knows") — and **decodes it per shape**, because the two shapes do not agree on what the accessor returns. Atomic: `getPairValueExtracter` (`BaseMonitor.java:1115-1140`) emits `getLastEvent(pairValue) = pairValue >> numStateBits` with no `-1`, and `calculatePairValue` stores `lastEvent + 1` (`results/gh101_group8_jca_frozen_control/monitors/MultiSpec_1RuntimeMonitor.java:3305-3309`; the initial state is `calculatePairValue(-1, 0) = 0` at `:3292`), so in the 15 atomic classes the raw call yields `idnum + 1`, and `0` before any event. Non-atomic (`BaseMonitor.java:427`, `AbstractSynchronizedMonitor.java:21`): the raw call yields `idnum`, and `-1` before any event. The helper subtracts 1 in the atomic shape and returns `"none"` for the no-event value of its shape (`-1` non-atomic, `0` atomic), the table entry at that index otherwise. The red test of task 3.1 asserts this per shape, on one atomic and one non-atomic fixture: the handler run after the first dispatched event sees that event's own name, and a handler run before any event sees `none`. A monitor that is not the outermost one (`isOutermost == false`, the suffix-matching mode) has neither the accessor nor the field; no `jca` specification uses that mode, so the helper returns the literal `"none"` there and the fail-closed check names the case.

  **A second superseded decision, recorded so it is not re-taken.** An earlier revision of this bullet expanded `__EVENTNAME` in a handler to a direct table lookup on `this.getLastEvent()` and called the expansion "deliberately not shape-aware", on the grounds that `HandlerMethod` is constructed in `initialize` (`BaseMonitor.java:226`) before `checkIfAtomicMonitorCanBeEnabled()` runs (`:665`, inside `toString()`), so `isAtomicMoniorUsed()` would throw `IllegalStateException` there, and the raw `RVM_lastevent` field does not exist in the atomic shape. The constraint is real; the conclusion was wrong, because the raw accessor is off by one between the shapes: the direct lookup would have named the *next* event in the 15 atomic classes and the first event instead of `none` — exactly the misindexed name read as a fact that this decision exists to rule out. The constraint is met by moving the decoding out of `HandlerMethod` into a helper emitted where the shape is known; the handler expansion needs only the helper's name.
- The **name table** is emitted once per monitor class, in the `// state declaration` loop of `BaseMonitor.toString()` (`:806-812`) — where the `Prop_N_transition_*` arrays land today — iterating `this.events` (`BaseMonitor.java:122`, populated at `:179` from `rvmSpec.getEvents()`) in `getIdNum()` order. One table per class, not per property: `getIdNum()` is spec-wide, which is why `handleEvent(idnum, …)` and `MonitorTermination`'s switch already share it. Its name and `RVM_eventName` are reserved in `RVMNameSpace` beside `RVM_lastevent`.
- `RawMonitor.java:90-105` substitutes the same macros for the raw-monitor mode and gets the same treatment, so no path can leak the literal. A post-generation check fails closed if the string `__EVENTNAME` survives anywhere in the generated Java.

**Why this beats the 134 hand-written lines.** It is written once instead of once per specification set (`jca_android` now, `generic` later). ### D-6 — the weaver arity rule is a measurement, not a filter: the three clauses are evaluated and counted, no advice is excluded

**What was decided and what it replaces.** The lineage's D-C landed the arity rule as a filter: an advice whose positional `args()` arity is incompatible with the concrete call would be dropped from the merged wrapper. **Decision: implement the rule, evaluate it in the same place, and publish the count — but exclude nothing.** `WrapperEmitter.generate` returns an `EmitResult` carrying `advicesExcludedByArity`, and `BatchRunner.java:199-201` puts it in `counts` beside `wrappersGenerated`. The emitted wrappers are byte-identical to what the weaver emits today, and the instrument that asserts it is task 4.6: the sha256 of `mop/MonitorWrappers.java` re-woven from the frozen descriptor before and after the change, recorded in `evidence/e2_reweave.md` and expected byte-identical — `EmissionParityTest` compares inline against wrapper emission, not before against after, and an unchanged `wrappersGenerated` would not see a lost monitor call, so neither is that instrument. Beside it, `WrapperMergeTest` gains three cases (task 4.4): an `args(a,*)` advice counted **and still emitted** (count 1 on a descriptor carrying the `TrustManagerFactory` group alone), an advice with no `args()` never counted, and a trailing `..` honoured.

**Why measurement and not filtering.** Excluding an advice changes which monitor calls fire, which changes which calls are accused, which changes what the published numbers mean — the same class of behavioural risk as the replay withdrawn in D-1, and this change has no before/after device evidence with which to take it. **The mechanism the counter uses.** `WrapperEmitter.generate` groups by `registryKey(cc)` (`:133-136`, `declFqn#method(params)return`) at `:270-273`; `firstCallTarget` (`:507-525`) walks the AST for the first `CallPC` and ignores `ArgsPC`; overload expansion (`:326-403`) is driven by the `call()` param specs only. ### D-10 — the allow-lists are a literal transcription of the api30 `CONSTRAINTS`, under one declared normalisation rule and with recorded divergences

> **Anchor superseded on 2026-08-24 by D-15.** The 2026-08-24 audit

(Sub-labels used elsewhere in this change: **D-b** = the Cipher list stays in Java, in a new class; **D-c** = the `EC` divergence; **D-30** = the `deferred-constant` class. **D-a**, cited by tasks for the `ErrorType` corrections, is D-13.)

**What was decided and what it replaces.** The lineage's D-B chose the oracle *per clause family*: MetaCrySL api30 for availability (Cipher catalogue, keystore types) and CrySL 1.5.2 for recommendation (digest algorithms, TLS protocols), recorded per specification. That rule is withdrawn. **Decision: every allow-list of `jca_android` is the `CONSTRAINTS` set of the matching `generated/api30/<Spec>.cryptsl`, transcribed literally.** One oracle, one anchor, no per-clause judgement call. The reason is that the mixed rule reintroduces the problem the set exists to solve: "recommendation" is exactly the label under which `TLS` and `AndroidKeyStore` were being rejected — a JSE-era preference presented to the developer as a platform fact. If the api30 rule admits a value, the set admits it; if the researcher believes the rule is wrong, the place to say so is the divergence record, not a second anchor.

**How far the current set is from that.** The row-level table was committed by task 2.15 on 2026-08-19 and it has **59 rows** — 55 api30 `CONSTRAINTS` clauses over the 21 paired rules plus 4 `.mop` value tests with no clause behind them: 30 **declared by the rule and ignored by the `.mop`**, 9 where the `.mop` is more permissive, 8 identical, 5 divergent, 4 **tested by the `.mop` with nothing behind them in the rule**, 3 where the `.mop` is more restrictive. The pivot analysis's summary of 74 = 30/14/13/7/7/3 is superseded: only its count of unimplemented clauses survived measurement. `MOP-SEM-BASE` is 4 rather than 1, because besides `SecretKeySpec`'s algorithm list three inherited value tests sit on rules that declare no `CONSTRAINTS` block at all (`IvParameterSpec`, `GCMParameterSpecSpec`, `DHGenParameterSpecSpec`). The table is `data/jca_android/constraint_table.csv`, the sixth record of the set (`spec,cryptsl_line,mop_line,verdict`; verdicts `CRYSL-NAO-IMPLEMENTADO`, `IGUAL`, `MOP-SEM-BASE`, `MOP-MAIS-PERMISSIVO`, `DIVERGENTE`, `MOP-MAIS-RESTRITIVO`; one row per api30 `CONSTRAINTS` clause of the 21 paired rules, Cipher through the Java class, plus one per `.mop` test with no clause behind it, verdict per row) and G-CONF's frozen-`jca` report reproduces the table, not this sentence. Two consequences follow directly from the transcription. `SecretKeySpecSpec`'s algorithm allow-list is in the third category — the rule declares nothing about `alg` — so **the list goes away**. And `SecureRandom`, `KeyManagerFactory` and `TrustManagerFactory` are cases where the api30 rule is the *more restrictive* one and is right: `Windows-PRNG`, `NativePRNG`, `PKCS11` and `SunX509` do not exist on Android.

**The normalisation rule, which the transcription cannot do without.** A literal transcription alone leaves roughly 3,000 of the measured events untouched, because the values the apps actually pass differ from the rule's spelling in case, in punctuation, or by being a Conscrypt alias:

- **`X509` (643 events, 3 apps, 5 misuses)** is not an algorithm at all: it is Conscrypt's alias for `PKIX` (`OpenSSLProvider.java:90`, beside the `PKIX` registration at `:89` — every `OpenSSLProvider.java` pointer in this design is a line of `rv-android/backup/gh104-analise/OpenSSLProvider.java`, a local, gitignored copy of Conscrypt `android11-release`; task 2.5 copies the pointers into `data/jca_android/alias_table.csv`, which is the versioned record; the `mapping_report.md` citation of `:101-107` is wrong — those lines are `AlgorithmParameters` DESEDE/TDEA — and this pointer replaces it). The api30 `TrustManagerFactory` rule declares `{PKIX}` and nothing else, so without an alias table the 643 stay accused after the transcription.
- **`SHA256WITHRSA` (4 events)** — api30 has `SHA256withRSA`; case only.
- **`OAEPWithSHA1AndMGF1Padding` (109 events, 1 app, 1 misuse)** — this one the normalisation rule does **not** close, and that is verified rather than assumed. The observed value is `RSA/ECB/OAEPWithSHA1AndMGF1Padding`, with no hyphen in `SHA1` (218 occurrences in the CSV = 109 events, counted once in `message` and once in `unique_msg`); api30 declares `OAEPwithSHA-1andMGF1Padding`, and Conscrypt registers `RSA/ECB/OAEPWithSHA-1AndMGF1Padding` (`OpenSSLProvider.java:338`) plus the alias `RSA/None/OAEPWithSHA-1AndMGF1Padding` (`:339-340`), all hyphenated — the unhyphenated spelling is registered nowhere in that file. Since `CipherSpec.g1` is an `after … returning(Cipher c)` advice, the 109 calls returned a `Cipher`, so some other platform provider accepts the spelling; the candidate is the Bouncy Castle build Android ships, which is outside this file. **Decision: no alias row.** There is no provider line to cite, and admitting a second class of authority would weaken the per-entry pointer requirement of INV-INS-127 for a single value. The case is entered in the divergence record with its evidence labelled **behavioural**, and naming the provider that resolves it is execution work.
- **`SHA1` / `SHA` / `SHA256`** (Conscrypt `OpenSSLProvider.java:115-116` for `SHA1`/`SHA` → `SHA-1` and `:124` for `SHA256` → `SHA-256`) fragment **2,340 events / 22 misuses** across three spellings of the same two digests. The `mapping_report.md` citation of `:131-132,140` is wrong — `:131-132` is `SHA-512`/`SHA512` and `:140` is `KeyGenerator.ARC4`, which is not an alias — and these pointers replace it.

The comparison the `.mop` files perform today is not uniform either: it is case-sensitive in eight specifications (`Mac`, `Signature`, `SecureRandom`, `KeyGenerator`, `TrustManagerFactory`, `KeyManagerFactory`, `KeyStore`, `KeyPairGenerator`) and passes through `.toUpperCase()` in three (`MessageDigest`, `SSLContext`, `SecretKeySpec`). **Decision: comparison is case-insensitive everywhere in the set, plus an alias table derived from Conscrypt `android11-release` with one source pointer per entry, recorded per specification in `data/jca_android/alias_table.csv`.** the table has 158 rows — 149 in services one of the 21 specifications covers and 9 (`AlgorithmParameters` 8, `SecretKeyFactory` 1) in services with no specification, kept with the flag — each with an `in_api30_allowlist` flag, defined once: `yes` when the canonical name is an entry of the successor set's allow-list **after tasks 2.6 and 2.7** (post-divergence), so the `KeyPairGenerator → EC` rows and the sixteen `SHA*withECDSA` rows are `yes`, and a row in a service the set does not cover is flagged against a rule the set does not carry (the `Cipher.GCM` registration is not among those: `GCM` occurs in the `Cipher` list as a mode of operation, and the alias points at a whole transformation). The counts of `yes`/`no` rows, and of the `yes` rows that resolve at run time in covered services, are recomputed and recorded by task 2.5 in the README line of `data/jca_android/alias_table.csv`, not here. A transcription without this rule would be literally faithful and practically inert.

**Where the alias table lives and how it is read (decided 2026-08-18, closing the open question this design carried).** `alias_table.csv` is a **file of its own** under `data/jca_android/`, not a column of `conformance_record.csv`: the conformance record answers *which api30 rule a specification transcribes*, one row per specification, and folding 158 alias rows into 21 conformance rows makes both unreadable. Resolution happens **at runtime but not by reading the CSV**: a new utility class, `ConscryptAliasTable` in `rvsec-core/src/main/java/br/unb/cic/mop/jca/util/`, carries the table **as code**, and each `jca_android` allow-list check **names that class in its call**. This is the same pattern D-b already fixes for the Cipher transformation tables, and it is what satisfies INV-INS-112 — the specification names the utility it calls, nothing selects between tables at runtime, no shared mutable key exists — while leaving the frozen `jca` untouched, since no `jca` specification names the class and therefore no `jca` verdict moves. The Java equality test of task 2.5 asserts that the in-code table equals the CSV row for row — all 158 rows, flag included, under the flag definition above — so the record and the instrument cannot drift.

**Why the aliases are not expanded into the allow-lists instead.** Three reasons, each sufficient. (a) The rule is not expansible: case-insensitive comparison cannot be written as a list, so an expanded allow-list would have to enumerate every spelling of every entry in every case. (b) An expanded list is no longer equal to the api30 clause, so G-CONF has nothing left to compare and the conformance argument — the whole reason the set has a single oracle — collapses. (c) It repeats precisely the defect this change removes: the frozen `jca` already resolves aliases by mixing them into the allow-list, which is why `KeyGeneratorSpec`, `MacSpec` and `SecretKeySpecSpec` carry `HMAC-SHA256`, `HMAC/SHA256` and `PBEWITHHMACSHA-256` as if they were algorithms the platform offers (they are Conscrypt aliases: `HMAC-SHA256`/`HMAC/SHA256` → `HmacSHA256` at `OpenSSLProvider.java:170-171`, `PBEWITHHMACSHA256` → `HmacSHA256` at `:481`), and why nobody can tell from the file which entries came from a rule and which from a provider registration.

**A limit of the table, declared.** Conscrypt is not the only provider on the platform: `AndroidKeyStore` comes from `AndroidKeyStoreProvider` and `BKS`/`BouncyCastle` from Bouncy Castle, and `OpenSSLProvider.java` registers **no** `KeyStore` alias at all. The `KeyStore` allow-list therefore has no alias coverage here, which is recorded as a limit of the table rather than as evidence that none is needed.

**Where the Cipher list lives (D-b).** It stays in Java and does not move into the `.mop`. Consequence: the set needs a **new class**, `Api30CipherTransformationUtil` in `rvsec-core/src/main/java/br/unb/cic/mop/jca/util/` (the package of the frozen `CipherTransformationUtil`), because `CipherTransformationUtil` belongs to the frozen `jca` and `AndroidCipherTransformationUtil` belongs to the archived `jca_android_bug_predicate`, and neither may be edited. Its tables are transcribed from the `CONSTRAINTS` of `generated/api30/Cipher.cryptsl` — where the frozen utility admits two algorithm families (AES, RSA), the api30 rule admits eight. The allow-list conformance gate therefore reads that Java class for `CipherSpec` and the `.mop` files for every other specification.

**The divergence rule, generalised (2026-08-18).** The transcription meets the platform in two directions, and the rule is asymmetric on purpose.

*The api30 rule admits something the frozen `jca` rejected → the set admits it, and the detection is lost.* This is a researcher decision, recorded, not a pending item: the single oracle is what makes the verdicts checkable, and re-narrowing a list because the reviewer prefers a stricter one restores exactly the JSE-era preference-as-fact that produced the `TLS` and `AndroidKeyStore` reports. The largest instance is measured, not estimated. The api30 `MessageDigest` rule admits `MD5` and `SHA-1` and the api30 `Signature` rule admits `MD5withRSA` and `SHA1withRSA`; the published dataset carries **6,048** `MessageDigestSpec` / `UnsafeAlgorithm` rows, of which **3,552** are `MD5` and **2,340** are `SHA-1`, `SHA1` or `SHA` — **5,892 rows**, 97.4 % of that specification's `UnsafeAlgorithm` reports (36.4 % of all its 16,183 reports) and 6.1 % of the corpus's 97,018. Those stop being reported. The number goes into `conformance_record.csv` against `MessageDigestSpec` and `SignatureSpec` so that the silence is legible as a decision.

A consequence for the vocabulary, declared here so it is not read as an oversight: in `jca_android` the `ErrorType` `UnsafeAlgorithm` (KIND `ALG` in the envelope's `code`) means "value outside the api30 allow-list of the platform", not "cryptographically insecure". `MD5` and `SHA-1` are admitted by the api30 `MessageDigest` rule and are no longer reported, and a value that is reported is one the platform rule does not list. The name is kept for continuity with `jca` — the readers of both eras key on it — and the meaning shift is declared, not hidden.

*The api30 rule omits something the platform demonstrably has → the list receives it, with a divergence entry citing the platform source.* Never the reverse: nothing the rule admits is removed, and nothing is added on preference. Two cases are proved and both are taken.

**Recorded divergence 1: `EC` in `KeyPairGenerator` (D-c).** The seed already carries `EC` (`KeyPairGeneratorSpec.mop:22`, `validate` at `:34`), and the literal transcription of task 2.4 would remove it: the api30 `KeyPairGenerator` rule (`KeyPairGenerator.cryptsl:45`) declares `{DSA, DH, RSA}`; `EC` appears only inside the implication `alg in {"EC"} => keySize in {256}`, which is a dead branch because the CONSTRAINTS are conjunctive and the algorithm list already rejects `EC`. This is a MetaCrySL modelling defect, and the evidence says so rather than inferring it: `samples/jca/android/11plus/KeyPairGenerator.ref:2` writes `define algorithm = {"EC"};`, the command that fills a `${algorithm}` hole, but `samples/jca/base/KeyPairGenerator.cryptsl:27` writes the list as a **literal** (`alg in {"DH","DSA","RSA"}`) instead of `alg in ${algorithm}` — so the `define` is discarded in silence. That this is an accident and not an intention is shown by the same `11plus` tier using the same idiom in `KeyGenerator.ref`, where it works, because `base/KeyGenerator.cryptsl:27` has the hole. Only three base specifications hard-code the literal (`KeyManagerFactory`, `KeyPairGenerator`, `TrustManagerFactory`) and only `KeyPairGenerator` has an Android `.ref` trying to extend it. **Decision: `jca_android`'s `KeyPairGenerator` allow-list keeps `EC` (keySize 256) against the literal rule — task 2.6 is a "kept against the rule" hunk, not an addition — and the divergence record carries an entry naming the MetaCrySL defect and stating that the root fix is `alg in ${algorithm}` in the base specification — not performed here, because MetaCrySL is not edited by this change.** The justification is the change's own purpose: `EC` is the algorithm Android documents for `AndroidKeyStore`, so removing it by literal transcription would fabricate exactly the class of spec-artefact this change exists to eliminate. The same rule has a second, smaller hunk in the other direction: api30 `KeyPairGenerator.cryptsl:51` gives RSA `{4096, 2048}` where the seed's `validate` (`:30`) also accepts 3072, so task 2.4 transcribes `{4096, 2048}` and the conformance record carries the hunk (RSA-3072 dropped).

**Recorded divergence 2: the four ECDSA signature algorithms in `SignatureSpec`.** The api30 `Signature` rule names exactly one ECDSA algorithm, `SHA224withECDSA`, because the only MetaCrySL tier that touches ECDSA is `20plus` and it names that one; the others were never modelled. That `SHA1withECDSA`, `SHA256withECDSA`, `SHA384withECDSA` and `SHA512withECDSA` exist on API 30 is read off the platform rather than inferred: Conscrypt `android11-release` registers `Alg.Alias.Signature` entries whose targets are those names — `OpenSSLProvider.java:270` (`ECDSA`) and `:271` (`ECDSAwithSHA1`) point at `SHA1withECDSA`, `:286` (`SHA256/ECDSA`) at `SHA256withECDSA`, `:293` (`SHA384/ECDSA`) at `SHA384withECDSA`, `:300` (`SHA512/ECDSA`) at `SHA512withECDSA` — and a provider does not register an alias to a service it does not implement. **Decision: the four enter the `SignatureSpec` allow-list, one divergence entry each, citing the Conscrypt line and the modelling gap.** Without them `SHA256withECDSA` becomes a false positive; it is the practice Android documents for EC keys in the `AndroidKeyStore` — the same keys divergence 1 admits — and the frozen `jca` already accepted it, so a literal transcription would make the successor accuse where its own predecessor did not. **Which record G-CONF reads for which exception**: for every value the successor list carries that the api30 rule omits — the `EC` of task 2.6, the four ECDSA algorithms of task 2.7, and nothing else — the gate (task 6.4) consults `data/jca_android/divergence_record.csv`; for the `deferred-constant` rows and the `api30-admits` cost it consults `conformance_record.csv`; the OAEP non-row above is a `divergence_record.csv` entry too, while aliases live only in `alias_table.csv`. Transcription also narrows lists the seed had wider (RSA-3072, `SunX509`, `NativePRNG*`, `Windows-PRNG`, `PKCS11`, `JKS`/`JCEKS`/`DKS`, `HmacPBESHA1`, `DiffieHellman` — the last leaves `KeyPairGeneratorSpec` and is recorded as a narrowing hunk, a `MOP-MAIS-PERMISSIVO` row of `constraint_table.csv` plus a conformance note, beside RSA-3072); a harness trace carrying one of those values classifies as `introduced — corrected verdict (narrowed by <api30 file:line>)`, an admissible class of task 2.14.

**The third recorded class: a constant the rule declares and the set does not check (D-30).** The pivot counted 30 constants the api30 rules declare and the frozen `.mop` files never test; the number is provisional until `constraint_table.csv` (task 2.15, the sixth record under `data/jca_android/`) is committed and its `CRYSL-NAO-IMPLEMENTADO` rows replace it. Transcribing all of them would add as many checks the set has never run, whose false-positive behaviour on the corpus is unmeasured — the same class of behavioural risk this change refuses in D-1 (the 94-hunk replay) and D-6 (the arity filter), and for the same reason: there is no before/after evidence with which to take it. **Decision: every one of them is born a `deferred-constant` row of `data/jca_android/conformance_record.csv` when task 2.4 transcribes; a row is promoted to a transcribed check only after the harness of task 2.14 (which waits for EV task 6.9) has sized the accusations it adds — so Group S's transcription pass has no dependency on EV, and the promotion pass does.** Each row names** the `.cryptsl` file and clause, the reason it is deferred, and the statement that no accusation is added by leaving it out. This is a third admissible departure from literal transcription and INV-INS-125 names it as such, which is what keeps G-CONF executable: the gate still fails on any difference with no row behind it, and a silently skipped constant is still a defect. The work belongs to Group S with the rest of the transcription (D-12), not to E4, and `constraint_table.csv` (task 2.15) is where they are enumerated before any of them is deferred.

### D-11 — the successor set keeps the predicates of its seed, unchanged: they are neither removed nor repaired

**Superseded decision, recorded so it is not re-taken.** An earlier revision of this design removed the predicate
machinery from the successor set outright: no `ExecutionContext` read, write or `remove`, no `RequiredPredicate`
error type, and the two pure-propagator specifications deleted. The reasoning was measured and it was about the
*repair* being unaffordable — gh101 landed 42 predicate hunks and the 2026-08-08 audit's gate G7 still failed 19 of
22 specifications with roughly five clean live edges, and two of the three defects the audit attributes to gh101
itself were predicate edits — and it concluded that a third attempt at the same graph is not a repair with a
measurable end, while dropping the graph is.

**That conclusion does not follow, and the decision is withdrawn.** "Repairing the graph is unaffordable" and
"removing the graph is affordable" are not the same claim, and only the first was measured. Removal is itself a
behavioural change, and the largest one in this change: it deletes detection at 11 of the 21 predicate-reading
events — 7 total losses, 1 partial and 3 cross-specification provenance checks — and it does so with no before/after
evidence, in a change whose own discipline is that anything altering what is accused is measured by the differential
harness first (INV-INS-124). The two arguments offered for the removal survive only as arguments against *repairing*
the graph here: that the three provenance checks are already inoperative on Android is a reason not to trust them,
not a reason to delete the events that carry them; and the audit's verdict is about the derived set gh101 built, not
about the frozen `jca` this set is seeded from.

**Decision: the predicate machinery of the seed is carried over byte-for-byte.** Every `REQUIRES` clause, every
`ExecutionContext.instance().validate(...)`, every `setProperty(...)`, every `remove(...)` and every
`setObjectAsInAcceptingState`/`unsetObjectAsInAcceptingState` call stays exactly as the frozen `jca` has it — 134
such lines across the 23 files. No `condition()` loses a conjunct, no event declaration is deleted, and no `@match`
handler is emptied. `ExecutionContext` is left exactly as it is at HEAD (`e204e2a4`, equality-keyed), read and
written by the set as before.

**Consequences, all of them simplifications.** The set is the seed's **23 specifications**:
`RandomStringPassword.mop` and `SecretKeySpec.mop` exist only to propagate predicates, and with the predicates in
place they still have work to do. There is no `predicate_removal.csv` — nothing left — so the set carries **five**
records, not six. There is no declared loss of detection to enter in the conformance record, and no recovered guard
to classify in the harness. The `deferred-constant` machinery of D-30 is untouched: it is about `CONSTRAINTS`
clauses, not about `REQUIRES`.

**What gate G-PRED becomes.** It was written to assert the *absence* of `ExecutionContext`. Inverted, it asserts
**preservation**: every predicate site of the frozen `jca` — by file, by event and by kind — is present in the
successor set, and none has been rewritten. That is the gate that would have caught this decision going in.

**Wiring the predicates correctly is a change of its own.** It is the right repair and it is not attempted here.
Its prerequisite is the instrument this change builds: the differential harness, which can size what a predicate
edit adds and removes trace by trace. Attempting it before that instrument exists is what gh101 did.

### D-12 — process: one `tasks.md`, per-group execution files, six parallel first-wave subagents

`openspec/schemas/rv-sdd/schema.yaml:162-164` tracks `tasks.md` and only `- [ ]` lines (`:120,:124`); `docs/WORKFLOW.md:443` needs the checkbox ticked immediately after each task for resume; `:1049-1060` detects the artifact by `tasks.md` existing. **Decision: `tasks.md` holds every checkbox and the dispatch hints (HTML comment at the top, `schema.yaml:151-152`, template `tasks.md:1-6`); each group heading points to `tasks/<GROUP>.md`, which holds the file inventory, per-site table, commands, expected values and the subagent brief. A subagent reads only its group file; the orchestrator reads only `tasks.md`.** This is additive — the schema forbids nothing in the change directory — and keeps subagent context small (`WORKFLOW.md:331`); Group 2 and EV are the two large briefs, the rest are short.

Groups by independence and locality. **Wave 0, one barrier, run by the orchestrator and not by a subagent:** task 2.1 — record `pre-rename-head`, `git mv` the derived set to `rvsec-mop/src/main/resources/jca_android_bug_predicate/`, commit with an explicit pathspec — then task 2.13 immediately (orchestrator, or the first act of Group 2). Monitor generation writes `.rvm` into the source directory (`runtime_verification_generator.py:207-223`) before moving them, so a rename during a generation would corrupt both the run and the rename record (`git diff --cached --name-status --find-renames` shows the similarity score; `git status --short` prints only `R `); hence the rename precedes every dispatch. From wave 1 on the archived set is `jca_android_bug_predicate/` (byte-identical to the pre-rename `jca_android`), `jca_android/` is created by task 2.2 as the seed and is never the derived control, and a task that finds `jca_android/` and no `jca_android_bug_predicate/` stops: wave 0 has not run. **Wave 1, six disjoint file sets, six subagents:** E0 (docs + scripts) ∥ S (rv-experiment and the new `jca_android/` directory) ∥ G (`rv-monitor/rv-monitor`, the generator) ∥ E2 (Java dexlib2) ∥ E3 (collectors + Python consumers, including `rv-monitor/rv-monitor-rt`, a different submodule from G) ∥ EV (new test and script files). ### D-13 — `ErrorType` gains `ForbiddenMethod`, and the mislabelled sites are corrected with it

An `ErrorType` is not a taxonomy for the report writer; it is the first thing the developer reads and it tells them where to look. Today `PBEKeySpecSpec.mop:24,30` report `InvalidSequenceOfMethodCalls` for a **forbidden constructor** — a developer reading that goes looking for a call they forgot to make, when the truth is that the call they *did* make must not exist at all. CrySL says this in its own vocabulary: `FORBIDDEN` is a clause of its own, and it is not a predicate — which matters here, because D-11 removes the predicates and this type survives that removal untouched.

**Decision: add `ForbiddenMethod` to `rvsec-core`'s `ErrorType`. Do not add `RequiredPredicate`** — the lineage planned both, but with D-11 no site of `jca_android` can raise one, and an error type no specification emits is dead vocabulary that the next reader will assume is live.

The same edit corrects the `ErrorType`s the census already catalogued as wrong:

| site | today | correct | why |
|---|---|---|---|
| `PBEKeySpecSpec.mop:24` | `InvalidSequenceOfMethodCalls` | `ForbiddenMethod` | CrySL `FORBIDDEN` constructor; nothing about ordering is wrong |
| `PBEKeySpecSpec.mop:30` | `InvalidSequenceOfMethodCalls` | `ForbiddenMethod` | idem |
| `PBEParameterSpecSpec.mop:49` | `UnsafeAlgorithm` | `UnsatisfiedConstraint` | the condition tests an iteration count, not an algorithm |

This supersedes the earlier plan for `PBEKeySpecSpec:24,30`, which mapped them to `UnsatisfiedConstraint`; that is closer than the current value but still wrong, because it sends the developer to check an argument when the constructor itself is the finding. `codes.csv` keeps the KIND `FORB` for these two sites; the `REQ` kind is dropped from the vocabulary (D-3). The message-property gate checks the type against the site kind (INV-INS-121), so a future edit cannot silently reintroduce the mismatch.

### D-14 — the generated dispatcher releases its lock on every exit

**The measurement.** The generated monitor serialises every event through one global lock. Each of the 134 dispatchers opens with `while (!MultiSpec_1_RVMLock.tryLock()) { Thread.yield(); }` and closes with `MultiSpec_1_RVMLock.unlock()`, and the file contains **zero** `finally` blocks — 134 acquisitions, 134 releases, none of them protected (`results/gh101_group8_jca_frozen_control/monitors/MultiSpec_1RuntimeMonitor.java:9005` declares the single `ReentrantLock`; measured 2026-08-18). The consequence is not a slow path or a lost report. An exception raised anywhere between acquisition and release — in a `condition()`, in an event body, in a `@fail` handler — leaves the lock held by a thread that has already unwound past it. The lock is a `ReentrantLock`, so that thread itself keeps entering (its hold count only grows), and no wrapper, aspect or dispatcher catches anything (`MonitorWrappers.java` and `MultiSpec_1MonitorAspect.aj` contain no `try`/`catch`), so the exception propagates into the woven application frame — on Android an uncaught one kills the process; one the app swallows, as apps commonly do around crypto calls, leaves the lock held. From then on every other thread's dispatcher, in every specification, spins on `tryLock()` inside a `Thread.yield()` loop rather than blocking: the monitored application burns CPU forever on its next monitored call from another thread, with no exception surfacing and no record written. One instrumented app in that state produces a run that looks like a timeout.

**The path is reachable in the frozen set.** `KeyPairGeneratorSpec.mop:29` switches on `algorithm`, a field written only by the `getInstance` events; `KeyPairGenerator.getInstance(String, Provider)` carries no pointcut (`results/gh101_group8_jca_frozen_control/monitors/MultiSpec_1MonitorAspect.aj:357,365` bind only the one- and two-argument overloads), so a generator obtained through that overload arrives at `initialize(int)` with the field still `null` and `switch(null)` raises `NullPointerException` inside the guarded region. Repair (4) of D-1 closes that particular door; it does not close the class, because any future `condition()` or handler can raise.

**Decision: the generator emits the guarded region so the lock is released on every exit.** This is a generator repair, not a specification repair, so it lands in the `__EVENTNAME` group (G) where `rv-monitor` is already open and no other group owns the module — not in E4, which touches `.mop` files only. The framing is emitted where acquisition and release bracket the dispatch body — `Advice.java:176-177` (acquire) and `:254-256` (release) in `rv-monitor/rv-monitor/src/main/java/.../output/combinedoutputcode/event/advice/` — not in `GlobalLock.java`, whose `getAcquireCode()`/`getReleaseCode()` are string fragments that `BaseMonitor.java:543-587` also uses unbalanced (release, start a thread, re-acquire) and that must keep working. The exception itself still propagates to the application, as today; only the lock's release changes. The red test needs a **second thread**: a reentrant lock lets the throwing thread re-enter, so two calls on one thread pass before the repair. It is behaviour-preserving on every path that does not throw, which is what makes it checkable: regenerating the frozen `jca` — the single control — must diff against `results/gh101_group8_jca_frozen_control/monitors/` in the framing, the event-name table and the `RVM_eventName` helper, and in nothing else (no expanded macro: the frozen `jca` has no `__EVENTNAME`). The framing wraps the explicit `tryLock` form the dispatchers emit; `GlobalLock.useImplicitLock` is hard-set `false`, so the implicit-lock branch is not emitted and receives no framing.

**Why it is inside this change rather than an issue of its own.** The researcher decided it on 2026-08-18. The argument that carried it is that this change already reopens the generator, already rebuilds the reactor and refreshes `lib/`, and already regenerates and diffs the control — so the marginal cost is the emitter edit and one test, while the marginal cost of deferring is that every device-side task of this change, E6 included, runs on an instrument that can hang without saying so. The invariant is INV-INS-129, and the scope is exactly the dispatcher framing: no change to which advice fires, to the lock's identity, or to the spin loop.

### D-15 — the value oracle is re-anchored to the expert-validated CrySL rules; D-10's machinery is kept, its anchor is withdrawn

**Decided by the researcher on 2026-08-24**, reversing the anchor of D-10 after the audit
(`docs/20260824_auditoria_specs_jca_android.md`, commit `5fbe8173`) measured the chain the
api30 oracle sits on. Three findings carried the reversal. (a) The MetaCrySL manual
transcription (original rules → `samples/jca/base/`) loses 16 of 49 rules and damages 19 of
the surviving 33 — inverted `length` comparators, fabricated clauses, a `FORBIDDEN` on a
method that does not exist, `notHardCoded[password]` deleted from all three rules that had
it. (b) The Android tier `.ref` files were derived from provider registries, so every
refined list is an **availability catalogue**: api30 `MessageDigest` admits `MD5`/`SHA-1`,
`SSLContext` admits `SSL`/`TLSv1`/`TLSv1.1`, `Mac` admits `HmacMD5`/`HmacSHA1`,
`KeyGenerator` admits `ARC4`, `SecretKeyFactory` grows 12→44 including broken KDFs. A set
faithful to that oracle cannot, by construction, accuse an insecure algorithm the platform
offers. (c) The generation stage is faithful (union exact in all 11 holes), so the defects
are upstream of it and un-fixable from here — MetaCrySL stays read-only.

**Decision.** Every **value clause** of `jca_android` — the allow-lists and value tests,
including the Cipher transformation tables in their Java class (D-b) — is a literal
transcription of the `CONSTRAINTS` of the corresponding rule in
**`RVSec-replication-package/tools/rules/*.crysl`**, the copy the published numbers were
measured against. `UnsafeAlgorithm` (KIND `ALG`) regains its published meaning:
"cryptographically insecure per the expert rule". The scope is values only: **ORDER,
event alphabets, and the predicate wiring of gh105 keep their api30 anchor** — the audit
measured the original ORDER survives the chain nearly intact, so there is no defect to
correct there, and re-anchoring it would reopen G-ORDER's nine recorded divergences and the
36-clause ledger for no detection gain.

**Provenance of the oracle copy, pinned.** Three local copies of the 49 rules exist and the
audit measured them: the upstream CogniCrypt checkout (`Crypto-API-Rules`, `master` at
`6d844ab`, 2022-05-12) and `rvsec-cognicrypt/CrySL-Rules` are byte-identical; the
replication-package copy differs in exactly one value — it adds `"CCM"` to the AES modes of
`Cipher.crysl:97,113`. That addition is **local to RVSec**: the *current* upstream `master`
(checked 2026-08-24) still carries no `CCM` — and has meanwhile moved in the opposite
direction, dropping `CBC`/`PCBC` from the AES modes, which is precisely why the oracle must
be a pinned copy and not a moving branch: re-anchoring to today's upstream would accuse
`AES/CBC/PKCS5Padding`, the corpus's most common transformation, on nobody's decision. The
re-anchoring task records the sha256 of the 49 files as a freeze item and enters the CCM
addition as a provenance row.

**Warts are transcribed, not fixed.** The expert lists carry measured quirks —
`Cipher` admits `OAEPWithMD5AndMGF1Padding` but no SHA-1 OAEP variant, `MessageDigest`
omits `SHA-224`, `Signature` omits `SHA224withECDSA` and `SHA1withECDSA`. Researcher
decision: they are transcribed literally, each with a record row (`kind=oracle-wart` in the
divergence record) naming the quirk. Correcting a wart privately would repeat the
MetaCrySL failure this decision exists to undo: an unvalidated edit on top of a validated
rule. The harness and the C5 replay size what each wart costs before merge.

**The platform-adjustment layer — the one admissible widening, closed and cited.** A value
enters an allow-list beyond the expert list **only** when rejecting it would accuse a
practice the platform itself recommends, and only with a primary-source citation
(`kind=platform-value` in the divergence record; an uncited candidate is dropped and stays
accused). The enumerated candidates, from the five rows that motivated D-10's pivot:
`SSLContext` += `TLS` (the negotiated-protocol name; on API 30 it negotiates up to
TLSv1.3); `KeyStore` += `{AndroidKeyStore, AndroidCAStore, BKS, BouncyCastle}` (the expert
list is JSE-only — `{JCEKS, JKS, DKS, PKCS11, PKCS12}` — and names no Android type);
nothing else. `X509` needs no entry — it resolves to `PKIX` through the alias table, and
`PKIX` is in the expert list. `SHA256WITHRSA` needs no entry — case-insensitivity covers
it. The unhyphenated OAEP spelling stays a `behavioural` record — doubly so now, since even
the hyphenated SHA-1 OAEP is outside the expert list (a wart row). Values the expert lists
carry that Android does not offer (`SunX509`, `NativePRNG*`, `Windows-PRNG`, `PKCS11`,
`JKS`, `JCEKS`, `DKS`) **stay in the lists**: they are inert on the platform and removing
them is exactly the un-validated narrowing this decision forbids.

**What dissolves and what returns.** Under the expert oracle, D-10's two recorded
divergences dissolve — `EC` (with `keySize 256`) and `SHA256/384/512withECDSA` are already
in the expert lists; their `api30-omits` rows are closed with a note, and `SHA224withECDSA`
leaves the `SignatureSpec` list as a wart. The narrowings D-10 accepted are undone: RSA
`3072` and `DiffieHellman` return to `KeyPairGeneratorSpec`, `SunX509` to the two factory
lists, the `SecretKeySpecSpec` algorithm list `{AES, HmacSHA256, HmacSHA384, HmacSHA512}`
is restored (its removal was the audit's clearest case of the oracle destroying a check the
monitor already had). The detections D-10 priced and gave up return: MD5/SHA-1 digests
(5,892 rows of the published corpus), `MD5withRSA`/`SHA1withRSA`/`SHA1withDSA`,
`SSL`/`TLSv1`/`TLSv1.1`/`Default`, `HmacMD5`/`HmacSHA1`,
`ARC4`/`BLOWFISH`/`DESede`/`ChaCha20`, and — the case D-10 never priced — `AES/ECB` and
every other transformation the frozen Cipher tables reject. The AES key-size clause is
**not** in this list: it is deferred, for the reason given below. The acceptance criterion is two-sided and measured by the harness plus the C5
replay: the security accusations return, **and** the four platform-artefact rows that
motivated D-10 (TLS 8,648 · AndroidKeyStore 2,005 · X509 643 · SHA256WITHRSA 4) stay
non-accused — the first two through the adjustment layer, `X509` through the alias table,
`SHA256WITHRSA` through case folding. The fifth row D-10 listed, OAEP-no-hyphen (109), is
**not** in the non-accused half and never was: `RSA/ECB/OAEPWithSHA1AndMGF1Padding` is
rejected by the api30 anchor too — the api30 padding list spells it `OAEPwithSHA-1andMGF1Padding`,
with the hyphen — so it was accused before this decision and stays accused after it, the more
so because the expert rule carries no SHA-1 OAEP variant at all (an `oracle-wart` row). Its
`behavioural` record explains the spelling; it does not clear the accusation. Counting it
among the rows the re-anchoring must keep silent was an error of D-10's own bookkeeping,
corrected here.

**How the anchor is realised: the expert rule is the authority, the frozen `jca` list is
the transcription of it that was published.** The re-anchoring does not re-transcribe the
rules from scratch. For each value clause, the list the successor set carries is the list
the frozen `jca` carries — because that list *is* the expert transcription, and it is the
one the published numbers were measured against — and each list is then checked, entry by
entry, against the `CONSTRAINTS` of the pinned expert copy. The two agree on every
security-relevant value; where they differ it is by spelling variants the frozen set
hand-wrote into its lists (`SHA256` beside `SHA-256`, `HMAC-SHA256` beside `HmacSHA256`,
`TLSV1.2` for `TLSv1.2`), and those stay in place rather than being stripped into alias
rows. Stripping them would be a second unvalidated edit for no detection gain: the lists
are compared through `ConscryptAliasTable.matches`, which folds case and resolves aliases,
so a redundant spelling changes no verdict, while removing one could. Each such entry gets
a `spelling-variant` note in the conformance record naming the expert clause it duplicates,
so the gate can tell a redundant spelling from an unbacked value.

**The measured cost of the api30 anchor, restated with the case D-10 never named:
`AES/ECB`.** The audit priced the api30 anchor by the algorithm lists it widened. The
larger loss is in the `Cipher` tables, and it was not stated: `Api30CipherTransformationUtil`
admits **`AES/ECB/PKCS5Padding`** — `ECB` is a member of the transcribed `AES` mode clause
(`Cipher.cryptsl:137`), and no transcribed padding clause covers `ECB`, so the method falls
through to its `return true`. Verified by execution against both classes: `AES/ECB/PKCS5Padding`,
`AES/ECB/NoPadding`, `DESede/CBC/PKCS5Padding`, `DESede/ECB/PKCS5Padding`,
`BLOWFISH/ECB/NoPadding`, `ARC4` and `ChaCha20` are all accused by the frozen
`CipherTransformationUtil` and all admitted by `Api30CipherTransformationUtil`. ECB is the
misuse the crypto-API literature reports first and the one this line of work exists to
detect; a set that admits it is not an Android instrument, it is a broken one. The case does
not appear in the published corpus's `CipherSpec` accusations (whose 109 rows are all the
OAEP spelling), so it costs no published number — it is a false negative the successor set
would have carried into the next campaign undetected, which is why it is recorded here and
carried by a trace of its own rather than by the C5 replay.

**`CipherSpec` re-points at the frozen utility; no new Cipher class is written**
(researcher decision, 2026-08-24). `jca_android/CipherSpec.mop` imports
`CipherTransformationUtil` — the class of the frozen `jca` — instead of
`Api30CipherTransformationUtil`. The freeze on that class (INV-INS-109/118, task 10.1)
forbids **editing** it, not **calling** it: it stays byte-identical and gains a second
caller, and no verdict of the frozen set moves, because a `.mop` of `jca` calling a class
that another `.mop` also calls is the same call it always made. The alternative — a third
class transcribing `Cipher.crysl` directly, which would additionally carry `CCM` and the
eight `PBEWithHmacSHA*AndAES_*` transformations — is rejected under P1: it is new code whose
behaviour on the corpus is unmeasured, to gain values no corpus app uses.
`Api30CipherTransformationUtil` is **not deleted**: it keeps no caller and stays as the
record of what the api30 anchor said, which is what INV-INS-112 asks of a set's Cipher
tables and what makes the two anchors comparable. It leaves the G-CONF path, whose
`--cipher-util` input now names the frozen class.

**`SSL` stays accused** (researcher decision, 2026-08-24). Conscrypt registers
`SSLContext.SSL` and `SSLContext.TLS` on the same implementation class
(`OpenSSLProvider.java:80-81` — both take `defaultSSLContextSuffix`, which is the TLSv1.2 or
TLSv1.3 suffix), so on API 30 the two names are behaviourally the same context. `SSL` gets
no `platform-value` row all the same: the registration is a `put`, not an `Alg.Alias`, so
the alias rule of INV-INS-127 gives it no row either; the expert rule names `TLSv1.2` and
`TLSv1.3` and nothing else; and asking a provider for `"SSL"` is the misuse the rule is
about, whatever this one platform happens to resolve it to. The behavioural equivalence is
recorded as a `behavioural` row so the reader of a report knows what the 103 accused events
actually got at run time. `TLS`, by contrast, does get the row: it is the name the platform
documents and the one an app that wants the current protocol is told to ask for.

**The AES key-size clause stays deferred** (researcher decision, 2026-08-24). The expert

published `jca` never implemented it — `jca/KeyGeneratorSpec.mop` has no key-size test at

an unmeasured false-positive rate, inside a change whose whole point is to stop making
unvalidated edits to expert-validated lists. It stays a `deferred-constant` row citing the
expert clause text. The same disposition applies to every expert clause the frozen set left
unimplemented: the re-anchoring restores the lists the experts wrote, it does not enlarge
the set of clauses the instrument checks.

**What this does to the records and gates, and what it deliberately does not touch.**

## API Design

### `WrapperEmitter.generate(descriptor, monitorDir[, index]) -> EmitResult`
`EmitResult { List<WrapperEntry> wrappers; int advicesExcludedByArity; }`. Precondition: descriptor parsed. Postcondition: **`wrappers` is exactly what the emitter produced before this change** — no advice is excluded — and `advicesExcludedByArity` is the number of **advice/overload pairs** — one admitted advice against one concrete overload of its wrapper — whose positional `args()` arity is incompatible under the three clauses of D-6 (advices with no `args()` clause are never counted; the same advice counts once per incompatible overload). On the frozen `jca` descriptor the expected value is 10 pairs over 4 distinct advices (`TrustManagerFactorySpec_g2` ×1, `KeyManagerFactorySpec_g2` ×1, `SecureRandomSpec_g2` ×3, `SecureRandomSpec_g4` ×5); the `MUST be 1` scenario of the instrumentation delta holds for a descriptor that carries the `TrustManagerFactory` group alone. `BatchRunner` writes `counts["advicesExcludedByArity"]`. The name says "excluded" because it counts what a filter would exclude; the filter is a follow-up, not this change.

### `ErrorCollector.addError(ErrorDescription err)` (logcat)
Emits one line `summary + "," + escape(expecting)`; `expecting == null` → sentinel envelope; `escape`: `\n`→`\\n`. Never throws for a `null` message.

### `_parse_error_message(message: str) -> RvErrorLog | None`, `parse_logcat_line(line, diagnostics: ParserDiagnostics | None = None)` and `LogcatRepository.parser_diagnostics: ParserDiagnostics`
`ParserDiagnostics` is defined in rv-android-core, `rv_android_core/domain/coverage.py`, beside `LogcatRepository` (`:451`), which gains the field — rv-android-core cannot import rv-coverage, so the type cannot live in `logcat_parser.py`; `parse_logcat_line` (`logcat_parser.py:214`) increments the object it is handed, and its live caller `tracker.py:411` passes the repository's. `RvErrorLog` gains `code, event, obj, val, exp, msg: str` (defaults: `code`/`event` = `UNSPECIFIED`, the others `""`, so the parser's six-positional constructions keep working until task 5.3 fills them) and `truncated: bool = False`; every `None` return increments exactly one counter; `parse_logcat_file` re-raises after logging the line number.

### `RvErrorLog.unique_msg -> str`
`f"{class_full_name}:::{method}:::{spec}:::{error_type}:::{code or 'UNSPECIFIED'}:::{event or 'UNSPECIFIED'}:::{message}"` — the only constructor.

### `violations.read_errors_csv(path) -> (rows, CsvDiagnostics)`; `parse_payload(payload) -> ViolationEvent`
`read_errors_csv` already returns `(rows, CsvDiagnostics)` (`violations.py:215`); the change extends `CsvDiagnostics` with `unique_msg_unparsed`/`unique_msg_disagrees` and the envelope counters. 13-column header or `ValueError`; seven `:::` parts or `unique_msg_unparsed += 1`; envelope keys parsed; unclosed quote → `shape_ok=False`, `envelope_truncated += 1`.

### `gh104_gates.py --monitor <MultiSpec_1RuntimeMonitor.java> --allowlist <data/<set>/gate_allowlist.csv> --crysl <generated/api30/> --alias <data/jca_android/alias_table.csv>` → JSON `GateReport`; `gh104_diff_harness.py run(set_a: Path, set_b: Path, traces: Path, out: Path)`
The gates CLI takes the generated monitor, the allowlist, the api30 directory and the alias table — no `.mop` directory. `--crysl` is `generated/api30/`, read-only: G-2 needs it to tell a correct `CONSTRAINTS`/`REQUIRES`/`FORBIDDEN` encoding from a real orphan, and G-CONF needs it to compare transcriptions under the normalisation `--alias` supplies. G-ERE and the lint read the `.mop` directory through `scripts/gh104_mop_lint.py`, and `test_gh104_structural_gates.py` pins G-ERE's expected count beside the others. Both entry points need `RVSEC_HOME`; generation happens in a scratch dir off tmpfs; the harness returns per-trace verdicts (`accused`, `event`, `envelope`) for both snapshots and a `moved`/`removed`/`unchanged`/`introduced` classification. Traces are keyed by API call (`<Class>.<method>(<args>)`), resolved by `TraceRunner` (`rvsec-mop/src/test/java/.../TraceRunner.java`, with its self-test in `TraceRunnerTest.java`) against each snapshot's own pointcuts and dispatched through the snapshot's generated static event dispatchers (`MultiSpec_1RuntimeMonitor.<Spec>_<event>Event(...)`), never through `mop/MonitorWrappers.java` — the wrapper file covers only merged `after` advices, and the harness must replay `before` advices (`MessageDigestSpec.reset`) and inline-woven events too — because the two snapshots of one comparison need not share an event alphabet — E4 renames `c1`→`c2` and deletes `reset`, and the archived set's `TrustManagerFactorySpec` has `i1`/`i2` where the seed has `init`.

## Data Flow

`.mop` (`jca_android`, writing `__EVENTNAME` where the envelope needs `ev=`, and allow-lists transcribed from api30) → rv-monitor generator (G) → `MultiSpec_1RuntimeMonitor.java` (event body: `__EVENTNAME` expanded to the literal `"g3"`, so `addError(new ErrorDescription(UnsafeAlgorithm, spec, __LOC, "v=1 code=TRUSTMANAGERFACTORY-ALG-01 ev=init …"))`; `@fail`: `__EVENTNAME` expanded to `RVM_eventName()`, the per-class helper that decodes the monitor's own last-event value per shape and indexes the event-name table, composed before `__RESET`) → dexlib2 weaver (wrappers unchanged; `advicesExcludedByArity` counted into the results JSON) → device → `RVSEC: spec,class,cls,method,loc,type,v=1 …` → `logcat_parser` (Format 2 by structure; envelope → fields; counters) → `RvErrorLog` (`unique_msg` 7 parts) → `result_processor` (`errors.csv` 13 columns) → `aperv_tool.analysis.violations` (13-column header; envelope) → E0 baseline / campaign analysis. In parallel: generated monitor + `.mop` sources + `generated/api30/*.cryptsl` → gates (pytest); two set snapshots → harness (JVM) → `evidence/harness/`.

## Risks / Trade-offs

- [E1 and E4 edit the same `.mop` files] → E4 starts after E1 is complete; inside E4 one owner per file; the message-property gate holds the `codes.csv` bijection and the message-vs-allow-list agreement across E4's transcription.
- [The generator serves all 191 `.mop` files, not only `jca_android`] → group G is additive (a new macro and a new table; no existing emission changes), and its acceptance regenerates `jca` and diffs against the frozen control, where the only admissible differences are the new table, the `RVM_eventName` helper and the lock framing (D-14) — no expanded macro, since the frozen `jca` has no `__EVENTNAME`. One control suffices precisely because the edit is global: any set derived from `jca` drives the same emitter paths, so a second regeneration — of the archived `jca_android_bug_predicate`, which this change regenerates nowhere — would repeat the measurement rather than extend it. The 11 `generic` files that do not compile today stay broken for their own reason and are not a regression signal.
- [Group G blocks E1, and no other group owns `rv-monitor/rv-monitor`] → G is dispatched in wave 1 alongside E0/S/E2/E3/EV; it is bounded (three substitution sites, one table, one helper, two reserved names, the dispatcher framing of D-14, one regeneration script and one control) and its own tests do not need a device or a full campaign.
- [`CipherSpec` sits at the generator ceiling with 17 events and no re-budget in this change] → every `CipherSpec` task declares its event count after the edit; adding an event requires removing one, and the transcription of the api30 Cipher catalogue lands in the new Java utility class, not as new events.
- [The transcription silences accusations the published analysis counted] → that is the point, and it is exactly why it must be measured: the harness runs before/after on every touched file once EV has landed (task 2.14 — S and EV share wave 1, so the evidence is produced after both, before E4 starts), and the conformance record names, per specification, which api30 clause each allow-list came from. The 11,409 events / 84 misuses that stop being reported are a declared consequence, not a regression, and so are the 5,892 `MessageDigestSpec` rows the api30 rule's admission of `MD5` and `SHA-1` silences (D-10), and any report comparing counts across `jca`, the archived `jca_android_bug_predicate` and `jca_android` carries that caveat.
- [Literal transcription without normalisation would be inert] → the alias table and the case-insensitive comparison are part of the same tasks as the transcription, not a follow-up; G-CONF fails an alias row with no source pointer. Normalisation is **not** implemented by expanding the allow-lists — that would make the lists unequal to the api30 clauses and leave G-CONF nothing to compare — but by a new utility class in `rvsec-core` that each `jca_android` check names (D-10). It is new shared code, so INV-INS-112 applies and is satisfied the same way the Cipher tables are: no `jca` specification names the class, so the frozen set cannot observe it, and nothing selects between tables at runtime.
- [The predicates are carried over, so no accusation is lost to them] → the 11 accusers that an earlier revision of this design would have deleted (7 total, 1 partial, 3 provenance) keep their events and their report sites. The three provenance checks remain inoperative on Android (`GENERATED_KEY` is never set by `AndroidKeyStore`, Tink or `KeyGenParameterSpec`; 11,620 events / 80 misuses / 25 apps), which is a reason to distrust their verdicts and record that, not a reason to delete them inside this change.
- [Not replaying gh101's 94 hunks leaves known automaton defects in the successor set] → accepted and bounded: the six structural repairs of D-1 are the subset confirmed against the api30 rules, the nine inherited divergences the frozen monitor proves are entered as measured-not-repaired rows (D-1, task 8.12), and the harness plus the CrySL-aware G-2 are what a follow-up would use to take the rest with evidence. The alternative — replaying repairs whose set was judged 22/22 REPROVADA — imports defects the gates cannot attribute.
- [Not filtering by arity leaves the merged wrappers firing incompatible advices] → accepted, and now visible: `advicesExcludedByArity` is published per run, over a domain of 48 advices that D-6 states explicitly so the number is not read as a fraction of 115.
- [G-2b′ flags deliberate idioms] → allowlist with reasons; a hit is a question. The Form-B residue (13 specifications per `frozen_set_debt.md:246`; its own enumeration yields 14–15 — the count is not authoritative) stays recorded, not gated.
- [The identity change creates two eras of every dedupe number] → declared, measured (must be non-zero on the harness corpus of task 6.9; zero by construction on comp162; reconfirmed on the 10.4 logcat); reports carry the era.
- [The static-analysis path still reads `jca` for every set] → `rv_static_analysis/config.py:200-207` defaults `mop_dir` to `resources/jca` and `get_static_analysis_config` passes no set (audit G12, `juizglobal_relatorio.md:234`) → task 10.0 makes `get_static_analysis_config()` pass the directory `get_monitored_operations_config()` resolves for the set — one mapping, not two — before the device task runs, and 10.4 records the directory the static analysis used.
- [The JSE agent's monitor is generated from `jca` at build] → `rvsec-agent/pom.xml:94-111` regenerates `rvsec-agent/src/main/java/mop` unless `-DskipMopAgent=true`, which every acceptance build of this change passes; the generated `MultiSpec_1RuntimeMonitor.java` there is gitignored (`mop/.gitignore`), so there is no committed source to diff against — task 3.9 diffs the regenerated file against the frozen control (`results/gh101_group8_jca_frozen_control/monitors/`, generated from the same `jca`) and records it once.
- [Consumers regexing free text break] → consumer matrix names each; the article scripts are declared frozen (they read the published dataset, which does not change).
- [Two monitor shapes carry the last event differently — `pairValue`/`getLastEvent()` in 15 classes, returning `idnum + 1` (`0` before any event); the inherited `RVM_lastevent` field plus inherited `getLastEvent()` in 8, returning `idnum` (`-1` before any event)] → the handler expansion calls `RVM_eventName()`, a per-class helper emitted where the shape is known, which reads `this.getLastEvent()` and decodes it per shape (D-4); the red test of task 3.1 covers one specification of each shape (`CipherSpec` or `SecretKeySpecSpec` for the atomic one, `TrustManagerFactorySpec` or `HMACParameterSpecSpec` for the non-atomic one — `TrustManagerFactorySpecMonitor` extends `AbstractSynchronizedMonitor`), and the fail-closed check catches any path that leaks an unexpanded `__EVENTNAME`.
- [E1's envelope is self-contradicting on the nine guard-on-field sites for an object with no observed `getInstance` — `val='SHA-256' exp='…SHA-256…'`] → E1 declares the case (a `conformance_record.csv` row and one harness trace per site), the message gate and the harness report flag `val ∈ exp`, and the repair — guard on the bound argument or getter — is E4 task 8.16 under harness measurement, expected class `removed` only for those traces (D-2); the same rule moves the `g4` revival (8.14) and the `KeyPairGeneratorSpec` `__RESET` (8.15) out of E1, so E1's acceptance stays harness `unchanged`.
- [The `KeyManagerFactorySpec` 296 rows have two candidate causes the record cannot separate] → E1's `ev=` is what separates them; the harness reads it; no gain is credited to E2 for those rows.
- [Device validation] → one task, four APKs from the published campaign (`com.owncloud.android_48000100`, `eu.opencloud.android_9`, `de.luhmer.owncloudnewsreader_196`, `com.etesync.syncadapter_20700` — the ones gh101 task 8.1 used), via `rv-experiment run`, never by hand; the change is complete without it being green, but not without it being run and its result recorded.
- [The control the tests read is unversioned — `results/gh101_group8_jca_frozen_control/**` is gitignored, and `./clear.sh --clean-results` removes it] → every test that reads it skips with a named reason (`pytest.skip("control directory absent: <path>; regenerate per data/gh104/README.md")`) and **fails** — does not skip — when the directory exists but its sha256 manifest disagrees; task 3.0 writes `data/gh104/README.md` with the regeneration recipe (the unmodified generator at the pre-3.2 commit recorded there, over `resources/jca`), and the manifest covers the generated `monitors/` files only, by name, since `mop/MonitorWrappers.java` is a product of the instrumentation step while the descriptor `MultiSpec_1MonitorAspect.json` is emitted by javamop `--emit-descriptor` in the generation run and is covered. **There is one control, not two**: the generator edit is global to all 191 `.mop` files, so regenerating `jca` exercises the same emitter paths that a second control derived from it would, and the archived `jca_android_bug_predicate` is regenerated by no task. E0 does not compute a second manifest for comp162 either: it cites the existing pin `modules/aperv-tool/tests/fixtures/cmp162_manifest.json` (465 entries, the 8 `errors.csv` among them) and its baseline test skips with a named reason when comp162 is absent.
- [gh56-smoke monitors predate the freeze] → oracles are always `results/gh101_group8_jca_frozen_control/monitors/` (transition tables identical to gh56-smoke; `KeyManagerFactorySpec.init` guard polarity differs there).
