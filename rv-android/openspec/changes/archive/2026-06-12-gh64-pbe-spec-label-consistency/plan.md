## Context

The spec name that appears in result CSVs is **the literal string each `.mop` handler
passes to `ErrorCollector.addError(...)`** — it is not derived from the spec block name.
Two JCA specs are internally inconsistent about that label, so the same spec can surface
in collected data under two different names depending on which violation fired:

- **`PBEKeySpecSpec.mop`** — 6 `addError` sites, **two labels**. The constructor-sequence
  events `f1`/`f2` emit `"PBEKeySpecSpec"`; the constraint/sequence-violation handlers
  `err1`/`err2`/`err3`/`@fail` emit the short form `"PBEKeySpec"`. The 4 short-form sites
  are exactly the ones that fire on *realistic* misuse (`iterationCount < 10000`,
  non-randomized password or salt), so a real violation is *more* likely to carry the
  short label than the block name.
- **`PBEParameterSpecSpec.mop`** — both `addError` sites (`c3` UnsafeAlgorithm, `@fail`)
  emit `"PBEParameterSpec"`. The block name `PBEParameterSpecSpec` is never emitted.

**Why it matters.** Impact on the current 169-APK article dataset is zero — no PBE
violations occur there, so the venn join is unaffected. But it is a latent data-join
hazard: a future experiment with a genuine PBEKeySpec constraint violation would emit
`"PBEKeySpec"`, which silently fails to join against any mapping keyed on
`"PBEKeySpecSpec"`. Closing this at the source removes the trap before it can bite.

**Decision (recorded in issue #64 discussion).** Canonicalize on the **spec block name**
(`PBEKeySpecSpec`, `PBEParameterSpecSpec`) — the unambiguous identity of the spec, and
already the convention used by 2 of the 3 rows in `cc_rv_mapping.csv`. The CSV
reconciliation is deliberately **out of scope** here and tracked as a separate follow-up;
this change fixes only the `.mop` source so the bug stops being produced.

**Not in scope / do not touch.** `SecretKeySpec.mop` and `SecretKeySpecSpec.mop` are two
distinct, internally-consistent specs (monitoring `javax.crypto.SecretKey` and
`javax.crypto.spec.SecretKeySpec` respectively). This is not truncation — leave them as is.

## Scope

Three hand-maintained `.mop` source copies each carry the identical drift and each must be
fixed (otherwise a rebuild from a sibling copy reintroduces it). Build output under
`rvsec-mop/target/classes/jca/` is regenerated by Maven and must **not** be hand-edited.

**Generated artifacts (excluded).** The JavaMOP toolchain lowers `.mop → .rvm → .aj`. The
`.rvm` files are **gitignored** (`*.rvm` in `rvsec-mop/.gitignore`) generated intermediates,
not tracked source — git tracks only the `.mop`. Any `.rvm` present on disk is stale local
output that will be regenerated (corrected) from the fixed `.mop`; do not hand-edit them,
same as `target/classes/`. A rebuild/regenerate of monitors is what propagates the fix to
the running AspectJ monitors — flagged here for whoever next regenerates.

## File Inventory

All trees are under `/pedro/desenvolvimento/workspaces/workspaces-doutorado/workspace-rv/rvsec/rvsec/`.

The edit is a literal token replacement of the **quoted** short-form label. Because the
closing quote disambiguates, replacing the quoted token `"PBEKeySpec"` never matches inside
`"PBEKeySpecSpec"` — the substitution is safe to apply globally per file.

### `PBEKeySpecSpec.mop` (all 3 copies)

Replace `"PBEKeySpec"` → `"PBEKeySpecSpec"` at the 4 short-form sites (handlers
`err1` UnsatisfiedConstraint, `err2` UnsatisfiedConstraint, `err3` UnsatisfiedConstraint,
`@fail` InvalidSequenceOfMethodCalls). The `f1`/`f2` sites already emit `"PBEKeySpecSpec"`
and are unaffected. Canonical-source line anchors (Group A): 49, 57, 65, 78.

### `PBEParameterSpecSpec.mop` (all 3 copies)

Replace `"PBEParameterSpec"` → `"PBEParameterSpecSpec"` at the 2 sites (handlers
`c3` UnsafeAlgorithm, `@fail` InvalidSequenceOfMethodCalls). Canonical-source line anchors
(Group A): 49, 56. Note: the `import javax.crypto.spec.PBEParameterSpec;` and the
`PBEParameterSpec` type references in event signatures are Java type names, **not** label
strings — they must NOT change. Only the quoted string literals inside `addError(...)` change.
