# Proposal: gh109-crysl-coverage

**GitHub Issue**: #109
**Track**: FF SDD
**Predecessor**: gh105 (`gh105-predicate-wiring`), which fixed the predicate substrate and re-anchored the set on the sole expert oracle (D-16) but deliberately kept the seed's coverage boundary ("no new accusation classes"). This change removes that boundary.
**Reference material**: the five external analyses `docs/analise_gh105_{gemini3,glm53,gpt5,grok4,opus5}.md`, used strictly as *candidate generators* — every claim adopted below was re-verified in this session against the primary sources (expert rule, live `.mop`, generated monitor, api30 jar via `unzip -l`) before selection; claims that failed verification were dropped, and several were corrected in the process (e.g. the B1 splitter repair is not the advertised one-liner, and the Mac/Signature two-arg gap migrates the accusation instead of silencing it).

## Why

The master question of the `jca_android` set — *is everything the expert CrySL oracle covers also covered by MOP?* — currently answers **no**: of the 49 rules in the pinned oracle (`RVSec-replication-package/tools/rules/`, sha256 `d7bcc019…`), only 22 have a paired `.mop`. The 27 absent rules leave 6 required predicates with no possible producer (`preparedRSA`, `preparedDSA`, `preparedEC`, `preparedOAEP`, `preparedAlg`, `generatedManagerFactoryParameters`) — and the consequence measured this session is sharper than "every read answers NOT_OBSERVED": **no site reads them at all**. The consuming specifications deliberately left the read closed *because the producer did not exist*, and both recorded the condition that would open it — `KeyPairGeneratorSpec.mop:135-141` ("*what would close it is a `.mop` for `DHParameterSpec`*", its `init3`/`init4` bodies empty) and `TrustManagerFactorySpec.mop:135-141` ("*an `else if (arg instanceof ManagerFactoryParameters)` would cost three lines... an accuser that can answer NOT_OBSERVED and nothing else*"). This change removes that premise, so it also owes the reads. The 27 absent rules further leave whole misuse classes mute (password→key via `SecretKeyFactory`, weak curves via `ECGenParameterSpec`, `KeyAgreement`, TLS configuration via `SSLEngine`/`SSLParameters`). Independently, verification confirmed 9 defects in the existing specs, including a value clause whose violation is total silence (`DHGenParameterSpecSpec`), an ORDER false negative (`CipherOutputStreamSpec` accepts construct–flush–close), and a value false positive against the oracle itself (the 8 `PBEWithHmacSHA*AndAES_*` families `Cipher.crysl:90-105` admits and the normalizer accuses).

## What Changes

- **Coverage parity**: every one of the 49 expert rules ends in exactly one of **three** terminal states — *covered by a `.mop`*, *N/A-by-platform adjudicated* (`Cookie`: `javax.servlet` absent from api30; `DSAGenParameterSpec`: class only exists from API 35), or *N/A-by-value adjudicated*. An **oracle defect is an attribute of the rule's row, never its destination** (D-21): the three verified defects — `preparedOAEP` clause vacuous at `Cipher.crysl:140-141`, `SSLEngine.crysl:12` referencing the undeclared label `cp1`, `KeyAgreement.crysl:31` referencing `g2` where `gs2` is meant — are recorded in `divergence_record.csv` and never edited upstream, and their rules are transcribed by evident intent and end *covered*, with the divergence row as warrant in the matrix's `oracle_defect_row` column. Verified viability census: **14 trivial** new specs (`ORDER = Con` parameter/producer classes; the one exception is the interface rule `Key`, `ORDER = GetEnc*`), **7 medium** (short ORDER), **3 complex** (`KeyAgreement`, `SSLEngine`, `SSLParameters`), plus `PasswordAuthentication` adjudicated recorded N/A-by-value (class exists, but both constraints are static-analysis predicates the instrument cannot evaluate at run time, and `generatedPasswordAuthentication` has no consumer among the 49 — a specification for it would monitor without a verdict surface. The earlier third leg, "the ORDER admits every trace", is withdrawn as imprecise: `Con, (GetPassword | GetUserName)*` does refuse a `getPassword()` on an unobserved construction; what that ORDER would still accuse is recorded with the adjudication instead of being assumed away — INV-INS-156).
- **The 6 producer gaps close, and the unblocked reads open** (D-24): the trivial group closes five of the six producer gaps and `preparedAlg` closes with the first two medium specs. A seventh gap, of a second shape, closes earlier and in G1: `generatedMessageDigest` is ensured by a rule that *is* paired — `MessageDigest.crysl:46` — whose `.mop` never wrote it, so the enumeration over absent rules could not see it and the ledger hides it under `unmonitored-consumer` until the two rules that read it (`DigestInputStream`, `DigestOutputStream`) gain their specs. Task 1.3(b) supplies the write, before G3 opens those reads. Four of the eight predicates INV-INS-151 counts then gain a reader from the new specifications themselves (`preparedEC`, `preparedDH`, `preparedAlg`, `preparedOAEP` — read by 3.1 and 4.3) and `preparedKeyMaterial` already has one. The remaining three — `preparedRSA`, `preparedDSA`, `generatedManagerFactoryParameters` — would end the change *written by a new specification and read by nobody*, which is the very argument that made `PasswordAuthentication` N/A-by-value. Group G1b therefore opens the three read sites that are structurally free: the four guarded clauses of `KeyPairGenerator.crysl:35-38` in `init3`/`init4`, and `generatedManagerFactoryParameters` in `KeyManagerFactorySpec`/`TrustManagerFactorySpec` over the `arg` those events already bind. The one read that cannot open is recorded, not silently dropped: `Cipher.crysl:136`'s `preparedAlg[params, alg(transformation)]` needs a binding of `params`, which `CipherSpec`'s fused `i2` (`args(mode, key, ..)`) does not carry and a new event cannot supply — `CipherSpec` is at 17/17, the generator ceiling.
- **9 verified repairs to existing specs** (each confirmed against the three sources this session): (R1) `DHGenParameterSpecSpec` — `condition()` fused into an accusing body + new CONSTR code (violation is currently total silence); (R2) `KeyPairGeneratorSpec` — `initError2` twin for `initialize(int, SecureRandom)`; (R3) `MessageDigestSpec` — value check in `d1`/`d3` (the 2-arg `getInstance` + direct `digest()` route emits ORDER only), carrying with it the `generatedMessageDigest` write `MessageDigest.crysl:46` ensures and the specification never made (task 1.3(b), see the producer bullet below); (R4) `CipherOutputStreamSpec` — `ere` no longer lets `fl` satisfy the `+` (`c1 fl cl` is accepted today; the rule rejects it); (R5) `SecretKeySpec.mop` — `SecretKey+.getEncoded()` so static-type `SecretKeySpec` receivers weave (the predicate bridge currently never fires for them); (R6) `CipherSpec.mop:177` — the `GENERATED_KEY` read splitter moves to `CipherTransformationNormalizer.alg` (alias-resolving), plus the ratified value decision that `AES_128`/`AES_256` compare equal to `AES` in the key×transformation check; (R7) `CipherTransformationNormalizer.isValid` admits the 8 `PBEWithHmacSHA{224,256,384,512}AndAES_{128,256}` families the oracle admits (CBC/PKCS5 forms); (R8) `KeyGeneratorSpec.mop:215` — the producer writes the canonical algorithm name into the predicate (raw spelling currently breaks propagation silently); (R9) `IvParameterSpec.mop` — `len > 0` per `IvParameterSpec.crysl:19` with an accuser on the reachable violated branch (`len == 0` currently passes *and* prepares the IV).
- **Android ports, deliberate and recorded**: disposition of the platform-dead `HMACParameterSpecSpec` (its subject class exists in no Android API level); BouncyCastle alias rows for the KeyStore service family; the TLS-default-per-platform note stays as the platform-value departure it already is. **AndroidKeyStore/`KeyGenParameterSpec` stays explicitly out of scope** — it has no expert rule; it seeds its own future issue.
- **Records and censuses**: the verified stale-record corrections (README site census 115→125 and its sibling scalars; `constraint_table.csv` verdict cells and seed-resolved `mop_line` pointers; `predicate_graph.csv` reasons (the `preparedPBE` falsehood and the stale `.cryptsl` pointers — **69 of its 76 rows**, measured, not the 7–8 first estimated); `predicate_ledger.csv` `preparedHMAC` contradiction and the `SecretKeySpec` chain rows; `PREDICATE_ALIASES` unfusion; the `next1`/`next3` alphabet-map decision; the freeze recipe, whose `LC_ALL=C` proposal is **withdrawn — measured, the recipe as written already reproduces `d7bcc019…` and `LC_ALL=C` breaks it**), and the enumeration constants the new files break (gh106 `Corpora`/`MopLiftCorpusTest`/`CalibrationTargets`, G-PARAM's pinned 24, G-ORDER's pinned skip set).
- **Not reopened**: the `KeyPair` mandatory constructor (adjudicated in gh105 task 11.6), the `SSL`-accused/`TLS`-admitted decision (D-15), and the two-argument-guard family residue registered in gh105 task 10.8(a) / divergence row F7 (`MessageDigestSpec` `g2`/`g3`, `SignatureSpec` `g2` and kin — deliberate deferral: the value accusation migrates to the init events, it is not silenced; R3 changes only `MessageDigestSpec`'s consumption route, the guards stay deferred).
- **Lighter execution protocol than gh105** (this is a process decision, not a gate change): records are re-emitted per group batch instead of per hunk; the differential harness runs at fixed checkpoints (after the repairs group and at final verification) instead of per task; the oracle is already pinned, so no re-derivation phase exists. All existing gates stay in force and green.

## Capabilities

### New Capabilities

(none — coverage parity extends the existing runtime-verification pipeline contract; no new spec domain is introduced)

### Modified Capabilities

- `instrumentation`: the monitor-generation contract changes — the specification set's coverage boundary moves from "the 22 rules the seed covered" to "all 49 expert rules, each with an adjudicated terminal state"; new specs follow the gh105 substrate rules (predicate reads in event bodies, writes at the rule's ORDER acceptance point, `PredicateStore` mechanism, ≤17 events per spec); the 9 repairs change what is accused at the verified sites (each carries its divergence-record rows and re-pinned censuses).

## Impact

- **Java (rvsec reactor, sibling tree)**: `rvsec/rvsec-mop/src/main/resources/jca_android/` (24 new `.mop`, 10 edited `.mop` — the eight of R1–R6/R8/R9 plus `KeyManagerFactorySpec` and `TrustManagerFactorySpec` from G1b, `KeyPairGeneratorSpec` being edited by both R2 and G1b — and `codes.csv` rows for every new accusation site); `rvsec/rvsec-core` (`CipherTransformationNormalizer` PBE branch + `AES_128/AES_256` equivalence; **`Property.java` gains the ~14 enum constants the new specifications write**, because the whole `PredicateStore` API is enum-typed and there is no string path — `ExecutionContext`, `CipherTransformationUtil` and the frozen `jca/` tree stay byte-identical); `rvsec-crysl` test constants (`Corpora.java:28`, `MopLiftCorpusTest.java:118,129`, `CalibrationTargets.java:69` — these run in CI).
- **rv-android**: no Python module changes behavior. `data/jca_android/` records move (divergence, predicate graph/ledger, alphabet maps, gate allowlist, alias table mirror), and `tests/parity` pinned censuses are re-pinned where they enumerate the set (G-PARAM 24→N, G-ORDER skip set, placement census).
- **Oracle (read-only)**: `RVSec-replication-package/tools/rules/` stays the sole, pinned oracle; its 3 verified defects (with an anomaly note and a notation-semantics note — D-21's five narrative rows) become `divergence_record.csv` rows, never upstream edits.
- **Out of scope**: campaign consolidation rules (NOBS families, junction buckets), the ase-journal article, the weaver path, gate retirement (#107), AndroidKeyStore specs (future issue), Network Security Config/cleartext (static-analysis domain, not RV).
- **FRs/NFRs**: FR01-FR03 (monitor generation pipeline), NFR06 (measurement integrity), NFR07 (reproducibility).
