## Why

GitHub Issue: #56.

The `rvsec-instrumentation-dexlib2` pipeline emits `invoke-static` instructions to the JavaMOP monitor with **register arguments in the wrong order** whenever an advice targets a constructor with a `returning(...)` binding. The Android Runtime (ART) verifier rejects the generated bytecode with `java.lang.VerifyError`, aborting the process before the monitor can observe the violation. Measured impact on the 2026-05-08 campaign: **2.202 / 18.267 task-runs (12,1%)** carry at least one `VerifyError`, distributed across **116 / 190 distinct APKs (61,1%)**. The smoke oracle on `cryptoapp.apk` captures only **3 / 8** expected violations — every violation routed through a constructor advice with `returning` binding is silently lost.

Two confirmed root causes interact (validated in source on 2026-05-14, see `docs/20260514_erro.md`):

1. **`PointcutMatcher.buildCallMatch`** treats `invoke-direct <init>` as a static invoke (`baseOffset = 0`), shifting every user-visible argument binding by one register and losing the receiver (`<this>`) reference.
2. **`MonitorInvokeBuilder.resolveBindings`** hardcodes the `returning(name)` parameter to literal `0` (register `v0`) instead of resolving it to either the freshly-constructed instance (constructor advice) or the destination of the trailing `move-result*` (non-constructor advice).

The bug entered with the dexlib2 pipeline in gh52 and was not caught because: (a) `DexWeaverConstructorAdviceTest` exercises constructor advice **without** a `returning(...)` binding; (b) `MessageDigest` is routed through `WrapperEmitter` (correct), masking the failure in the only smoke specimen; (c) the Layer 3 oracle gate was registered as "diagnostic", not blocking. The failure mode is structural: it affects all 12 JCA constructor-typed specs (`SecretKeySpecSpec`, `IvParameterSpecSpec`, `PBEKeySpecSpec`, `GCMParameterSpecSpec`, `KeyPairSpec`, `DHGenParameterSpecSpec`, …) and biases RQ3 of the ASE journal paper (violation origin in app code vs libraries) to ~0% in the new campaign versus 33,91% in the original ICST measurement. A meaningful portion of that gap is an instrumentation artifact rather than an ecosystem evolution.

## What Changes

- Fix `PointcutMatcher.buildCallMatch` to distinguish constructor invokes (`invoke-direct <init>`, `baseOffset = 1`, `targetRegister = regs[0]`) from truly static invokes (`baseOffset = 0`, `targetRegister = -1`). The constructor's `<this>` register MUST be captured as the receiver / "returning" reference, because the freshly-constructed instance is the semantic return value of `<init>`.
- Fix `MonitorInvokeBuilder.resolveBindings` to resolve the `returning(name)` binding to a real register: the constructor's `targetRegister` for `invoke-direct <init>`, or the destination of the trailing `move-result*` for non-constructor advice. The literal `0` fallback is removed entirely.
- Extend `PointcutMatcher.buildCallMatch` to peek at the instruction following the matched invoke and, when it is `move-result`, `move-result-object`, or `move-result-wide`, record the destination register under a synthetic `$return` binding inside `Match.argBindings`. The synthetic key is consumed by `resolveBindings` for non-constructor advice with `returning(...)`.
- Introduce a named-binding contract spanning the five emitters (`Before`, `After`, `AfterReturning`, `AfterThrowing`, `StaticInitialization`): the bindings `target(name)`, `args(n1, n2, …)`, `returning(name)`, `throwing(name)`, and the synthetic `$return` MUST resolve to registers consistent with the runtime type expected by the monitor signature. Type-aware validation lives in unit tests, not in the emitter.
- Add a parametrized JUnit5 test class `MonitorInvokeBindingTest` covering the cross-product `{Before, After, AfterReturning, AfterThrowing, StaticInitialization} × {constructor, virtual instance, static} × {args, target, returning, throwing}` and asserting **register-to-type correspondence** against the emitted monitor signature — not only instruction shape — with the "expected type per register" sourced from a hand-written fixture table (independent of any helper that re-parses the monitor signature; closes the gh52-smoke gap). Extend `DexWeaverConstructorAdviceTest` with `returning(...)` scenarios for both `SecretKeySpec.<init>` and `IvParameterSpec.<init>`.
- Promote the `validator/oracles/cryptoapp-oracle.yaml` Layer 3 oracle from "diagnostic" to **mandatory gate** in `scripts/run_phase5_validators.sh`, **conditionally on `cryptoapp.apk` appearing in the dex result set** (see D4 / INV-INS-73). When cryptoapp is in scope, a non-zero deviation from the 8 expected events MUST fail the validator via the existing `Report(passed=false) → exit 1` contract — no new exit code is introduced (see D6). When cryptoapp is out of scope, Layer 3 stays diagnostic and the orchestrator exits zero on deviation.
- Record an Architecture Decision Record (ADR) capturing the named-binding contract for dexlib2 advice emission, and a risk register entry for the re-run cost trade-off.
- Document the four new invariants in `openspec/specs/instrumentation/spec.md`: `INV-INS-70` (constructor offset), `INV-INS-71` (returning-register resolution), `INV-INS-72` (`$return` synthetic binding), `INV-INS-73` (cryptoapp oracle-gate-mandatory rule).

**Not changed** (explicitly out of scope; deferred to follow-up change `gh<N+1>-instr-pointcut-completeness`):

- Overloads not enumerated in `expandCallTarget` (`Mac.update([B)V`, `SSLContext.init`, `SecureRandom.setSeed(J)`, …).
- Kotlin `suspend` / CPS state-machine detection (INV-INS-61 residual).
- `Format35c` for registers `>v15` (INV-INS-32 residual; mechanic is orthogonal — register escalation, not binding resolution).
- `InheritanceResolver` Phase 2 expansion for custom Cipher subclasses (`wrappersAliasedToSubtype` residual).
- Building a centralised `rv-validator` Python module or a `.github/workflows/` CI pipeline for the oracle gate.

## Capabilities

### New Capabilities

None. This change does not introduce a new domain capability; it corrects the bytecode-emission contract of an existing one.

### Modified Capabilities

- `instrumentation`: the dexlib2 variant gains a normative named-binding contract for advice emission. Four new invariants are added (INV-INS-70..73) covering constructor offset, returning-register resolution, the `$return` synthetic binding, and the cryptoapp oracle gate. Existing INV-INS-66 (inline-vs-wrapper partitioning) is referenced — the named-binding contract is the precondition that allows the inline path to handle constructor+returning safely.

## Impact

**Affected Java modules** (under `rvsec/rvsec-android/rvsec-instrumentation-dexlib2/`, the Maven aggregator outside the `rv-android` uv workspace — same convention used by the gh52 archived spec):

- `pointcut-engine/src/main/java/br/unb/cic/rv/pointcut/PointcutMatcher.java` — `buildCallMatch` rewrite (lines 175-202): split constructor vs static, add `move-result*` peek.
- `advice-emitter/src/main/java/br/unb/cic/rv/emitter/MonitorInvokeBuilder.java` — `resolveBindings` rewrite (lines 141-194): introduce `resolveReturningRegister(match)`, delete the hardcoded `0`.
- `pointcut-engine/src/main/java/br/unb/cic/rv/pointcut/Match.java` — add a new immutable `boolean isConstructor` field (constructor + `Match.empty(pe)` factory updated accordingly); extend `argBindings` Javadoc to include the `$return` synthetic key. The existing `matchedAgainst` field (`PointcutExpression`, the parent type) stays unchanged.

**Affected tests**:

- `dex-mutator/src/test/java/br/unb/cic/rv/mutator/DexWeaverConstructorAdviceTest.java` — extend with `returning(...)` scenarios for `SecretKeySpec.<init>` and `IvParameterSpec.<init>` (the latter documented in `docs/20260514_erro.md:§2.4` as bug-affected).
- `advice-emitter/src/test/java/br/unb/cic/rv/emitter/MonitorInvokeBindingTest.java` (NEW) — parametrized cross-product covering all five emitters × constructor/virtual/static × all four binding kinds.
- `pointcut-engine/src/test/java/br/unb/cic/rv/pointcut/PointcutMatcherConstructorTest.java` (NEW) — direct unit tests on offset/targetRegister for constructor vs static invokes.

**Affected Python modules**: none required for correctness. The wrapper `modules/rv-instrumentation-dexlib2/src/rv_instrumentation_dexlib2/dexlib_instrumentation.py` is binding-agnostic.

**Affected scripts / validators**:

- `rv-android/scripts/run_phase5_validators.sh` — three changes:
  1. Parameterise hardcoded `rvsec-gh52-instr-dexlib2` paths (L38-44 for `THRESHOLDS`, `REPO_ROOT`, `VALIDATOR_DIR`) via script-relative derivation with env-var overrides; without this fix the script cannot run from this workspace.
  2. Conditionally append `--mandatory` to the existing `layer3 --batch` invocation (L114) when `cryptoapp*.apk` is found in `$DEX_DIR/instrumented_apks` (picocli subcommand topology — not a top-level CLI flag).
  3. Fail fast via `jq` if `plansSkippedUnresolvedBinding > 0` in `$DEX_DIR/instrument_results.json` when cryptoapp is in scope (closes the manual-check gap).
- `rvsec-instrumentation-dexlib2/validator/oracles/cryptoapp-oracle.yaml` — confirmed authoritative (8 events). No change to oracle content.

**FRs / NFRs**:

- FR01 (Monitor weaving): correctness of emitted bytecode.
- FR03 (Bytecode validity): post-fix, ART verifier MUST accept all instrumented APKs in the cryptoapp smoke.
- NFR03 (Coverage fidelity): violations routed through constructor advice are no longer lost — RQ3 measurements regain validity.

**Cross-module dependencies**: none. The fix is confined to the dexlib2 instrumentation variant. The `rv-instrumentation-core` ABC is unaffected; the `rv-instrumentation` factory is unaffected.

**Build artifacts**: `instr-cli.jar` rebuilt and re-deployed under `modules/rv-instrumentation-dexlib2/lib/`. The Dockerfile gate (gh53 D6) for `RUN test -f .../instr-cli.jar` already covers this — no Docker manifest change required.

**Experimental cost**: re-running the 2026-05-08 campaign on a **stratified 9-APK slice** (top-3 + median-3 + tail-3 by `VerifyError` count, single timeout, single repetition) is the minimum acceptance gate (~6 h GCP). The stratification is intentional — a pure top-10 selection biases toward hot-spots and misses tail patterns (`args(name)` unresolved, R8-obfuscated `<init>`, Tink/Okio internals) that may regress silently via `plansSkippedUnresolvedBinding`. Acceptance also requires paired pre-vs-post-fix delta on event count and coverage (post ≥ pre per APK) — "0 VerifyError" alone can mask a regression in exploration. A full re-run (190 APKs × 11 tools × 3 timeouts × 3 reps ≈ 85 h GCP on 4 VMs) is a separate decision documented in `RISKS.md` — the trade-off is RQ3 representativeness vs. ASE journal timeline.
