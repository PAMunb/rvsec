# Proposal: gh90-e3-decisive-run-setup

GitHub Issue: #90

## Why

The E3 thesis study must prove the chain *decision → action → MOP screen → violation*, and today that chain is broken at both ends. At the measurement end, only 2.06% [2.00; 2.13] of steps are causally attributable to MOP guidance — the sister change in the `ape` repository (`telemetry-proof-llm-efficacy`) fixes that by making the jar emit the missing per-step fields. At the **experimental-design** end, which is this change, the problem is different and cannot be fixed by any amount of telemetry: **the experiment has never had a control arm**. Every APE-RV run ever executed had MOP guidance switched on. Without a MOP-off arm there is no contrast, and therefore no claim about the effect of MOP guidance is attributable — however good the telemetry gets.

Three further defects bias the reading of whatever the decisive run produces. First, the direct/transitive axis of the scoring pipeline is noise: `[DM]` is 0 across all 181 apps of the corpus because `directlyReachesTarget` means 0-hop (only methods whose own body invokes JCA) while UI handlers delegate, so `mop_weight_direct=500` is unreachable by construction of the data and calibrating it measures nothing. Second, the LLM backend actually serving each run is not recorded anywhere, so a run's results cannot be tied to the model and sampling parameters that produced them. Third, `mop_activity_source_components` sits at its `false` default in the substrates that inherit it, suppressing the MOP-activity signal (measured effect: 20.0% → 85.0% of activities flagged on the subset40, 17.7% → 86.2% offline across the 181 apps).

The design decisions below were fixed by the project author on 2026-07-29 and are recorded in `docs/20260729_propostas_melhorias_e3.md` §0, which is the source of record for this change — **with four exceptions, all added on 2026-07-31 after the adversarial verification and decided here rather than there**: the coverage-dump parser (O3), the capture grace window, the pre-registered stratification with its declared expectation, and the clone-dependence declaration. A fifth, the RQ-C1 power probe, is decided here for the same reason and is described below. Each is tagged where it appears. They feed a decisive run (3 arms × 40 APKs × 1800 s × 1 rep = 120 runs, ≈ 8 h on 8 containers) that decides whether the LLM stays in the design at all.

## What Changes

- **A1 — the decisive run's arm set, enumerated.** The MOP-off arm is defined as `mop_data` **present** + `mop_weight_*=0` + `mop_frontier_weight=0` + `activity_trigger_enabled=false`. This specific shape is forced by two verified jar behaviours: leaving `ape.mopDataPath` set while the load fails **aborts the run** (`StatefulAgent.java:216-223`, INV-MOP-22), and removing `mop_data` altogether would also disable the generic WTG and frontier passes (`WtgPass:29` and `FrontierPass:35` both require `mopData != null`), turning the intended "MOP guidance off" contrast into "most of the navigation substrate off". The standing rule *sempre modo frontier* holds: `sata_mop_act_frontier` remains the substrate of every aperv arm.
  **This change also closes a gap in the record**: the decisive run's three arms are enumerated here for the first time, and named — (1) `mop_on_llm_off`, the shared reference; (2) `mop_off_llm_off`, isolating the MOP contrast; (3) `mop_on_llm_70`, isolating the LLM contrast. The ledger fixed the MOP-off arm's internal design but never wrote down the arm set, and the names matter beyond bookkeeping: the variant string is the resume identity key (`platform.py:308-318`) and the consolidation column key (`{arm}__{metric}`), so it must be decided before any manifest is generated. The names encode both factors, which is what makes each contrast readable straight off the results CSV.
  **The LLM dose of arm 3 is `llm_percentage=0.7`** — the dose is what fixes what "LLM on" means in the result, and its rationale is `design.md` D8.
- **A9 — offline clock ↔ logcat join**, as a utility of the `aperv_tool` package. Correlates the trace clock with `RVSEC:` violation lines to test the premise "reaching a MOP screen is enough to fire the monitor" — the premise on which the whole MOP-frontier mechanism rests. It also supplies the evidence for the deferred N5 decision (runtime logcat).
- **N6 — a direct/transitive axis that means something**, computed offline inside `_compact_static_analysis_json` (`modules/aperv-tool/src/aperv_tool/tools/aperv/tool.py:801-875`). The compaction step already loads the analysis JSON and rewrites it in memory before pushing to the device; it will additionally populate `listeners[].handlerReachesTarget` / `handlerDirectlyReachesTarget` from the document's own `reachability` section. Redefined semantics: **direct = the handler of *this* widget reaches JCA at any depth**; transitive = containment. Source `.apk.json` files are never modified, the static analysis is never re-run, and `rvsec-gator` is not touched. The consumer already parses both fields with precedence over its local join (`MopData.java:516-517,531-533`).
- **N4 — per-run backend provenance.** At the start of each run the tool queries `/v1/models` (it already holds `llm_url`) and records backend, model, and sampling parameters in the task output. Applies to any experiment, calibration and real alike.
- **B2 — `mop_activity_source_components` forced ON** in the arms that inherit the `false` default (`Config.java:159`).
- **B3 — `llm_snap_tolerance_px=150`**, property-only and **gated**: applied only when the jar in use contains the B1 dead-pair ban from the sister change. Without B1, a wider snap radius amplifies repeated dead taps instead of rescuing near-misses.
- **O3 — a versioned parser for the coverage dump**, as an offline utility of `aperv_tool` alongside A9's join. The sister change hoists the dump so that 333 of the 338 runs that lose it today keep it (`ape` design D9); without a consumer, that recovers data nothing reads — a grep for `UICOV` across the whole rv-android tree returns zero hits in `.py`. The parser SHALL operate at **Activity** grain (`UICOV-ACT`), because the per-state `UICOV` key embeds a JVM identity hash and is not comparable across runs (measured cross-replica Jaccard 0.000, mean/median/max), and SHALL tolerate a truncated final line as a partial dump rather than discarding the run.
- **Grace window for the capture, `+15 s` → `+45 s`.** `tool.py` gives the `adb` invocation `timeout_seconds + 15` before SIGKILL, and that ceiling is exactly where the lost dumps pile up: on runs that survive, teardown overruns the exploration budget by up to 12,991 ms with 32 runs stacked against the wall and nothing beyond it. Widening the window costs one line, touches no jar, and is complementary to the sister change's reordering rather than redundant with it — the reordering moves the dump earlier, this gives the whole chain room to finish. It is a **hypothesis, not a measurement**: the true teardown duration of the cut runs is unobservable by construction, which is what censoring means, so the change records it as such and the smoke reports what it actually cost.
- **N2 — measurement rule, not code.** Any future grounding measurement reports both centre distance and containment. Recorded in `design.md`; no script is created (the offline harness that would host one is frozen).
- **Pre-registered stratification, with its expected outcome declared.** UI toolkit (Compose / View) becomes a declared analysis axis of the decisive run, because in ~30% of Compose apps every activity is MOP-flagged, making `activity_has_mop` constant and leaving the MOP-guided arm with no contrast to exhibit there (`docs/20260730_compose_gator_substrato_estatico.md` §5.2). Verification on 2026-07-31 sharpened this from a caveat into a **prediction that must be recorded before the run**: across the ten `aperv` arms of iter0, all **22 of 22** Compose APKs are concordant on the binary outcome (`mop_unique > 0`), against 13 of 18 View. Under the same binary definition the whole-corpus concordance is 33/40 (35/40 among `aperv` arms), not the 25/40 that earlier drafts rested on — 25/40 is concordance on the *identity of the continuous value*, which is not the McNemar's concordancy set. The pre-registration's 2026-07-31 revision already retracts 25/40 on the same grounds and tabulates all three definitions, so the two documents agree. The stratum is therefore expected to contribute approximately **zero discordant pairs**, and a null there is absence of contrast in the instrument rather than evidence about the hypothesis. Declaring it in advance is what keeps that reading from being post-hoc.
- **Clone contamination of the subset, declared.** Eight of the 40 APKs are the same codebase — the six `info.metadude.*.schedule` apps plus `at.linuxtage.Eventfahrplan_1700028` and `ch.digitale_gesellschaft.winterkongress.schedule_118`, all declaring `mainActivity = nerd.tuxmobil.fahrplan.congress.schedule.MainActivity`. All eight are Compose, all eight are concordant, and all eight report `mop_unique = 8` in every iter0 arm. Six of them additionally share one byte-identical `.apk.json`. Any paired statistic over the 40 treats them as independent units when they are not; collapsing them moves the toolkit×outcome association from p=0.00091 to p=0.0135 (odds ratio 12.67 → 8.0) — direction and significance survive, the precision does not. The subset stays at 40 (author's decision, unchanged); what changes is that the dependence is stated wherever a paired test is reported.

- **RQ-C1 power probe, before committing the decisive run** (added 2026-07-31; design D9). The adversarial verification showed that the exact McNemar cannot reject at Holm α=0.025 with fewer than 7 discordant pairs, and the iter0 analogues predict 3–4 on both contrasts. No iter0 arm fixes the frontier substrate and turns MOP off — `ape:default` differs in 18 keys, not the 6 of the real contrast — so **nothing already recorded answers whether the RQ-C1 primary contrast has discordant pairs at all**. The probe answers that at ~1/5 of the full run's cost: the two RQ-C1 arms only, 40 APKs × 1 rep × 2 arms = 80 runs at **300 s** (not 1800 s), no SGLang. It is a design diagnostic, never an outcome: its results do not enter the confirmatory analysis under any circumstance, and it must be declared in the pre-registration §7 *before* it runs, or it is peeking on the pre-registered contrast. Reading rule and the author's decision branches are fixed in advance in `tasks.md` group 7.

Subset stays at the current 40 APKs — `bitbanana` does not enter (author's decision).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `aperv`: arm definitions and their configuration keys (A1, B2, B3); offline enrichment of the pushed static-analysis document (N6); per-run backend provenance in the task output (N4); the clock↔logcat join utility and its validation gate (A9); the coverage-dump parser at Activity grain (O3); the capture grace window (`+45 s`).

No other capability's requirements change. `analysis` is untouched: N6 consumes the `reachability` section that FR06 already specifies and rewrites only the in-memory copy the tool pushes, never the artifact the analysis produces.

## Impact

- **Modules**: `aperv-tool` (all code changes live here — variants, `_compact_static_analysis_json`, the new join utility, the preflight provenance query). `rv-experiment` and `rv-platform` are read-only consumers: they gain no new interface, and the arm set reaches them through the existing variant mechanism.
- **Requirements**: FR20 (per-tool variant system — the arms), FR06 (REACH analysis output consumed by N6), FR11 and FR13 (logcat capture and violation detection — the substrate A9 joins against), FR19 (external tool support), NFR03 (testability — the offline pytest layer), NFR06 (observability — N4 provenance).
- **Cross-repository dependency**: B3 is gated on the `ape` jar containing B1; the arm-3 contrast is only interpretable once the jar emits `pick_channel` and `activity_has_mop` (sister change items A4/A5). This change can be implemented and unit-tested independently of the jar, but the decisive run requires both halves. The new jar reaches the container by the same bind-mount the campaign scaffold already uses for `tool.py`, over the image's baked copy. In the other direction, the sister change's verification gate 17.4(a) exercises the MOP-off arm that task group 1 here defines, so that gate cannot be checked off before this change lands.
- **Dependency on a sibling change in this repository**: `INV-APV-26` (the `LLM_ARM_KEYS` guard that task 1.6 extends) is defined in `openspec/changes/gh88-cal-llm-control/`, which is **not yet archived**, together with INV-APV-27 and INV-APV-28. Two consequences to keep visible: task 1.6 rests on an invariant that is not yet normative, and the INV-APV-29…37 numbering used here is only contiguous if gh88 archives first. If gh88 is abandoned or renumbered, this change leaves a 26–28 hole.
- **Two invariants this change once cited across repositories describe a design that was never built**: `INV-BUILD-09` and `INV-BUILD-11`, which earlier drafts of INV-APV-34 and smoke gate 6.3 verified against, are defined only in `ape/openspec/changes/archive/2026-06-21-gh14-build-provenance-stamp/` — a change **archived without implementation** (`6b7b96f`, 2026-06-21), superseded by B-1 (build-ship-integrity), which makes a runtime banner redundant with build-time provenance. `ape-rv.jar` therefore carries no build stamp and emits no `[APE-BUILD]` banner; verified at `ape` HEAD `5dcf2259` — no `APE-BUILD` string under `src/`, no `BuildInfo*` file, no `git-commit-id` plugin in `pom.xml` — and `ape/openspec/specs/build/spec.md` stops at INV-BUILD-08. The B3 gate is verified instead against the installed jar's sha256, which the tool already captures (design D4). No action is required in the `ape` repository.
- **Data**: no schema migration. `.apk.json` corpora are read-only; iter0 recorded traces are read-only test fixtures.
- **Deadline**: none. The 2026-07-31/08-01 window originally recorded here was cancelled by the author; nothing in this change is descoped on schedule grounds.
