# Deferred-by-Design — gh62-aspectj-grammar-coverage (round-8)

**Purpose**: snapshot of every AspectJ construction the gh62 round-8 closure series explicitly does NOT implement, with the demand evidence (zero at the pipeline stage that would consume it) and rationale per entry. Matches one-to-one with matrix rows whose `Verdict ∈ {EXPLICIT-NO-OP, NOT-NEEDED}`.

**Frozen-snapshot tripwire**: SHA-256 of this file is committed to `rvsec-android/rvsec-instrumentation-dexlib2/grammar-tests/src/test/resources/deferred.snapshot.sha256` per design D7 (round-7 reformulation). `MatrixIntegrityTest.testDeferredDocumentIsFrozenPostArchive` reads both files and fails the build if they diverge (positive enforcement of the "frozen post-archive" property). Round-8 fix: the snapshot is generated in the same commit as the final `deferred.md` edit (see tasks §1.4), eliminating the round-7 race condition flagged by cross-LLM review.

**Round-8 redesign — absorption-aware demand**: round-7 framed scope by **source-level `.mop`/`.aj` demand**. Round-8 reframes scope by **pipeline-level demand** — the demand that actually reaches the dexlib2 instrumenter after the upstream stages (JavaMOP compiler, AJC, `coverage-weaver`) have absorbed everything they can absorb. The Three Empirical Audits Appendix at the bottom of this file documents the evidence base.

Concretely: a `.mop` source may declare 64 `condition(...)` clauses in `jca/`, but the `.aj` produced by the JavaMOP compiler contains **zero** — the condition logic has been folded into the corresponding `*RuntimeMonitor.*Event(...)` method body that the dexlib2 instrumenter already invokes. The round-7 closure §4.G (`ConditionGuardEmitter`, ~80 LOC) was attacking a construction the instrumenter never sees. Round-8 catches seven such closures.

**What is NOT here**: every construction with `DemandCounter ≥ 1` at the pipeline stage that consumes it ships in-change per design D9 (round-8 demand-driven absorption, post round-7 absorption-aware refinement). The round-6 `Fix-now`/`Follow-up` ledger buckets remain eliminated. AspectJ extensions outside the closed enumeration (`lock`/`unlock` per OQ3; per-clauses, ITDs, `declare warning/error/soft`, annotation-style aspects, generics in type patterns per OQ4) are NOT in the matrix and NOT here — they are AUSENTE-JUSTIFICADO in design.md.

## 2. Deferred-by-design (NOT-NEEDED)

`DemandCounter` returns zero at the pipeline stage that would consume the construction. There are two paths under this verdict and the matrix `Evidence` column distinguishes them:

- **Path α** — zero source-level demand AND no implementation. The construction does not appear in any of the four corpora at any stage.
- **Path β** — non-zero source-level demand in `.mop` and/or `.aj`, but absorbed by an upstream pipeline stage (JavaMOP compiler, `coverage-weaver`, AJC weaver, `MonitorRuntime` dispatch loop) before reaching the dexlib2 pipeline. Pipeline-stage demand at dexlib2 is zero.

For both paths, the Evidence column cites an enabled passing test asserting the absence of pipeline demand. For path β, the test additionally asserts that the upstream-absorbed equivalent input is produced (or absorbed equivalently) regardless of upstream source syntax. If a future corpus introduces non-zero **pipeline** demand for any deferred row, `MatrixIntegrityTest.testPipelineDemandCountsReproducible` fails the build (the matrix's pipeline-demand cell will diverge from the helper's output), forcing amendment via a new sub-change.

The 6+ cross-references to `docs/analise_sintese_macro.md` in proposal.md/design.md/tasks.md/this file are preserved (the file is regeneratable on the originating workstation); they should be read as pointers to the synthesis-of-record while this Appendix carries the empirical conclusions inline.

Summary:

### A.1 APK AJC-instrumentado real

**Target**: `results/gh53_smoke_ajc/instrumented_apks/cryptoapp.apk`, decompiled via `apktool d`.

**Question**: what does AJC actually emit in the woven bytecode for MOP advices, and for `Coverage.aj`?

**Finding**: 115/115 MOP advices in `smali/mop/MultiSpec_1MonitorAspect.smali` are trivial pass-through (`invoke-static *RuntimeMonitor.*Event(args_typed)`), with zero `thisJoinPoint`/`__STATICSIG`/`condition`/`Signature` references. Only `Coverage.aj` uses `JoinPoint.StaticPart` (via `ajc$tjp_N` static fields built by `Factory.makeSJP(...)` in each instrumented class's `<clinit>`). Implication: the round-7 closures targeting runtime-reflection-bearing constructions in MOP advices were attacking nothing — the JavaMOP compiler had already reduced them to pass-through calls.

### A.2 `.aj` gerado pelo JavaMOP

**Target**: `results/gh53_smoke_dexlib2/monitors/MultiSpec_1MonitorAspect.aj` (JCA-derived) and `results/gh53_smoke_dexlib2/monitors/Coverage.aj`.

**Question**: which AspectJ constructions survive the `.mop` → `.aj` compilation step?

**Finding**:
- `condition(...)` — **completely removed**. The MOP source `condition(isValid(transformation))` at `CipherSpec.mop:32` becomes `after (...) returning (...) : CipherSpec_g1(transformation) { MultiSpec_1RuntimeMonitor.CipherSpec_g1Event(transformation, c); ... }` at `MultiSpec_1MonitorAspect.aj:212-218` — the condition logic moved into the runtime monitor body.
- `__STATICSIG` — **zero occurrences** in the compiled JCA `.aj`.
- Named pointcuts — `Coverage.aj` declares two named pointcuts (`excludedPackages()`, `traced()`); if `Coverage.aj` were in-pipeline, §4.D would need to resolve them. Since `Coverage.aj` is absorbed (§2.2.1-D/F), §4.D is needed only for `BaseAspect.notwithin()` (§4.B's input). **Round-8 A-decision 2026-05-28**: NO schema change is required. Empirical inspection (`descriptor-reader/src/main/java/br/unb/cic/rv/descriptor/AspectDescriptor.java` + the production JSON fixture `MultiSpec_1MonitorAspect.json`) proved the existing `baseAspectExclusions: List<String>` field already carries the canonical twelve-entry expansion populated by `javamop.output.descriptor.DescriptorWriter#defaultBaseAspectExclusions()` — exactly the data §4.D / §4.B need. The early-round-8 plan to add a cross-repo `namedPointcuts: Map` field is RETIRED; §4.D consumes the existing field directly and fails closed on unrecognised names per round-8 G-decision (see proposal.md §"In-change closures" and design.md D11 for the full A-decision rationale).
- Construction inventory of the compiled `.aj`: `pointcut`, `before`, `after`, `after returning`, `call`, `target`, `args`, `!within`, `&&`, `||`, `!adviceexecution()`. **Nothing else**.

### A.3 `coverage-weaver` vs `Coverage.aj`

**Target**: `rvsec-android/rvsec-instrumentation-dexlib2/coverage-weaver/src/main/java/br/unb/cic/rv/coverage/*` and `rvsec-mop/src/main/resources/aspect/Coverage.aj`.

**Question**: is `coverage-weaver` semantically equivalent to `Coverage.aj`?

**Finding**: YES, and the equivalence is explicit in the module's javadoc:
- `CoverageWeaver.java:23-32` — "Semantically equivalent to the AspectJ rule in `Coverage.aj`".
- `SignatureFormatter.java:14-17` — "reproduces it byte-for-byte so the Layer-5 RVSEC-COV recall check comparing ajc output against dexlib2 output lines up without per-apk tweaks".
- `experimento-20260508/RELATORIO.md` §3.2 / §7.2 — the 190-APK production experiment ran `RV_INSTRUMENTATION_VARIANT=dexlib2` exclusively; all 2.78M coverage rows came from `mop.Coverage.log()` (the `coverage-weaver`-emitted runtime helper), NOT from `Coverage.aj`.

The implication is unambiguous: shipping the AspectJ runtime substrate (~600 LOC under `br.unb.cic.rv.aspectjlang.*`) + the `thisJoinPoint` binding emitter (~250 LOC) + the `execution(...)` emitter (~150 LOC) to support `Coverage.aj` would buy zero net capability. `coverage-weaver` already delivers the equivalent operational outcome with better thread-safety (`ConcurrentHashMap.newKeySet()` vs `HashSet<String>` in the aspect), better runtime cost (string-pool constant vs reflective `Method.getDeclaringClass().getName()` per call), and zero AspectJ runtime dependencies.
