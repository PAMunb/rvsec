## 1.7. Saturation Fix (BLOCKER for Group 5)

Fix saturation calculation so proactive backtracking works correctly on all screen sizes. Without this fix, `get_saturation_rate()` returns N/(N+2) at maximum — screens with fewer than 8 real actions can never reach the 80% `backtrack_saturation_threshold`. Depends on Group 1 only. Can run in parallel with Group 1.5.

- [ ] 1.7.1 Fix saturation calculation: in `DynamicStateGraph.get_or_create_state()`, compute `total_actions` excluding system actions (actions with `coordinates=None`). The visitor injects BACK and RESTART with `coordinates=None` — these inflate `total_actions` making max saturation = N/(N+2), never reaching 100%. Screens with <8 real actions never reach the 80% threshold. Fix: when computing `total_actions`, count only actions where `coordinates is not None`. The numerator already naturally excludes system actions (they are never recorded in `action_execution_counts`), so the implementation fix targets the denominator (`total_actions`) only. The visitor still injects BACK/RESTART for other consumers (e.g., action selection); only the saturation denominator changes. HOME is NOT in the strategy — no change needed. TDD: `test_saturation_reaches_1_0_all_non_system_saturated`, `test_back_restart_excluded_from_total_actions` (BACK/RESTART injected by visitor with coords=None do not inflate `total_actions`), `test_total_actions_excludes_system_actions` (explicit check that `total_actions` count only actions where `coordinates is not None` — verify on a screen with 5 real actions + 2 system actions that `total_actions == 5`). Satisfies INV-AGT-37. **BLOCKER for Group 5 task 5.4**.
