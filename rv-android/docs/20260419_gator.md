# Pré-plano: Melhoria da Análise Estática (GATOR/Soot)

**Data**: 2026-04-19
**Contexto**: Resultados da gh50 mostram instrumentação em 352/400 APKs (88%), mas SA consegue analisar apenas 97/352 (27.6%). A causa raiz é um bug do Soot 3.3.0 no `TypeResolver` que crasha em bytecode Kotlin moderno. Este documento analisa o problema, explora soluções, e serve de entrada para a fase de ideação do workflow SDD.

**Relação com gh50**: A gh50 melhorou a instrumentação (17.5% → 88%) mas **não toca** na análise estática. Este pré-plano propõe uma change futura para melhorar a taxa de SA (27.6% → alvo 50-60%).

---

## 1. Diagnóstico Detalhado

### 1.1 O erro

```
Unexpected type null
    at soot.jimple.toolkits.typing.integer.ClassHierarchy.typeNode(ClassHierarchy.java:152)
    at soot.jimple.toolkits.typing.integer.TypeResolver.typeVariable(TypeResolver.java:121)
    at soot.jimple.toolkits.typing.integer.ConstraintCollector.caseAssignStmt(ConstraintCollector.java:406)
    at soot.dexpler.DexBody.jimplify(DexBody.java:660)
    at soot.SootMethod.retrieveActiveBody(SootMethod.java:402)
    at soot.jimple.toolkits.callgraph.OnFlyCallGraphBuilder.processNewMethod(OnFlyCallGraphBuilder.java:755)
    at soot.jimple.toolkits.callgraph.CallGraphBuilder.build(CallGraphBuilder.java:107)
    at soot.jimple.toolkits.callgraph.CHATransformer.internalTransform(CHATransformer.java:51)
```

O crash ocorre no pipeline Dexpler (conversor DEX → Jimple) durante inferência de tipos inteiros. O `ClassHierarchy.typeNode()` tem um mapa fixo de tipos conhecidos. Quando o Dexpler converte bytecode Kotlin moderno, produz tipos intermediários (`Integer1Type`, range types como `[0..1]`) ou referências `null_type` que **não estão registrados** no `typeNodeMap`. O lookup retorna `null` → crash.

### 1.2 Comportamento observado

- **Exit code**: 0 (Soot captura a `InternalTypingException` internamente e sai "normalmente")
- **JSON produzido**: Não — o crash ocorre antes do `GUIAnalysis` e do `RvsecAnalysisClient`
- **Tempo**: 7-50 segundos (crash instantâneo, não timeout)
- **Padrão**: Apps Java puros e Kotlin pequenos (< 30 classes) funcionam. Apps Kotlin/Compose médios/grandes falham.

### 1.3 Evidência empírica (dataset F-Droid 2026, 400 APKs JCA)

| Categoria | APKs | Taxa SA | Exemplo |
|-----------|------|---------|---------|
| Java puro | ~20 | ~80% | NoteSR (162 .java, 0 .kt) |
| Kotlin pequeno (< 30 .kt) | ~30 | ~60% | NanoLedger (31 .kt, Compose) |
| Kotlin + Compose (> 50 .kt) | ~250 | ~15% | Podcini.X (167 .kt), HypoStats (63 .kt) |
| Flutter/other | ~50 | ~40% | pomodorot (Flutter) |

| Compose | Sim (14 refs) | Sim (12 refs) |

| Issue | Título | Status | Relevância |

| [#1279](https://github.com/soot-oss/soot/issues/1279) | Same error on Facebook APK, Soot 4.0.0 | Fechada (sem fix) | Confirma que **Soot 4.x também tem o bug** |

| [#201](https://github.com/soot-oss/soot/issues/201) | `null_type` crash durante array type creation | Aberta | Variante do mesmo bug no Dexpler |

### 2.2 Conclusão das issues

O bug existe desde pelo menos 2016 (issue #201), nunca foi corrigido, e persiste no Soot 4.x (issue #1279 reportada em 4.0.0). O `ClassHierarchy` tem um mapa finito de tipos que não cobre todos os tipos intermediários produzidos pelo Dexpler moderno. É um **bug de design fundamental**, não um fix simples.

## 3. Soluções Investigadas

### 3.1 W1: Opções `jb.tr` no Main.java (BAIXO ESFORÇO, IMPACTO MODERADO)

**O que é**: Adicionar opções ao phase `jb.tr` (type resolver) do Soot para usar um assigner de tipos mais tolerante.

**Mudanças em `Main.java`** (ambos branches: `withCHA` e non-CHA):
```java
"-p", "jb.tr", "ignore-nullpointer-dereferences:true",
"-p", "jb.tr", "use-older-type-assigner:true",
```

Também adicionar programaticamente:
```java
Options.v().set_wrong_staticness(Options.wrong_staticness_ignore);
```

**Racional**:
- `use-older-type-assigner:true` roteia para o `soot.jimple.toolkits.typing.TypeResolver` legado em vez do fast resolver. O resolver antigo pode lidar com os padrões problemáticos de forma diferente.
- `ignore-nullpointer-dereferences:true` instrui o type assigner a deixar locals `null_type` como estão em vez de crashar.
- `wrong_staticness_ignore` previne crashes por chamadas estáticas/não-estáticas incorretas no bytecode.

**Esforço**: ~5 minutos
**Risco**: Baixo — pior caso: não muda nada
**Impacto esperado**: Desconhecido sem teste. Pode desviar o crash em alguns APKs.

### 3.2 W2: Forçar single-thread no Soot (BAIXO ESFORÇO, IMPACTO BAIXO)

**O que é**: `Options.v().set_num_threads(1)` força o Soot a processar bodies sequencialmente.

**Racional**: Crashes em modo multi-thread podem ser não-determinísticos. Single-thread é mais previsível e pode evitar condições de corrida no TypeResolver.

**Esforço**: ~2 minutos
**Risco**: Performance mais lenta
**Impacto**: Provavelmente baixo para nosso caso (o crash é determinístico)

### 3.3 W3: Excluir pacotes problemáticos do body loading (BAIXO ESFORÇO, IMPACTO BAIXO-MÉDIO)

**O que é**: Adicionar flags de exclusão ao Soot:
```java
"-exclude", "kotlin.",
"-exclude", "kotlinx.",
"-no-bodies-for-excluded",
```

**Racional**: Diz ao Soot para não carregar method bodies de classes da stdlib Kotlin. Como essas classes provavelmente não contêm operações criptográficas (MOP methods), excluí-las não afeta a análise de reachability para specs JCA. O crash frequentemente ocorre quando o Soot tenta jimplify um método de uma classe Kotlin stdlib.

**Limitação**: Só ajuda se o crash é em classes Kotlin stdlib. Se é no código Kotlin do **próprio app**, não ajuda.

**Esforço**: ~5 minutos
**Risco**: Pode perder reachability para specs generic/generic_new que monitoram APIs usadas pelo Kotlin stdlib
**Impacto**: Depende de onde o crash ocorre — se na stdlib, pode ser significativo

### 3.4 W4: Upgrade Soot 3.3.0 → 4.6.0 (ESFORÇO MÉDIO, IMPACTO INCERTO)

**O que é**: Atualizar a dependência Soot no `rvsec-gator/pom.xml`:
```xml
<!-- De -->
<gator.soot.version>3.3.0</gator.soot.version>
<!-- Group: ca.mcgill.sable -->

<!-- Para -->
<gator.soot.version>4.6.0</gator.soot.version>
<!-- Group: org.soot-oss -->
```

**Racional**:
- Soot 4.6.0 (out/2024) traz ~6 anos de melhorias no Dexpler e TypeResolver
- A API core (`Scene`, `SootClass`, `SootMethod`, `CallGraph`) é **largamente backward-compatible**
- Issue #1279 (mesmo bug) foi fechada em 4.0.0 sem fix documentado, mas muitos fixes incrementais foram feitos

**Riscos**:
- Mudança de Maven group (`ca.mcgill.sable` → `org.soot-oss`) — breaking change de import
- API breaks menores em classes internas que GATOR possa usar
- Soot 4.x tem seus próprios bugs
- GATOR (Ohio State, ~2016-2017) nunca foi testado com Soot 4.x

**Esforço**: ~2-4 horas (mudar pom, testar compilação, corrigir API breaks, testar)
**Impacto**: Incerto — pode melhorar, pode introduzir novos bugs

### 3.5 W5: Fallback Androguard para reachability (ESFORÇO ALTO, IMPACTO ALTO)

**O que é**: Quando GATOR/Soot falha, usar Androguard (Python) como fallback para análise de reachability. Androguard lê DEX diretamente sem conversão para Jimple — o bug do TypeResolver **não existe**.

**Implementação**:
1. Detectar falha do GATOR (sem JSON produzido)
2. Rodar análise de reachability via Androguard + networkx (call graph)
3. Produzir JSON no mesmo formato que GATOR (`reachability`, `windows`, `transitions`)
4. `windows` e `transitions` ficariam vazios (Androguard não faz GUI analysis)
5. `reachability` seria completa — classes, métodos, flags MOP

**Racional**: O projeto GAPS (2025) demonstra que Androguard pode construir call graphs e computar reachability via `networkx`. O RVSEC já usa Androguard (via `rv-android-core/domain/app.py` para PackageDetector).

**Limitação**: Sem WTG (Window Transition Graph) — `windows` e `transitions` ficariam vazios. Isso impacta `NavigationGuidance` e `TransitionManager` do rv-agent, mas **não impacta** a cobertura MOP (que depende apenas de `reachability`).

**Esforço**: ~2-3 dias
**Risco**: Baixo (fallback, não substituição)
**Impacto**: Alto — potencialmente resolve 100% das falhas SA para reachability

### 3.6 W6: SootUp 2.0 (INVIÁVEL PARA PRAZO ATUAL)

**O que é**: SootUp 2.0 (março 2025) é rewrite completo do Soot. Usa `dexlib2` em vez do Dexpler — o bug do TypeResolver **não existe**.

**Por que não**: Requer rewrite total do GATOR/SootAndroid. API completamente nova (sem `Scene.v()`, sem `Options.v()`, sem `SootClass` no formato antigo). Estimativa: **meses** de trabalho.

**Nota**: O projeto já tem um módulo `teste-sootup` com SootUp 1.3.0 — aparentemente já foi explorado e não foi adotado.

## 4. Análise de Impacto por Spec Set

### 4.1 JCA (foco principal)

A reachability JCA monitora APIs criptográficas (`javax.crypto.*`, `java.security.*`). Essas APIs são chamadas pelo código do app, não pelo Kotlin stdlib. Portanto:
- **W3 (excluir kotlin.*)**: Impacto mínimo na reachability JCA — as chamadas crypto estão no app code
- **W5 (Androguard fallback)**: Impacto máximo — reachability completa sem WTG

### 4.2 generic/generic_new

Monitoram APIs de uso geral (`Iterator`, `InputStream`, `Map`). Kotlin stdlib **usa intensivamente** essas APIs. Portanto:
- **W3**: Pode perder reachability significativa (stdlib Kotlin chama essas APIs)
- **W5**: Mesma limitação que JCA (reachability OK, sem WTG)

### 4.3 Trade-off WTG

O WTG (Window Transition Graph) é usado pelo rv-agent para navegação guiada. Sem WTG:
- **rv-agent `pure_algorithm`**: Funciona normalmente (DFS-based, não precisa de WTG)
- **rv-agent `multimode`/`llm_only`**: Funciona mas sem navigation hints
- **APE-RV**: Não usa WTG
- **Monkey/Droidbot**: Não usam WTG

Na prática, a maioria dos experimentos não depende criticamente do WTG. A reachability é o dado essencial para coverage tracking.

## 5. Estratégia Recomendada

### 5.1 Fase 1: Quick wins (W1 + W2 + W3) — ~15 minutos

Aplicar as três opções de configuração no `Main.java` e testar nos APKs que falham. Medir a melhoria.

**Critério de sucesso**: Se ≥5 dos 28 APKs que falharam no teste local agora produzem JSON, a fase 1 é um sucesso e justifica uma Quick Path change.

### 5.2 Fase 2: Soot upgrade (W4) — ~4 horas

Se a fase 1 não for suficiente, tentar o upgrade para Soot 4.6.0. O GATOR usa a API core do Soot que é largamente compatível.

**Critério de sucesso**: Compila sem erros, testes GATOR passam, taxa SA melhora em ≥10 pontos percentuais.

### 5.3 Fase 3: Androguard fallback (W5) — ~2-3 dias

Implementar fallback de reachability via Androguard quando GATOR falha. Esta é a solução mais robusta mas requer mais trabalho.

**Critério de sucesso**: 100% dos APKs instrumentados têm pelo menos dados de reachability.

### 5.4 Fora de escopo

- **SootUp (W6)**: Rewrite completo, meses de trabalho, fora do prazo
- **FlowDroid**: Não relevante (taint analysis, não WTG/GUI)
- **Substituição do GATOR**: Não viável no prazo
