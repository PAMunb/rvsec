## Problema Identificado

Os testes no rvsec-vision-llm atual usam apenas `coordinate_validation` (coordenadas no prompt).
O modelo apenas **copia** as coordenadas fornecidas - não faz **grounding visual real**.

**Exemplo do prompt atual (ERRADO para grounding)**:
```
"Click on Button 'OK' at position (352, 782)"
→ Modelo copia (352, 782) - trivial, 100% acerto
```

**Grounding real (CORRETO)**:
```
"Click on the OK button"
→ Modelo DESCOBRE visualmente onde está o botão
```

## Fase 1: Correção do Sistema de Coordenadas

### 1.1 Atualizar Parser de Tool Calls
**Arquivo**: `src/parsers/tool_call_parser.py`

Já corrigido para suportar:
- [x] `.91` → `0.91` (floats sem zero inicial)
- [x] `{"coordinate": [x, y]}` → `{"x": x, "y": y}` (formato Fara)
- [ ] **NOVO**: Detectar e converter [0, 1000] → pixels

```python
def normalize_coordinates(x, y, image_width, image_height):
    """Convert normalized [0, 1000] coords to pixels."""
    if 0 <= x <= 1000 and 0 <= y <= 1000:
        # Likely normalized format
        pixel_x = int((x / 1000) * image_width)
        pixel_y = int((y / 1000) * image_height)
        return pixel_x, pixel_y
    # Already in pixel format
    return x, y
```

## Problemas Identificados e Soluções (Revisão)

### 1. Ground Truth para Elementos Dinâmicos

**Problema**: UIAutomator NÃO enxerga dentro de Canvas/WebView.

**Solução**: Anotação manual pelo Claude:
1. Analisar screenshots dos apps com elementos dinâmicos identificados
2. Se elemento visível NÃO estiver no dump UIAutomator → anotar coordenadas manualmente
3. Apenas 1-5 casos necessários por tipo (Canvas, WebView, SurfaceView)

**Apps prioritários**:
- `org.secuso.privacyfriendlydicer_8` (Canvas - dados)
- `org.secuso.privacyfriendlyludo_5` (Canvas - tabuleiro)
- `com.gh4a_73` (WebView - Markdown)

### 2. Testes Negativos - Validação Binária

**Problema**: Validar "texto explicando que não encontrou" é frágil.

**Solução**: Tool explícita `android_status(status="not_found")`:
```
If the element is NOT visible, call android_status with status='not_found'.
```

Isso torna validação binária: True Negative vs False Positive.

### 3. Coordenadas Qwen3-VL

**Problema**: Qwen3-VL pode preferir [0-1000] normalizado.

**Teste**: Comparar saída normalizada vs pixels direto.

### 4. Detecção de Viés Espacial

**Métrica adicional**: Position bias - tendência de clicar em regiões específicas.

### 5. Expectativas

Visual-only terá acurácia MENOR que coordinate-validation (esperado ~30-96% vs ~100%).

## Resultados Experimentais

Ver `docs/008_visual_grounding.md` para detalhes completos.

### Benchmark - Qwen3-VL-4B-Instruct (2025-12-25)

**Configuração**: 50 screenshots, 144 elementos, 1 repetição

| Modo | Hit Rate | Tool Call Rate | Avg Distance | Latency |
|------|----------|----------------|--------------|---------|
| `coords_provided` | **100%** | 100% | 0.0px | 1589ms |
| `visual_only` | **3.5%** | 87.5% | 34.7px | 1511ms |

**Diferença**: 96.5 pontos percentuais.

### Conclusões

1. **coords_provided é trivial**: O modelo copia as coordenadas fornecidas - não testa visão
2. **visual_only mede grounding real**: Capacidade do modelo localizar elementos visualmente
3. **Qwen3-VL-4B tem baixo grounding**: 3.5% hit rate sem coordenadas
4. **Tool calling funciona bem**: 87.5-100% das vezes chama a ferramenta correta
