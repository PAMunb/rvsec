# gh120 — os achados A3–A6 da revisão, explicados

07/10/2026. Revisão completa: `docs/20261007_gh120_code_review.md`. Rótulos: **[conferido]** = abri o
código ou medi; **[hipótese]** = inferência.

Nenhum dos quatro tira do artefato algo que setembro tinha, com uma exceção possível (A3). São
limites do que a gh120 acrescenta, não regressões medidas. Os 14 APKs da verificação de hoje não
perderam janela, widget, par (id, host) nem listener.

## A3 — spinner cujo adapter é criado num if/else fica sem itens

**[conferido]** `SpinnerItemExtractor.adapterSite` (`client/.../SpinnerItemExtractor.java`, perto da
linha 253) aceita só **uma** definição que chega ao `setAdapter`. Código assim:

```java
ArrayAdapter a;
if (modoA) a = ArrayAdapter.createFromResource(ctx, R.array.X, ...);
else       a = ArrayAdapter.createFromResource(ctx, R.array.Y, ...);
spinner.setAdapter(a);
```

tem duas definições de `a`, e o spinner sai com `entries` vazio. O código de setembro indexava os
itens pela variável local, não pelo comando que criou o adapter. Por isso juntava os itens das duas
ramificações, quase por acaso. A troca para indexar pelo comando de criação foi feita por causa do
cry.otp (D13), onde **uma** variável guardava adapters de **vários** spinners em sequência e cada
spinner recebia a união de todos.

- Quando acontece: só se setembro já preenchia esse spinner por um construtor literal
  (`new ArrayAdapter(ctx, layout, new String[]{…})`) atribuído em ramificações. Não medi quantos
  APKs têm isso **[hipótese: raro]**.
- Correção possível: unir os itens de todas as definições que chegam, em vez de exigir uma só.
  Isso muda a saída e exige rebuild e re-checar o cry.otp.

## A4 — dois resolvedores de host tratam diferente uma activity base concreta

**[conferido]** Há dois códigos que decidem em qual activity uma janela fica pendurada:

- `FragmentHostResolver.launchedActivities` (janelas `FRAGMENT`): se o código está numa activity
  base, a janela vai para **cada subclasse declarada no manifesto**.
- `HostResolver.hostsOf` (janelas `HOSTED`): se a classe já está no conjunto de activities do GATOR,
  ela é o próprio host. Esse conjunto (`allNActivityNodes`) contém toda activity concreta do app,
  **declarada no manifesto ou não**.

Efeito: uma classe `BaseActivity` concreta (não abstrata), que não está no manifesto e que abre um
diálogo, gera `BaseActivity#Dialogo`. Em execução a activity é sempre uma subclasse (`MainActivity`,
…), então o APE-RV nunca casa essa janela e os widgets dela não guiam nada. Com uma base
**abstrata** isso não acontece: o resolvedor desce para as subclasses. Não é perda contra setembro,
porque essas janelas não existiam; é ganho que deixa de acontecer.

- Não medi em quantos APKs isso ocorre **[hipótese: apps Kotlin com `open class BaseActivity`]**.
- Correção possível: o `HostResolver` usar a mesma regra do manifesto. Muda a saída.

## A5 — as arestas de lambda também mexem no denominador de cobertura

**[conferido]** As arestas wrapper → corpo entram no grafo de chamadas do Soot antes da
alcançabilidade. Além de `reachesTarget` (o efeito pretendido, D3), elas mudam `reachable`, que é o
denominador do `rv-coverage`. Medido hoje contra setembro, mesmos métodos:

| APK | `reachable` set → out |
|---|---|
| deku, etesync, linxshare, dsub2000 | sem mudança |
| broccoli | 271 → 272 |
| sexytopo | 871 → 872 |
| iyps | 522 → 542 |
| giggity (tarefa 1.1) | +2 |

Nunca desce. Se o +20 do iyps vem das arestas de lambda ou dos modelos de fragment/ViewBinding,
eu não separei **[hipótese]**. O D3 e a spec falam só de `reachesTarget`. A proposta é registrar
no D3 que `reachable` também sobe, sem mudar código.

## A6 — falha nas arestas de lambda não fica registrada no artefato

**[conferido]** `RvsecAnalysisClient.run` envolve `LambdaEdges.addTo` num `try` que só imprime no
log. Se falhar, os wrappers saem com `reachesTarget: false` e o artefato não tem nenhuma marca
disso. Pelo D9 (INV-DRV-09), o derive confia no flag do wrapper listado e não recupera mais pela
classe. Então, nesse caso, o derive perde flags que a recuperação por classe teria dado, sem aviso.

- Chance: baixa, porque `addTo` já pula corpos que não carregam **[hipótese]**. Nenhuma falha
  apareceu nos 14 APKs de hoje (o log imprime a contagem de arestas).
- Correção possível: uma chave no artefato (por exemplo `lambdaEdges: false`) que o derive lê para
  voltar à recuperação por classe. Muda o esquema (INV-ANA-32) e o derive.

## Proposta

Registrar A5 no D3 via `/opsx:update`. Deixar A3, A4 e A6 para uma change seguinte, citados no
fechamento da gh120. Cada um muda o que o GATOR emite.
