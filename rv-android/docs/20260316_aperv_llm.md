# APE-RV: Integração LLM + Calibração de Parâmetros

**Data**: 2026-03-16
**Status**: Ideação (Phase 0 — entrada para workflow SDD)
**Objetivo**: Integrar LLM (Qwen3-VL) no loop de exploração do APE-RV e preparar espaço de parâmetros para calibração via Optuna.

---

## 1. Contexto e Motivação

### 1.1 Resultados experimentais (exp1 + exp2)

O experimento comparativo (169 APKs, 5 variantes) produziu os seguintes resultados:

| Ferramenta | Method Cov | MOP Cov | Violation Types | APKs c/ Violação |
|------------|-----------|---------|-----------------|-------------------|
| `aperv:sata_mop_v1` (500/300/100) | **28.35%** | 37.02% | **23** | **80/169 (47.3%)** |
| `ape` (original) | 27.82% | 37.08% | 23 | 76/169 (45.0%) |
| `aperv:sata_mop_v2` (100/60/20) | 27.35% | 36.35% | 20 | 79/169 (46.7%) |
| `aperv:sata` (sem MOP) | 27.28% | 35.49% | 20 | 76/169 (45.0%) |
| `rvsmart:mvp` | 24.24% | 31.53% | 23 | 72/169 (42.6%) |

### 1.2 Lições aprendidas

1. **MOP guidance funciona quando domina**: Os pesos v1 (500/300/100) são ~15x o SATA base (~32), forçando APE a sempre escolher ações MOP. A tentativa de "balancear" (v2: 100/60/20) reduziu o efeito — delta de -1.00pp em method coverage (p=0.031) e perda de 3 tipos de violação.

2. **47% dos APKs têm exploração determinística**: Mesmo com MOP, muitos APKs seguem o mesmo trace porque o SATA é determinístico quando não há ações não-visitadas. LLM pode quebrar esse determinismo.

3. **rvsmart encontrou os mesmos 23 tipos de violação** que `ape` e `sata_mop_v1`, apesar de menor cobertura — caminhos de exploração diferentes são complementares.

4. **Oportunidade**: Combinar o modelo de exploração do APE (SATA + MOP) com decisões pontuais de LLM pode melhorar tanto a cobertura quanto a descoberta de violações.

### 1.3 Hipótese

> APE-RV com LLM pontual (`aperv:sata_mop_llm`) supera `aperv:sata_mop` em method coverage e violation discovery porque a LLM quebra padrões determinísticos e identifica elementos de UI semanticamente relevantes que o SATA ignora.

## 2. Arquitetura

### 2.1 Visão geral

```
                    APE-RV (device, Java, app_process)
                    ┌─────────────────────────────────────────┐
                    │  MonkeySourceApe.nextEventImpl()        │
                    │    ├── capture GUITree                  │
                    │    ├── map to abstract State             │
                    │    ├── [NEW] LLM routing decision        │
                    │    │     ├── YES → LlmClient.chat()     │
                    │    │     │         ↓                     │
                    │    │     │    SGLang (host:30000)        │
                    │    │     │         ↓                     │
                    │    │     │    parse action → ModelAction  │
                    │    │     └── NO  → SATA selection        │
                    │    ├── adjustActionsByGUITree() (MOP)    │
                    │    ├── selectNewAction()                 │
                    │    └── execute event                     │
                    └─────────────────────────────────────────┘
```

### 2.2 Componentes reutilizáveis do rvsmart

A infraestrutura LLM do rvsmart (`rvsec-android/rvsmart/src/.../llm/`, ~1543 LOC) é madura e testada. Vamos copiar 6 classes diretamente para o APE-RV (P1: simplicidade, sem shared library para 2 consumidores):

| Classe | LOC | Função | Adaptação |
|--------|-----|--------|-----------|
| `SglangClient.java` | 369 | HTTP client OpenAI-compatible, multimodal | Nenhuma |
| `ScreenshotCapture.java` | 97 | Screenshot via SurfaceControl reflection | Nenhuma |
| `ImageProcessor.java` | 89 | PNG→JPEG+base64, resize ≤1000px | Nenhuma |
| `ToolCallParser.java` | 264 | 3-level fallback (native/XML/JSON), Qwen3-VL fixes | Nenhuma |
| `CoordinateNormalizer.java` | 43 | [0,1000) → device pixels | Nenhuma |

**Código novo para APE-RV** (~400-500 LOC):
- `ApePromptBuilder.java` — prompt adaptado para APE (usa GUITree em vez de ScreenItem)

- Config keys em `Config.java`

### 2.3 Comunicação device → host

Mesmo padrão do rvsmart: `HttpURLConnection` via `10.0.2.2:30000` (Android emulator → host localhost). Em Docker: socat bridge ou `extra_hosts: host.docker.internal:host-gateway`.

## 3. Três Modos de LLM

### 3.1 New State (ape.llmOnNewState)

**Quando**: Primeira visita a cada state novo (`state.getVisitedCount() == 0`).

**Onde**: Em `StatefulAgent`, antes de `adjustActionsByGUITree()`.

**Custo**: ~50-100 chamadas LLM por run (uma por state novo). Com ~3-5s por chamada: +2.5-8min ao run de 10min.

**Impacto esperado**: Maior — LLM vê cada tela pela primeira vez e escolhe a ação mais promissora. Quebra o determinismo do SATA na primeira visita.

**Lógica**:
1. Captura screenshot (SurfaceControl)
2. Extrai widget list do GUITree atual
3. Envia ao SGLang com prompt "escolha a ação mais relevante"
4. Parse resposta → coordenadas + tipo
5. Mapeia para ModelAction mais próximo (por distância euclidiana ao centro do widget)
6. Se match encontrado: executa via caminho normal do APE (Model registra transição)
7. Se sem match: injeta raw event (como fuzzing)

### 3.2 Epsilon-LLM (ape.llmRate)

**Quando**: Com probabilidade `llmRate` em cada step (default: 0.05 = 5%).

**Onde**: No início de `selectNewAction()`, antes do epsilon-greedy check.

**Custo**: ~30-60 chamadas por run. +1.5-5min.

**Impacto esperado**: Moderado — injeta variabilidade contínua. Substitui parte do epsilon-greedy random por decisões LLM informadas.

**Alternativa ao fuzzing**: Com `doFuzzing=false` e `llmRate=0.05`, a LLM substitui completamente o fuzzing random. Decisão semanticamente informada vs random noise.

### 3.3 Stuck Recovery (ape.llmOnStuck)

**Quando**: Quando `graphStableCounter` atinge threshold (antes do restart forçado).

**Onde**: Em `StatefulAgent.onGraphStable()` ou `SataAgent.onGraphStable()`.

**Custo**: ~5-10 chamadas por run. +15-50s.

**Impacto esperado**: Baixo mas valioso — LLM pode sugerir ação "fora da caixa" quando APE está preso (scroll em lugar inesperado, long press, text input).

**Lógica**: Em vez de restart imediato, tenta LLM uma vez. Se LLM não produz transição nova em 2 tentativas → restart normal.

## 4. Espaço de Parâmetros para Calibração

### 4.1 Parâmetros de exploração APE (existentes, nunca calibrados)

| # | Parâmetro | Default | Tipo | Range sugerido | Impacto |
|---|-----------|---------|------|----------------|---------|
| 1 | `defaultEpsilon` | 0.05 | double | [0.01, 0.20] | Prob. ação aleatória vs greedy |
| 2 | `graphStableRestartThreshold` | 100 | int | [30, 300] | Steps sem crescimento → restart |
| 3 | `stateStableRestartThreshold` | 50 | int | [20, 150] | Steps no mesmo state → restart |
| 4 | `fuzzingRate` | 0.02 | double | [0.0, 0.10] | Prob. fuzzing por step |
| 5 | `doFuzzing` | true | bool | {true, false} | Habilita fuzzing |
| 6 | `throttleForActivityTransition` | 500 | int (ms) | [200, 1000] | Delay transição de activity |
| 7 | `defaultGUIThrottle` | 200 | long (ms) | [100, 500] | Delay entre ações |
| 8 | `maxExtraPriorityAliasedActions` | 5 | int | [1, 15] | Boost para ações com múltiplos alvos |
| 9 | `maxStatesPerActivity` | 10 | int | [5, 30] | Limite de states por activity |
| 10 | `trivialActivityRankThreshold` | 3 | int | [1, 8] | Threshold para activity trivial |
| 11 | `doBackToTrivialActivity` | false | bool | {true, false} | Backtrack para activities triviais |

| # | Parâmetro | Default | Tipo | Range | Impacto |

## 7. Riscos e Mitigações

| Risco | Probabilidade | Impacto | Mitigação |
|-------|---------------|---------|-----------|
| Latência LLM degrada exploração | Média | Alto | Circuit breaker (3 falhas → 60s block), timeout 30s, fallback para SATA |
| Screenshot via SurfaceControl falha no Android 10 | Baixa | Médio | Fallback UiAutomation (já implementado no rvsmart) |
| Qwen3-VL coordenadas imprecisas (~84% hit rate) | Média | Médio | Mapear para ModelAction mais próximo (tolerância de 50px) |
| SGLang indisponível durante calibração | Média | Alto | Monitorar saúde do SGLang, auto-restart script |
| Build d8 incompatível com classes do rvsmart | Baixa | Médio | Testar build incremental, resolver conflitos de API level |
| Overhead de rede inaceitável em Docker | Baixa | Baixo | `extra_hosts` resolve, mesma solução do rvsmart |

## 8. Métricas de Sucesso

1. **Method coverage**: `aperv:sata_mop_llm` > `aperv:sata_mop` (Wilcoxon p<0.05)
2. **Unique violation types**: ≥23 (pelo menos igualar ape/sata_mop_v1)
3. **APKs com violação**: >47.3% (superar sata_mop_v1)
4. **Determinismo**: <30% de APKs com traces idênticos entre reps (reduzir dos 47% atuais)
5. **Overhead aceitável**: <5min adicional em run de 10min com LLM ativo
