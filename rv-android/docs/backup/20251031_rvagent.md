# RVAgent: Introdução e Contexto do Problema

## Contexto da Pesquisa de Doutorado

Esta pesquisa de doutorado investiga a aplicação de técnicas de Runtime Verification (RV) para detectar mau uso de APIs em aplicações Android, com ênfase particular em violações de APIs criptográficas. O trabalho está estruturado em três fases complementares, cada uma construindo sobre os achados e infraestrutura da fase anterior. A ferramenta RVAgent, objeto deste documento, representa a terceira e última fase desta investigação.

## Fase 1: Runtime Verification para APIs Criptográficas Java (Concluída)

A primeira fase estabeleceu a capacidade fundamental da runtime verification para detectar mau uso de APIs criptográficas em aplicações Java, focando especificamente na Java Cryptography Architecture (JCA). Esta fase produziu resultados significativos que demonstraram o potencial da abordagem:

### Resultados Principais

A Phase 1 utilizou 22 especificações JavaMOP direcionadas a padrões comuns de mau uso de APIs criptográficas. Estas especificações foram integradas com a infraestrutura RVSec para gerenciamento de especificações e geração de monitores. Os resultados demonstraram a precisão superior da runtime verification em comparação com ferramentas de análise estática estado-da-arte, particularmente CogniCrypt e CryptoGuard.

### Limitação Fundamental Identificada

O achado mais importante da Fase 1 foi a identificação de uma limitação intrínseca da runtime verification: **sua eficácia está fundamentalmente limitada pela cobertura de testes**. Quando casos de teste não exercitam caminhos de código contendo mau uso de APIs, essas violações permanecem não detectadas, resultando em falsos negativos. Esta constatação motivou diretamente a Fase 2 da pesquisa.

A precisão da RV é excepcional - quando as violações são exercitadas durante a execução do programa, elas são detectadas com alta acurácia e baixa taxa de falsos positivos. No entanto, esta vantagem está intrinsecamente acoplada à qualidade e abrangência dos testes executados. Esta dependência de cobertura representa o principal desafio a ser endereçado nas fases subsequentes.

## Fase 2: Plataforma RV-Android e Comparação de Ferramentas de Geração de Testes (Artigo em Elaboração)

Reconhecendo que a eficácia da RV depende da qualidade dos testes, a Fase 2 expandiu a pesquisa para o ecossistema Android com dois objetivos principais:

### Desenvolvimento de Infraestrutura: Plataforma RV-Android

Foi desenvolvida a plataforma RV-Android, um sistema abrangente para runtime verification de aplicações Android. Esta plataforma consiste em 11 módulos especializados organizados em uma arquitetura modular baseada em Poetry workspace:

**Infraestrutura Central:**
- **rv-android-core**: Infraestrutura fundamental com modelos de domínio, sistema de eventos (EventBus), tratamento de erros e logging
- **rv-platform**: Plataforma de execução que coordena tarefas, gerencia dispositivos e coleta resultados
- **rv-tools**: Sistema de registro e plugin de ferramentas de teste com padrões de factory
- **rv-uiautomator**: Componentes compartilhados UIAutomator para interação direta com dispositivos

**Módulos de Análise:**
- **rv-monitor-generator**: Integração JavaMOP/RV-Monitor para geração de monitores de verificação
- **rv-instrumentation**: Instrumentação de APKs com capacidade de tecelagem de monitores
- **rv-static-analysis**: Ferramentas de análise estática (GATOR, GESDA, REACH) para aplicações Android
- **rv-coverage**: Análise e rastreamento de cobertura de operações monitoradas
- **rv-screen-parser**: Parser de UI Android com padrões visitor para análise de estados

**Módulos de IA e Orquestração:**
- **rv-llm**: Framework de integração com modelos de linguagem (LLMs) com suporte a múltiplos backends
- **rv-experiment**: Sistema de orquestração e coordenação de experimentos
- **rvandroid-tool e rvsmart-tool**: Ferramentas de teste guiadas por IA com integração LLM

Esta arquitetura modular fornece comunicação orientada a eventos, tratamento de erros abrangente, e suporte completo ao ciclo de execução de testes com runtime verification.

### Avaliação Empírica: Comparação de Ferramentas de Geração de Testes

A Fase 2 realizou uma comparação abrangente de 10+ ferramentas de geração de testes Android para avaliar sua eficácia em descobrir mau uso de APIs via runtime verification. O estudo envolveu:

**Configuração Experimental:**
- **Dataset**: 193 aplicações Android do repositório F-Droid com uso da biblioteca JCA
- **Ferramentas avaliadas**: APE, ARES, DroidBot (múltiplas variantes: naive, DFS greedy, BFS greedy), DroidMate, FastBot, Humanoid, Monkey e Q-testing
- **Configurações de timeout**: 60, 120, 180 e 300 segundos
- **Conjuntos de especificações**: Especificações JCA específicas e especificações genéricas de APIs
- **Métricas**: Eficácia na detecção de bugs, cobertura de métodos, cobertura de métodos JCA

**Resultados: Detecção de Mau Uso de APIs Criptográficas JCA**

As ferramentas com melhor desempenho foram Humanoid (média de 1.18 violações por app), FastBot (1.14) e Ape (1.08) com timeout de 300s. Os ganhos de desempenho ao estender o tempo de execução variaram de 14.80% (Q-testing) a 77.50% (DroidBot BFS greedy) ao comparar execuções de 300s vs 60s.

No total, foram detectadas **206 violações únicas de APIs criptográficas** em 20,477 violações reportadas, sugerindo grande sobreposição entre os achados das diferentes ferramentas e repetições. Isto indica que selecionar apenas a ferramenta de geração de testes mais eficaz é provavelmente suficiente para cobrir grande percentual das violações criptográficas detectadas via runtime verification.

Para contexto, CogniCrypt (uma ferramenta de análise estática estado-da-arte) reportou uma média de 3.00 violações por app, mas com taxa substancialmente maior de falsos positivos em comparação com a abordagem de runtime verification.

**O Achado Crítico: O Gap de Cobertura**

O resultado mais significativo da Fase 2 concerne aos padrões de cobertura de código. As melhores ferramentas alcançaram:
- **Cobertura geral de métodos**: FastBot (20.40%), Humanoid (20.04%), Ape (19.45%) com timeout de 300s
- **Cobertura de métodos JCA**: Dramaticamente menor - Humanoid (13.49%), DroidBot BFS greedy (13.31%), FastBot (12.27%)

Esta disparidade de cobertura revela um problema fundamental: **estratégias padrão de geração de testes, que tipicamente priorizam amplitude de exploração de UI ou métricas básicas de cobertura de código, não estão efetivamente alcançando métodos que usam APIs criptográficas**. As ferramentas se destacam em descobrir e interagir com componentes de UI, mas têm desempenho sistematicamente inferior quando medidas contra os padrões específicos de uso de API que a runtime verification tem como alvo.

**Resultados com Especificações Genéricas de APIs**

A Fase 2 também validou a abordagem usando especificações JavaMOP de propósito geral, demonstrando:
- Detecção substancialmente maior de violações: 150,342 (FastBot) a 120,282 (DroidMate) violações com timeout de 300s
- Maior cobertura de métodos de APIs genéricas: Humanoid (26.08%), DroidBot DFS greedy (24.66%)
- Demonstra que a aplicabilidade da RV estende muito além de APIs criptográficas

## O Problema Central: Gap de Cobertura Guiada

Os achados cumulativos das Fases 1 e 2 estabelecem uma declaração clara do problema:

**Runtime verification oferece precisão superior na detecção de mau uso de APIs em comparação com abordagens de análise estática, mas sua eficácia é fundamentalmente limitada pela cobertura de testes. Ferramentas existentes de geração de testes Android, apesar de alcançarem cobertura geral de código razoável (≈20%), sistematicamente falham em exercitar adequadamente métodos contendo padrões específicos de uso de API de interesse (≈13% para APIs criptográficas). Este gap de cobertura representa o principal gargalo impedindo a runtime verification de alcançar seu potencial completo em análise de segurança Android no mundo real.**

### Análise das Estratégias de Exploração Atuais

As ferramentas atuais de geração de testes empregam várias estratégias de exploração:

- **Exploração aleatória** (Monkey): Sem guiamento sistemático, puramente probabilística
- **Exploração baseada em modelos** (DroidBot, Humanoid): Constroem modelos de estados de UI e exploram baseados em transições de estados
- **Aprendizado por reforço** (Q-testing): Aprendem políticas ótimas de exploração através de tentativa e erro
- **Maximização de cobertura de atividades/métodos** (FastBot): Direcionam métricas gerais de cobertura de código

No entanto, nenhuma dessas abordagens considera explicitamente a **importância semântica** de diferentes caminhos de código relativos aos objetivos de runtime verification. Uma ferramenta de geração de testes que alcança 20% de cobertura geral mas apenas 8% de cobertura de métodos contendo operações monitoradas está fundamentalmente desalinhada com os objetivos da RV.

### Implicações para Runtime Verification

Este desalinhamento tem implicações diretas para a eficácia da runtime verification:

1. **Falsos Negativos por Falta de Cobertura**: Violações em código não exercitado permanecem não detectadas
2. **Exploração Ineficiente**: Tempo gasto explorando caminhos irrelevantes para objetivos de RV
3. **Baixo ROI de Instrumentação**: O custo de instrumentar toda a aplicação não é justificado se apenas pequena fração dos métodos instrumentados é exercitada
4. **Gap entre Análise Estática e Dinâmica**: Análise estática pode identificar potenciais violações que nunca são verificadas dinamicamente

## Fase 3: RVAgent - Teste Guiado para Runtime Verification

A Fase 3 endereça este gap de cobertura através do desenvolvimento do **RVAgent**, uma ferramenta de teste guiado inovadora que aproveita informações de análise estática para direcionar a exploração em direção a métodos e caminhos de UI mais relevantes para especificações de runtime verification.

### Conceito Central

O RVAgent opera no princípio de que **análise estática pode identificar quais elementos de UI e sequências de interação têm maior probabilidade de alcançar operações monitoradas**, e esta informação pode ser usada para guiar um agente autônomo baseado em LLM durante exploração dinâmica. Ao invés de explorar a aplicação uniformemente ou otimizar para métricas genéricas de cobertura, o RVAgent prioriza interações que levam a caminhos de código contendo usos de APIs monitoradas.

### Abordagem Técnica: Três Dimensões Complementares

A arquitetura da ferramenta combina três dimensões de análise complementares:

#### 1. Fundação em Análise Estática

O RVAgent integra-se com ferramentas de análise estática para construir um mapa semântico da aplicação:

- **Integração com GATOR**: Extrai Window Transition Graphs (WTG) que fornecem mapeamentos entre elementos de UI e métodos de programa alcançáveis
- **Análise de Call Graphs**: Identifica métodos contendo operações monitoradas (MOP - Monitored Operations)
- **Análise de Alcançabilidade Reversa**: Determina quais elementos de UI podem alcançar quais operações monitoradas
- **Classificação de Elementos de UI**: Cada elemento interativo recebe marcadores semânticos:
  - `[DM]` (Directly reaches Monitored operation): Alcança diretamente operação monitorada - alvo imediato, máxima prioridade
  - `[M]` (reaches Monitored operation): Alcança operação monitorada através de chamadas transitivas - alvo secundário
  - Sem marcação: Não alcança operações monitoradas - menor prioridade

Esta classificação permite que o agente tome decisões informadas sobre quais interações priorizar durante a exploração.

#### 2. Exploração Autônoma Guiada por LLM

O RVAgent utiliza um modelo de linguagem habilitado com visão para entendimento de UI e geração de ações:

- **Modelo de Visão-Linguagem**: Qwen2.5-VL para compreensão contextual de interfaces Android
- **Arquitetura LangGraph**: Fornece workflow estruturado do agente com checkpointing e memória persistente
- **Agente Aumentado com Ferramentas**: Capacidades de interação Android:
  - Interação com elementos de UI (click, long-click, entrada de texto)
  - Operações de dispositivo (back, home, captura de screenshot)
  - Consulta de estado da aplicação (hierarquia UI, atividade atual)
- **Processamento Otimizado de Screenshots**: Resolução de 728×1288 pixels (múltiplos de 28) para inferência eficiente do modelo de visão
- **Hiperparâmetros Validados**: Temperatura=0.25, Top-P=0.8, Top-K=50 (determinados através de testes extensivos da Fase 0)

A abordagem baseada em LLM permite entendimento contextual do comportamento da aplicação, reconhecendo fluxos de autenticação, requisições de permissões, workflows multi-etapas e outros padrões semânticos que ferramentas baseadas em regras têm dificuldade em lidar.

#### 3. Estratégia de Decisão Híbrida

O RVAgent implementa uma estratégia híbrida que combina os pontos fortes de análise estática e dinâmica:

- **Análise Estática**: Fornece **guiamento estratégico** (quais elementos de UI priorizar)
- **LLM**: Fornece **adaptação tática** (como interagir, lidar com estados dinâmicos, recuperar de erros)
- **Parser de Tela Integrado**: Incorpora resultados de análise estática nas descrições de elementos de UI
- **Engenharia de Prompt**: Informação de alcançabilidade MOP é incorporada no contexto de geração de ações
- **Exploração Adaptativa**: Balanceia exploitation (seguir dicas estáticas) e exploration (descobrir novos caminhos)

### Diferenciadores Chave de Ferramentas Existentes

O RVAgent distingue-se tanto das ferramentas de pesquisa existentes quanto das ferramentas previamente desenvolvidas (rvandroid-tool/rvsmart-tool) de várias maneiras fundamentais:

**1. Guiamento Específico para RV**:
Ao contrário de DroidBot/Humanoid (que otimizam para cobertura de estados) ou FastBot (que otimiza para cobertura de métodos), o RVAgent explicitamente otimiza para cobertura de **operações monitoradas**.

**2. Entendimento Semântico**:
A abordagem baseada em LLM permite entendimento contextual do comportamento da aplicação, reconhecendo padrões que ferramentas baseadas em regras têm dificuldade em capturar.

**3. Sinergia Estático-Dinâmica**:
Enquanto Q-testing aprende políticas ótimas através de aprendizado por reforço (requerendo muitas tentativas), o RVAgent aproveita análise estática para fornecer guiamento imediato desde a primeira execução, implementando efetivamente uma forma de "exploração informada".

**4. Operação Autônoma**:
Ao contrário do rvandroid-tool (que integra com o motor de exploração do DroidBot), o RVAgent opera como um agente autônomo standalone com controle completo sobre a estratégia de exploração, permitindo integração mais estreita entre guiamento estático e decisões dinâmicas.

### Objetivos de Pesquisa

O desenvolvimento e avaliação do RVAgent contribuirá:

**1. Arquitetura Inovadora**:
Primeira demonstração de integração de análise estática de programas com agentes LLM habilitados com visão para testes Android, especificamente otimizado para objetivos de runtime verification.

**2. Validação Empírica**:
Comparação abrangente contra ferramentas baseline da Fase 2 (particularmente Humanoid, FastBot e variantes DroidBot) medindo:
- Cobertura de operações monitoradas (métrica primária)
- Eficácia na detecção de mau uso de APIs criptográficas
- Tempo até primeira violação para violações conhecidas
- Eficiência de exploração (cobertura por unidade de tempo)

**3. Infraestrutura Reutilizável**:
Extensão da plataforma RV-Android com:
- Arquitetura de agente baseada em LangGraph adaptável a outros objetivos de teste
- Padrões de integração de análise estática para mapeamento UI-para-caminho-de-código
- Estratégias de otimização de modelo de visão para análise de UI Android

**4. Impacto Prático**:
Demonstração de que testes guiados podem superar a limitação de cobertura que atualmente restringe a eficácia da runtime verification, potencialmente habilitando deployment de RV em contextos industriais de análise de segurança Android.

### Resultados Esperados

Se bem-sucedido, o RVAgent deverá demonstrar:

- **Maior cobertura MOP**: >20% de cobertura de métodos contendo operações monitoradas (vs. ≈13% baseline)
- **Detecção mais eficiente de violações**: Tempo reduzido até primeira violação através de exploração priorizada
- **Precisão mantida ou melhorada**: Aproveitando a vantagem inerente de precisão da RV enquanto endereça gaps de cobertura
- **Generalizabilidade**: Eficácia tanto em especificações JCA específicas quanto em especificações genéricas de APIs

## Estratégias de Teste e Abordagem de Implementação

### Estratégias de Exploração Investigadas

O desenvolvimento do RVAgent está investigando múltiplas estratégias de teste para determinar a abordagem ótima:

**Estratégias Clássicas:**
- **Depth-First Search (DFS)**: Exploração em profundidade, útil para alcançar estados profundos
- **Breadth-First Search (BFS)**: Exploração em largura, garante exploração sistemática de todos os estados acessíveis
- **Random Exploration**: Baseline para comparação, sem guiamento sistemático

**Estratégias Guiadas:**
- **Coverage-Guided**: Prioriza interações que aumentam cobertura de código geral
- **MOP-Guided**: Prioriza interações marcadas com [M] ou [DM] (específico para RV)
- **Hybrid Strategies**: Combina exploração (descoberta de novos estados) com exploitation (seguir dicas estáticas)

A seleção da estratégia será baseada em pesquisa de LLMs sobre abordagens estado-da-arte em teste guiado, seguida de implementação e avaliação empírica.

### Arquitetura de Implementação LangGraph

A implementação utiliza a arquitetura LangGraph com componentes pré-construídos para eficiência e manutenibilidade:

**Componentes Core:**
- **MessagesState**: Gerenciamento de estado com histórico de mensagens
- **tools_condition**: Roteamento automático entre assistente e execução de ferramentas
- **ToolNode**: Execução de ferramentas Android (click, text input, back, etc.)
- **SqliteSaver**: Persistência de memória com checkpointing

**Fluxo de Execução:**
```
START → assistant (análise e decisão) → tools_condition (roteamento)
                                       ├─ tools (execução) → assistant (loop)
                                       └─ END (conclusão)
```

Esta arquitetura simplifica significativamente o código em comparação com abordagens manuais de gerenciamento de estado e roteamento.

## Contribuições Científicas e Práticas

O sucesso da Fase 3 culminará em uma dissertação de doutorado abrangente apresentando:

**Fase 1**: Vantagens de precisão da runtime verification para detecção de mau uso de APIs criptográficas, estabelecendo a superioridade em relação a análise estática em termos de precisão.

**Fase 2**: Avaliação sistemática da eficácia de geração de testes para RV em Android, identificando o gap crítico de cobertura que limita a aplicabilidade prática da abordagem.

**Fase 3**: Abordagem inovadora de teste guiado superando limitações de cobertura através de integração estático-LLM, demonstrando que é possível direcionar exploração para objetivos específicos de verificação.

Juntas, estas três fases estabelecem tanto a proposição de valor da runtime verification para análise de segurança Android (precisão sem falsos positivos) quanto uma solução prática para sua principal limitação (eficácia dependente de cobertura), avançando o estado-da-arte em testes automatizados de segurança para aplicações móveis.

## Requisitos e Objetivos Principais do RVAgent

Este documento serve como especificação fundamental de requisitos para o desenvolvimento do RVAgent, estabelecendo:

1. **Contexto de Pesquisa**: Inserção em projeto maior de doutorado com três fases distintas
2. **Motivação do Problema**: Gap de cobertura identificado empiricamente na Fase 2 (20% cobertura geral vs 13% cobertura MOP)
3. **Objetivos Técnicos Core**:
   - Integração de análise estática (GATOR/WTG) com exploração dinâmica (LLM)
   - Classificação semântica de elementos de UI ([M], [DM])
   - Otimização de cobertura de operações monitoradas (não apenas cobertura geral)
4. **Abordagem de Implementação**: Arquitetura LangGraph com visão-LLM (Qwen2.5-VL)
5. **Critérios de Sucesso**: Superação da baseline de 13% de cobertura MOP, demonstrando eficácia de testes guiados para RV

As fases de implementação e avaliação subsequentes seguirão estas especificações fundamentais, com refinamentos baseados em descobertas empíricas durante o desenvolvimento.
