## PRIORITY 1: Fix Memory Sync (CRÍTICO)

### Problema Arquitetural

```python
# AgentFactory cria memórias
ui_coverage = UICoverageTracker()
short_term = ShortTermMemory()
long_term = LongTermMemory()

# MemoryCoordinator recebe todas
memory_coordinator = MemoryCoordinator(
    ui_coverage=ui_coverage,
    short_term=short_term,
    long_term=long_term
)

# RVAgent recebe apenas coordinator
agent = RVAgent(memory_coordinator=memory_coordinator)
# agent.ui_coverage NÃO EXISTE!

# Test script falha
if hasattr(agent, 'ui_coverage'):  # False!
    stats = agent.ui_coverage.get_overall_statistics()  # Never runs
```

### Solução: Facade Pattern

**MemoryCoordinator já coordena todas as memórias** - adicionar facade method

#### Implementação

**Arquivo**: `modules/rv-agent/src/rv_agent/memory/memory_coordinator.py`

Adicionar método:
```python
def get_all_statistics(self) -> Dict[str, Any]:
    """
    Unified facade for all memory statistics.

    Returns:
        Dictionary with ui_coverage, short_term, long_term, and graph stats
    """
    return {
        'ui_coverage': self.ui_coverage.get_overall_statistics(),
        'short_term': self.short_term.get_statistics(),
        'long_term': self.long_term.get_statistics() if self.long_term else {},
        'dynamic_graph': {
            'total_states': len(self.dynamic_graph.states),
            'total_transitions': len(self.dynamic_graph.transitions)
        }
    }
```

**Arquivo**: `modules/rv-agent/src/rv_agent/core/rv_agent.py`

Adicionar método de delegação:
```python
def get_memory_stats(self) -> Dict[str, Any]:
    """Get all memory statistics via coordinator facade."""
    return self.memory_coordinator.get_all_statistics()
```

Atualizar `run()` para incluir stats:
```python
def run(self) -> Dict[str, Any]:
    # ... existing execution ...

    # Collect memory stats before returning
    memory_stats = self.get_memory_stats()

    return {
        "status": "completed",
        # ... existing metrics ...

        # Add memory statistics
        "memory_stats": memory_stats
    }
```

## PRIORITY 2: Investigar V11 Outliers (APRENDIZADO)

### Objetivo

Entender por que certos apps causaram fallback excessivo no V11

### Apps Outliers

- `com.dozuki.ifixit`: 180 ações, 86.7% algoritmo (apenas 13.3% LLM)
- `org.secuso.privacyfriendlydicer`: 193 ações, 87.6% algoritmo (apenas 12.4% LLM)

**Padrão**: Ambos têm ~24 chamadas LLM (inicial allocation) depois 100% algoritmo

### Hipóteses

**H1: Prompts longos degradam qualidade LLM**
- V11 system: ~650 tokens
- Dynamic hints: +50-100 tokens
- Total: ~750 tokens/chamada

**H2: Instruções conflitantes confundem LLM**
- Múltiplas seções "HIGH PRIORITY"
- Pode gerar responses ambíguas

**H3: Loop detection agressivo**
- Apps com UI repetitiva triggam falsos positivos

### Análise dos Dados Reais

**Dados extraídos do teste V10/V11/V12 (28 apps × 3 prompts):**

#### ifixit V11:
```
- Total ações: 180
- LLM calls: 24 (13.3%)
- Algorithm: 156 (86.7%)
- Estados únicos: 6
- Transições: 5
- Ratio estados/ações: 1:30 (péssimo!)
- Tokens total: 77,909
- Tokens/ação: 432.8
```

#### dicer V11:
```
- Total ações: 193
- LLM calls: 24 (12.4%)
- Algorithm: 169 (87.6%)
- Estados únicos: 3
- Transições: 3
- Ratio estados/ações: 1:64 (TERRÍVEL!)
- Tokens total: 77,523
- Tokens/ação: 401.7
```

### Descobertas Críticas

**🔴 PROBLEMA IDENTIFICADO: Early LLM Failure + Algorithm Loop**

1. **Padrão idêntico nos 2 outliers**:
   - Ambos têm EXATAMENTE 24 chamadas LLM
   - Depois param de usar LLM completamente
   - Ficam 100% no algoritmo até timeout

2. **Hipótese confirmada: H1 (Prompts longos)**:
   - V11 prompts muito verbosos (~750 tokens)
   - LLM falha validação cedo (após ~24 iterações)
   - Sistema cai no fallback algorítmico
   - Algoritmo fica preso em loops (ratio 1:30 e 1:64!)

3. **Razão do fallback**:
   - Após 24 chamadas, LLM para de gerar tool calls válidos
   - Validation router detecta falha
   - Roteamento vai 100% para algoritmo
   - Algoritmo não tem lógica de loop avoidance sofisticada
   - Fica repetindo ações que não mudam estado

4. **Por que V10/V12 não têm esse problema?**:
   - V10: Prompts mais simples (~500 tokens) → LLM não falha
   - V12: Similar a V10 em estrutura → LLM mantém qualidade

### Learnings para V13

**✅ FAZER:**
1. **Prompts compactos** (<500 tokens total)
   - System prompt: ~300-350 tokens
   - User prompt: ~150-200 tokens
   - Total: ~450-550 tokens

2. **Instruções únicas e claras**
   - Uma prioridade principal, não múltiplas "HIGH PRIORITY"
   - Evitar verbosidade desnecessária
   - Foco no essencial

3. **Dynamic hints minimalistas**
   - Máximo 30-50 tokens quando presentes
   - Complementares, não duplicativos
   - Baseados em contagem de elementos

**❌ EVITAR:**
1. Prompts verbosos (>700 tokens)
2. Múltiplas seções de prioridade
3. Instruções redundantes ou conflitantes
4. Dynamic hints que duplicam informação já presente

### Conclusão da Investigação

**Hipótese H1 CONFIRMADA**: Prompts longos (~750 tokens no V11) causam degradação da qualidade do LLM após ~24 iterações, levando a fallback permanente para algoritmo e loops de ações improdutivas.

**Impacto**: V13 DEVE ter prompts compactos (<500 tokens) para evitar esse problema.

## PRIORITY 3: Design V13 (PROMPT COMPACTO)

### Princípios

1. **Simplicidade**: <500 tokens total (system + user)
2. **Clareza**: Instruções não-ambíguas
3. **Essencialidade**: Apenas o necessário

### Componentes Obrigatórios

**Coordenadas** (obrigatório):
- Screen: 704x1248 pixels
- Formato: `at position (x, y)`
- Tools: `android_click(x, y)`, `android_type_text(x, y, "text")`

**Monitored Operations Markers** (obrigatório):
- `[M]`: reaches_mop - método alcança algum método de especificação MOP
- `[DM]`: directly_reaches_mop - método chama diretamente método MOP
- **Objetivo**: Aumentar detecção de erros MOP exercitando esses métodos
- **Problema conhecido**: Priorizar demais causa LLM chamar apenas esses ou não popular forms

**Análise Estática** (opcional):
- Nem todos apps têm análise estática
- Quando disponível, markers [M] e [DM] aparecem nos elementos

### Estrutura V13

**System Prompt** (~300-350 tokens):
```
Role: Android UI testing agent for systematic exploration

OBJECTIVE: Exercise application to trigger monitored operations and detect specification violations.

COORDINATE SYSTEM:
- Screen resolution: 704x1248 pixels
- Use EXACT coordinates from UI element descriptions
- Format: android_click(x, y) or android_type_text(x, y, "text")

ELEMENT MARKERS:
- [M]: Reaches monitored operation - method reaches MOP specification method
- [DM]: Directly reaches monitored operation - method directly calls MOP method
- [UNTESTED]: Element not yet tested - explore when appropriate

NOTE: Prioritize testing monitored operations ([M], [DM]) but ensure forms are
filled before submission and explore systematically.

STRATEGY: Depth-first exploration
- Test new elements before retesting known ones
- Fill required fields before clicking submit buttons
- Explore different execution paths
```

**User Prompt** (~150-200 tokens):
```
Current screen: {activity_name}

UI ELEMENTS:
{ui_elements_text}  # Pre-formatted with coordinates + markers

RECENT ACTIONS (last 5):
{action_history_summary}

NAVIGATION PATH:
{navigation_path}

Select next action using available tools.
```

**Total estimado**: ~450-550 tokens (vs V10 ~600, V11 ~750, V12 ~700)

### O que REMOVER

❌ Seção de permissões (V12: ~150 tokens)
❌ "HIGH PRIORITY ACTIONS" extenso (V11: ~100 tokens)
❌ Dynamic hints por substring matching (V11: duplicação)
❌ Instruções redundantes

### O que MANTER/MELHORAR

✅ Coordenadas exatas
✅ Markers [M] e [DM]
✅ Estratégia DFS clara
✅ Formato de ferramentas
✅ Contexto de navegação
✅ **Dynamic hints MELHORADOS**: Detectar por contagem de elementos, hints complementares (~30-50 tokens)

### Implementação

**Arquivo**: `modules/rv-agent/src/rv_agent/prompts/v13.py`

```python
"""
V13: Compact and efficient prompt with smart dynamic hints.

Key improvements over V10/V11/V12:
- Compact system prompt (~350 tokens)
- Smart dynamic hints (complementary, not duplicative)
- Detect by element counts, not substring matching
- Clear MOP prioritization without over-emphasis
- No permission-specific instructions

Dynamic hints add ~30-50 tokens when relevant, providing actionable guidance
without duplicating information already in categorized sections.
"""

SYSTEM_PROMPT = """
You are an Android UI testing agent for systematic application exploration.

OBJECTIVE: Exercise the application to trigger monitored operations and detect
specification violations through comprehensive testing.

COORDINATE SYSTEM:
- Screen resolution: 704x1248 pixels
- Use EXACT coordinates from UI element descriptions below
- Tools: android_click(x, y), android_type_text(x, y, "text"), android_scroll(direction)

ELEMENT MARKERS:
- [M]: Reaches monitored operation - explores execution paths to MOP methods
- [DM]: Directly reaches monitored operation - directly invokes MOP methods
- [UNTESTED]: Not yet tested - prioritize exploration

IMPORTANT: Test monitored operations ([M], [DM]) but fill forms completely
before submitting. Balance exploration of new areas with thorough testing.

STRATEGY: Depth-first systematic exploration
1. Test new elements before retesting known elements
2. Fill all required fields (EditText) before clicking submit buttons
3. Explore different navigation paths to discover functionality
4. Use BACK strategically to explore alternative paths

Use the android_* tools to interact with elements at their exact coordinates.
"""

def build_user_message(
    state: AgentState,
    text_input_count: int = 0,
    spinner_count: int = 0,
    has_scrollable: bool = False
) -> str:
    """
    Build user message with smart dynamic hints.

    Hints complement categorized sections without duplicating information.
    Detection based on element counts from ScreenProcessor, not substring matching.

    Args:
        state: Current agent state with ui_elements_text, etc
        text_input_count: Number of text input fields detected
        spinner_count: Number of spinners/dropdowns detected
        has_scrollable: Whether screen has scrollable content

    Returns:
        User message with optional actionable hints
    """
    # Build actionable hints (complementary, not duplicative)
    hints = []

    if text_input_count > 0:
        hints.append("💡 Fill text fields before submitting forms")

    if spinner_count > 0:
        hints.append("💡 Open dropdowns to see available options")

    if has_scrollable:
        hints.append("💡 Scroll to discover content below the fold")

    # Format hints section (only if hints exist)
    hints_section = ""
    if hints:
        hints_section = "HINTS: " + " | ".join(hints) + "\n\n"

    return f"""Current screen: {state['current_activity']}

{hints_section}=== UI ELEMENTS ===
{state['ui_elements_text']}

=== RECENT ACTIONS (last 5) ===
{state['action_history_summary']}

=== NAVIGATION PATH ===
{state['navigation_path']}

Select your next action using the available android_* tools.
"""
```

## Notas Importantes

### AgentMemoryManager vs MemoryCoordinator

**NÃO renomear nada**:
- `AgentMemoryManager`: Mantém responsabilidade atual (summaries)
- `MemoryCoordinator`: Adiciona facade method `get_all_statistics()`
- São componentes diferentes com responsabilidades diferentes

### Dynamic Hints (V11)

**O que eram**: Instruções adicionadas dinamicamente ao prompt:
- ListView detectado → "Try scrolling to see more items"
- EditText vazio → "Fill text fields before submitting"
- Spinner → "Try opening dropdowns"

**V13**: SEM dynamic hints - apenas prompt estático

### Monitored Operations Context

**Objetivo principal**: Aumentar detecção de erros MOP

**Estratégia**:
- Exercitar métodos marcados [M] e [DM]
- Gerar trace suficiente para monitors chegarem a veredito
- **Balanceamento**: Não priorizar demais (causa LLM ignorar resto)

**Conjuntos de especificações**:
1. JCA (Java Cryptography API) - uso indevido de criptografia
2. Generic (hasNext antes de next, etc)

**Nota**: Usar "monitored operations", não "segurança" (não é sempre security)
