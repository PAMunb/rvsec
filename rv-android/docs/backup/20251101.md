# RVAgent Tool Calling Implementation

**Data:** 2025-11-01
**Objetivo:** Implementar tool calling nativo com vision model para Android testing
**Modelo:** Qwen 2.5VL 7B com Modelfile customizado (qwen-vision-tools-v1)

---

## Problema Identificado

Análise de testes em 14 aplicações Android revelou:

- **23.6% UNKNOWN actions**: Ações geradas pelo LLM não executadas no device
- **0% TYPE_TEXT**: EditText detectados mas não recebem input de texto
- **65.8% BACK dominante**: Loops causados pelos problemas acima
- **Device/LLM ratio 0.23**: Apenas 23% das iterações do LLM resultam em ação real

### Causa Raiz

1. **Parsing manual**: Código extrai ações de texto livre via regex, não usa tool calling
2. **Screen description sem coordenadas**: UI elements descritos sem posição espacial
3. **Matching failures**: LLM gera targets incompatíveis com formato esperado

---

## Solução: Tool Calling com Vision Model

### Arquitetura

```
Vision Model (Qwen 2.5VL 7B)
    ↓ (bind_tools)
LangGraph Workflow:
    observe → assistant → ToolNode → update_memories → END
                ↑          ↓
                └─────────┘ (tools_condition)
```

### Componentes

**Android Tools** (`android_tools.py` - já implementado):
- `android_click(element_description, x, y)`: Click em coordenadas
- `android_type_text(element_description, x, y, text)`: Input de texto
- `android_long_click(element_description, x, y)`: Long press
- `android_back()`: Navegação back
- `android_home()`: Navegação home

**Vision Model Capabilities**:
- Análise visual de screenshots Android
- Identificação de elementos interativos
- Seleção de coordenadas apropriadas (98.3% precisão em testes)
- Suporte a elementos DOM e não-DOM (canvas, jogos, renderização dinâmica)

---

## Decisões de Design

### 1. Hybrid Approach: DOM + Visual Elements

**Elementos DOM** (presentes no screen description):
- Coordenadas explícitas fornecidas ao LLM
- Formato: `EditText 'Email' at position (540, 300) - bounds[[100, 250], [980, 350]]`
- Validação: Coordenadas geradas devem corresponder a elemento conhecido (±20px)

**Elementos não-DOM** (canvas, jogos, elementos dinâmicos):
- LLM analisa visualmente e gera coordenadas
- **Sem validação estrita**: Aceitar coordenadas dentro de screen bounds (0-1080, 0-1920)
- Justificativa: Elementos renderizados dinamicamente não aparecem na árvore de views

### 2. Tool Result Validation

```python
# Validação em dois níveis:

# Nível 1: Coordenadas dentro dos limites da tela
if 0 <= x <= 1080 and 0 <= y <= 1920:
    valid_coords = True

# Nível 2 (opcional): Match com elemento DOM
screen_item = find_item_by_coords(x, y, tolerance=20)
if screen_item:
    # Elemento DOM confirmado
    use_item_actions(screen_item)
else:
    # Elemento possivelmente não-DOM (aceitar)
    execute_visual_coords(x, y)
```

### 3. LangGraph Workflow

**Stateless Processing**:
- Cada iteração recebe state fresh (evita context overflow em Ollama)
- Mensagens construídas from scratch com screen state + history summary
- External loop gerencia iterações (não internal graph loop)

**Node Responsibilities**:
- `observe`: Captura screenshot + screen description
- `assistant`: LLM invocation com tool calling
- `ToolNode`: Execução automática de tools (LangGraph built-in)
- `update_memories`: Processa tool results, atualiza estado, captura próxima tela

**Função**: `_build_agent_graph()`

```python

workflow.add_node("tools", ToolNode(self.tools))
workflow.add_node("update_memories", self._update_memories_node)
```

**tools_condition**: Routing automático baseado em tool_calls na resposta do LLM

#### 4. Assistant Node

**Função**: `_assistant_node()`

```python
def _assistant_node(self, state: AgentState) -> AgentState:
    """LLM decides action via tool calling."""
    message = self._build_message(state)
    response = self.llm.invoke([message])
    return {"messages": [response]}
```

**Simplificação**: Sem parsing manual, LangGraph roteia automaticamente

#### 5. Memory Update Node

**Nova função**: `_update_memories_node()`

```python
def _update_memories_node(self, state: AgentState) -> AgentState:
    """
    Process tool execution results.

    Steps:
    1. Extract tool_calls from messages
    2. ToolNode already executed tools, get results
    3. Map coordinates to ScreenItem (if DOM element)
    4. Update short_term_memory with action
    5. Update long_term_memory with transition
    6. Capture next screen state
    """
    tool_messages = [m for m in state["messages"] if isinstance(m, ToolMessage)]

    for tool_msg in tool_messages:
        coords = extract_coords_from_tool_call(tool_msg)

        # Try to find DOM element (optional validation)
        screen_item = self._find_item_by_coords(coords, state["screen_description"])

        # Update memories regardless of DOM match
        # (elementos não-DOM são válidos)
        self.short_term_memory.add_action(...)
        self.long_term_memory.add_transition(...)

    # Capture next state
    new_screenshot = self.device.take_screenshot()
    new_screen_desc = self.device.get_screen_description()

    return {**state, "screenshot": new_screenshot, "screen_description": new_screen_desc}
```

#### 6. Coordinate to ScreenItem Mapping

**Nova função**: `_find_item_by_coords()`

```python
def _find_item_by_coords(self, coords: Tuple[int, int], screen_desc, tolerance: int = 20):
    """
    Map coordinates to ScreenItem with fuzzy bounds matching.

    Returns:
        ScreenItem if DOM element found, None otherwise

    Note: None result does NOT mean invalid action.
    Elementos não-DOM (canvas, games) are valid but unmatchable.
    """
    x, y = coords

    for item in screen_desc.items:
        bounds = item.view.get('bounds')
        if not bounds or len(bounds) != 2:
            continue

        [[x1, y1], [x2, y2]] = bounds

        # Check if coords within bounds (with tolerance)
        if (x1 - tolerance <= x <= x2 + tolerance) and \
           (y1 - tolerance <= y <= y2 + tolerance):
            return item

    return None  # Not DOM element, possibly visual/dynamic element
```

## Considerações de Implementação

### 1. Código Legado

**Política**: Remover completamente, sem adapters de compatibilidade

- Parsing manual → Tool calling nativo
- Manual execution → ToolNode automático
- Regex matching → Coordinate-based validation

**Backup**: `backup/2025-11-01_pre-toolcalling/`

### 2. Comentários no Código

**Diretrizes**:
- Refletir estado atual (não histórico de migração)
- Sem termos de viés (moderna, sofisticada, avançada)
- Sem linguagem promocional
- Público-alvo: desenvolvedores e pesquisadores
- Foco técnico objetivo

**Exemplo ruim**:
```python
# Modern approach using sophisticated tool calling (migrated from legacy parsing)
```

**Exemplo bom**:
```python
# LLM invocation with tool calling support
```

### 3. Elementos Não-DOM

**Justificativa para vision model**:
- Jogos renderizam UI via canvas (não-DOM)
- Elementos dinâmicos não aparecem na árvore de views
- Botões customizados em engines de jogos
- Interfaces WebView com rendering JavaScript

**Validação híbrida**:
```python
# Tentar match DOM (para logging e action selection)
screen_item = find_item_by_coords(x, y)

if screen_item:
    logger.info(f"DOM element matched: {screen_item}")
    use_item_actions = True
else:
    logger.info(f"Visual element (non-DOM): coords ({x}, {y})")
    use_visual_coords = True  # Igualmente válido!
```

**Métrica de sucesso**: Device action executada, independente de DOM match

### 4. Coordinate Validation Levels

**Nível 1: Screen bounds** (obrigatório)
```python
valid = (0 <= x <= 1080) and (0 <= y <= 1920)
```

**Nível 2: DOM match** (opcional, informativo)
```python
screen_item = find_item_by_coords(x, y, tolerance=20)
dom_matched = screen_item is not None
```

**Critério de aceitação**: Nível 1 suficiente para elementos não-DOM
