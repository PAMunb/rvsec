# Plano de Otimização e Avaliação de LLMs para RV-Android

## 1. Introdução
### 1.1 Objetivo
Este plano detalha o processo de seleção, treinamento e otimização contínua de Large Language Models (LLMs) para serem utilizados no framework de teste RV-Android. O foco é garantir a máxima eficácia na geração de ações de teste para aplicativos Android, considerando as restrições de recursos (8GB de VRAM) e a necessidade de um ciclo de melhoria contínua baseado em dados reais.

### 1.2 Ferramentas Utilizadas (RV-Android LLM Evaluator e RV-Android Test Framework)
O processo utilizará duas ferramentas complementares do ecossistema RV-Android:
* **RV-Android LLM Evaluator:** Para a triagem inicial e pré-seleção de modelos LLM candidatos.
* **RV-Android Test Framework:** Para a avaliação aprofundada, orquestração de testes em aplicativos reais, coleta de dados dinâmicos e análise de desempenho do modelo otimizado.

---

## 2. Fase de Pré-Seleção de Modelos (Triagem Inicial)
### 2.1 Propósito
A pré-seleção tem como objetivo identificar rapidamente um ou poucos modelos LLM que sejam candidatos viáveis para a otimização, atendendo aos requisitos básicos de compatibilidade com o ambiente RV-Android e as restrições de hardware.

### 2.2 Processo de Execução com RV-Android LLM Evaluator
O RV-Android LLM Evaluator será configurado para testar múltiplos modelos LLM disponíveis via Ollama (e.g., Llama, Phi, Gemma, Qwen, suas variantes de diferentes tamanhos e quantizações) em um conjunto padronizado de prompts representativos da tarefa de geração de ações de teste. Estes prompts serão projetados para serem simples, de modo a testar a capacidade básica de compreensão e geração de formato.

### 2.3 Critérios de Seleção de Candidatos (8GB VRAM, Sucesso de Parsing, Latência)
Os modelos serão avaliados pelos seguintes critérios essenciais:
* **Compatibilidade com 8GB VRAM:** Verificação da capacidade do modelo de ser carregado e executado eficientemente dentro do limite de memória da GPU. Modelos que excedam este limite serão descartados.
* **Sucesso de Parsing:** A porcentagem de respostas do LLM que o `ResponseProcessor` do RV-Android consegue parsear corretamente em ações válidas. Modelos com baixa taxa de sucesso de parsing (indicando formato inadequado ou incompreensão) serão priorizados para descarte.
* **Latência de Resposta:** Tempo médio que o modelo leva para gerar uma resposta após o prompt, visando identificar modelos ágeis para o ciclo de testes.
* **Coerência Básica:** Uma avaliação qualitativa inicial da coerência das ações geradas, mesmo que não perfeitas, para garantir que o modelo não esteja gerando ruído aleatório.

### 2.4 Resultados Esperados
Ao final desta fase, teremos uma lista curta de 1 a 3 modelos LLM candidatos que atendem aos requisitos técnicos e demonstram o potencial para serem otimizados nas fases subsequentes. A documentação registrará as métricas de triagem e a justificativa para a seleção dos candidatos.

## 3. Fase de Treinamento Inicial e Adaptação ao Domínio
### 3.1 Propósito
Esta fase visa adaptar o modelo LLM candidato selecionado ao domínio específico de teste de aplicativos Android e ensiná-lo a seguir instruções precisas para a geração de ações, utilizando técnicas de ajuste fino eficiente de parâmetros (PEFT) para gerenciar as restrições de recursos.

### 3.2 Planejamento do Pipeline de Dados de Treinamento
Um pipeline de dados robusto é fundamental para o sucesso do treinamento. Ele garante que os dados estejam no formato correto, sejam acessíveis e possam ser atualizados e gerenciados de forma eficiente.

#### 3.2.1 Aquisição e Curadoria de Dados de Domínio
* **Fontes:** Coleta de um volume significativo de dados textuais relacionados ao domínio Android. Isso inclui, mas não se limita a:
    * Documentação oficial do Android (APIs, guias de componentes UI).
    * Fóruns de desenvolvedores (e.g., Stack Overflow, Android Developers Blog).
    * Artigos e livros sobre desenvolvimento e teste de aplicativos Android.
    * Descrições de interfaces de usuário (UI) de aplicativos existentes ou fictícios.
    * Relatórios de bugs e discussões sobre falhas de aplicativos.
* **Formato:** Preferencialmente texto simples (`.txt`), Markdown (`.md`) ou HTML (`.html`) para facilitar o pré-processamento.
* **Curadoria:** Processos iniciais de limpeza para remover informações irrelevantes ou ruído, embora para o DAPT, um grau de ruído seja aceitável dado o volume.
* **Armazenamento:** Os dados serão armazenados em um diretório dedicado para dados de pré-treinamento, possivelmente organizados por tipo de fonte.

#### 3.2.2 Aquisição e Curadoria do Dataset de Instrução Inicial (Manual)
* **Fontes:** Geração manual de aproximadamente 200 exemplos de alta qualidade, criados por especialistas em teste ou curados a partir de cenários de teste ideais.
* **Conteúdo:** Cada exemplo será um par que descreve um **contexto de UI e uma instrução de teste**, e a **ação de teste desejada** correspondente. O contexto de UI incluirá informações como elementos visíveis, IDs, textos, estados e hierarquia. A instrução de teste será o prompt que se espera que o LLM responda.
* **Formato:** Serão armazenados em formato JSON Lines (`.jsonl`), onde cada linha é um objeto JSON contendo as chaves `instruction`, `input` (contexto da UI) e `output` (ações de teste desejadas).
* **Exemplo de Estrutura de um Exemplo:**
    ```json
    {
      "instruction": "Navegue para a tela de configurações do usuário clicando no ícone apropriado.",
      "input": "{\"screen_name\": \"Home Screen\", \"elements\": [{\"id\": \"user_profile_icon\", \"type\": \"ImageView\", \"text\": \"\"}, {\"id\": \"search_button\", \"type\": \"Button\", \"text\": \"Buscar\"}]}",
      "output": "[{\"action_type\": \"click\", \"target_id\": \"user_profile_icon\"}]"
    }
    ```
* **Curadoria:** Revisão minuciosa para garantir a precisão, clareza e diversidade dos exemplos, cobrindo casos comuns e algumas variações.

#### 3.2.3 Formato e Estrutura dos Dados para PEFT
* **Padronização:** Ambos os datasets (domínio e instrução) serão pré-processados para se adequarem ao formato esperado pelas bibliotecas PEFT (e.g., Hugging Face `datasets` ou `transformers`).
* **Tokenização:** Os dados serão tokenizados usando o tokenizer do modelo LLM base selecionado, garantindo que estejam prontos para o treinamento.
* **Armazenamento de Datasets Processados:** Os datasets tokenizados serão salvos em um formato otimizado (e.g., binário ou formato `arrow` do Hugging Face `datasets`) para carregamento rápido durante o treinamento.

### 3.3 Treinamento de Adaptação ao Domínio (DAPT com PEFT)
* **Modelo Base:** Utilização do modelo LLM candidato selecionado na Fase 1.
* **Técnica:** Aplicação de **PEFT (Low-Rank Adaptation - LoRA ou Quantized Low-Rank Adaptation - QLoRA)** para continuar o pré-treinamento do modelo. Apenas as camadas adaptadoras LoRA serão treinadas, mantendo o modelo base congelado.
* **Dataset:** A carga grande de dados textuais do domínio Android (definida em 3.2.1).
* **Ambiente:** O treinamento será executado em um ambiente configurado para utilizar a GPU com 8GB de VRAM, otimizado para as bibliotecas PEFT.
* **Saída:** O modelo base com o adaptador LoRA treinado em dados do domínio Android.

### 3.4 Treinamento de Instrução Inicial (IFT com PEFT)
* **Modelo Base:** O modelo resultante da etapa DAPT (ou o modelo LLM candidato original, se DAPT não for realizado nesta fase).
* **Técnica:** Aplicação de **PEFT (LoRA/QLoRA)** no modelo base/adaptado. Um novo adaptador LoRA ou a continuação do treinamento do adaptador existente será utilizada.
* **Dataset:** O dataset de instrução inicial, manualmente curado (definido em 3.2.2).
* **Ambiente:** O mesmo ambiente de treinamento otimizado para 8GB de VRAM.
* **Saída:** O modelo com o adaptador LoRA treinado nas instruções de teste, pronto para ser avaliado pelo RV-Android Test Framework.

### 3.5 Modelo Resultante
Ao final desta fase, teremos um modelo LLM (com seus adaptadores LoRA) que foi adaptado ao domínio Android e ajustado para gerar ações de teste a partir de instruções. Este modelo será o foco da próxima fase de avaliação e otimização aprofundada.

## 4. Fase de Avaliação Aprofundada e Otimização Inicial
### 4.1 Propósito
Esta fase tem como objetivo realizar uma avaliação rigorosa e multifacetada do modelo treinado, utilizando as capacidades avançadas do RV-Android Test Framework para identificar seu desempenho real e otimizar as estratégias de prompt e outros parâmetros.

### 4.2 Definição de Test Suites no RV-Android Test Framework
* **Configuração:** Utilização do `ConfigGenerator` para criar `TestSuite`s que contemplem o modelo recém-treinado.
* **Parâmetros:** Os testes incluirão variações em:
    * **Estratégias de Prompt:** Experimentação com diferentes templates de prompts, inclusão/exclusão de exemplos (few-shot), e uso de técnicas como Chain-of-Thought.
    * **Tipos de Parsers:** Avaliação de diferentes implementações de `ResponseProcessor` para verificar qual melhor se adapta à saída do modelo.
    * **Tipos de Visitors:** Teste com diferentes abordagens de coleta de contexto de UI (`Visitor Pattern`) para ver qual fornece a informação mais útil para o modelo.
    * **Timeouts:** Múltiplos valores de `timeout` (e.g., 60s, 120s, 180s, 300s, 600s) para a análise de platô (`PlateauAnalyzer`).
    * **Aplicações:** Testes em uma variedade de aplicativos para garantir a robustez e generalização do modelo.

### 4.3 Execução de Testes e Coleta de Métricas
* **Orquestração:** O `TestFramework` coordenará a execução dos testes em cada combinação de configuração (modelo, prompt, parser, visitor, app, repetição).
* **Coleta:** O `TestResult` e `ConfigurationMetrics` coletarão um conjunto abrangente de métricas, incluindo:
    * Cobertura de código/UI (se o framework coletar).
    * Sucesso de execução de ações (sem crashes).
    * Número de ações geradas e executadas.
    * Tempo de resposta do LLM e tempo total de execução.
    * Sucesso de parsing das ações.
    * Métricas de qualidade de ação (a serem definidas, ex: relevância, correção semântica, impacto no teste).
    * Métricas específicas de `Batch Action Strategy` (se aplicável), como redução de chamadas LLM e ganho de eficiência.

### 4.4 Análise Aprofundada de Desempenho e Comportamento
* **Processamento de Resultados:** O `ResultAnalyzer` processará as métricas brutas em resultados comparáveis.
* **Análise de Platô:** O `PlateauAnalyzer` identificará o ponto de rendimento decrescente para o tempo de execução, ajudando a otimizar os `timeouts`.
* **Análise de Correlação:** O `CorrelationAnalyzer` buscará relações entre as características dos aplicativos (extraídas da análise estática) e o desempenho das diferentes configurações do LLM, para fornecer recomendações contextuais.
* **Identificação de Anomalias:** O `AnomalyDetector` auxiliará na detecção de comportamentos inesperados.

### 4.5 Identificação de Estratégias Ótimas (Prompts, Parsers, Visitors)
Com base na análise dos resultados, serão identificadas as combinações de:
* **Estratégia de Prompt:** O formato de prompt que melhor extrai as capacidades do modelo ajustado para a tarefa de teste.
* **Parser:** O `ResponseProcessor` mais eficaz para interpretar as saídas do modelo.
* **Visitor:** A abordagem de coleta de contexto de UI que mais contribui para a precisão das ações.
Esta otimização inicial é crucial para estabelecer a melhor "configuração de inferência" para o modelo.

### 4.6 Geração de Linha de Base de Desempenho
Um relatório completo será gerado (`SpreadsheetExporter`, `Dashboard`) consolidando todas as métricas e análises. Este relatório servirá como a linha de base de desempenho para o modelo e suas configurações, permitindo comparações futuras e medição do progresso nas etapas de otimização contínua.

## 5. Fase de Otimização Contínua e Dataset Dinâmico
### 5.1 Propósito
Esta fase estabelece um ciclo de feedback contínuo, onde o desempenho do modelo é aprimorado incrementalmente através da coleta de dados de execuções reais, curadoria e re-treinamento iterativo, garantindo que o LLM se adapte e melhore sua performance em cenários de teste diversificados e complexos.

### 5.2 Geração de Dataset Dinâmico via Execução do Sistema Real
#### 5.2.1 Coleta de Dados Brutos pelo Test Framework
* **Execução:** O `Test Framework` será configurado para executar testes em aplicativos reais usando o modelo ajustado e as configurações ótimas identificadas na Fase 4.
* **Coleta:** Durante cada execução, o framework coletará:
    * O **contexto completo da UI** (conforme o `Visitor`) enviado ao LLM.
    * O **prompt exato** formulado e enviado ao LLM.
    * A **resposta bruta** gerada pelo LLM.
    * A **ação parseada e executada** pelo `ResponseProcessor`.
    * **Métricas de Execução:** Sucesso/falha da ação, impacto no estado do aplicativo (e.g., crash, navegação esperada, falha de validação).
    * **Feedback/Anomalias:** Marcação de ações que levaram a resultados indesejados, ou que o `AnomalyDetector` possa sinalizar.

#### 5.2.2 Validação e Curadoria dos Dados Dinâmicos
* **Análise de Falhas:** Os dados coletados serão analisados para identificar instâncias onde o LLM gerou ações incorretas, ineficazes, mal formatadas ou que levaram a resultados negativos.
* **Curadoria Humana/Semi-Automatizada:** Para cada falha identificada, a ação gerada pelo LL LLM será corrigida ou uma ação ideal será fornecida manualmente por um especialista em teste. Este processo gerará novos pares `(contexto da UI + instrução de teste) -> ação de teste desejada`.
* **Expansão de Casos de Borda:** Além das correções de erros, novos cenários de teste complexos ou de borda que não estavam no dataset inicial serão adicionados.

#### 5.2.3 Processamento e Inclusão no Pipeline de Dados de Treinamento
* **Formato Consistente:** Os novos exemplos curados serão formatados para se alinharem à estrutura do dataset de instrução (JSON Lines, conforme 3.2.2).
* **Atualização do Dataset:** Os novos exemplos serão adicionados ao dataset de instrução existente, enriquecendo-o e corrigindo lacunas de desempenho. É crucial gerenciar versões do dataset para rastrear o progresso.
* **Tokenização:** O dataset combinado será tokenizado novamente, pronto para o re-treinamento.

### 5.3 Re-treinamento Iterativo do Modelo (Continuação do PEFT)
* **Ação:** O modelo LLM (com seus adaptadores LoRA) será re-treinado usando o dataset de instrução atualizado (agora incluindo os exemplos dinâmicos curados). Isso será feito continuando o treinamento do adaptador LoRA existente, sem a necessidade de reiniciar do zero.
* **Frequência:** Os ciclos de re-treinamento serão determinados pela quantidade de novos dados curados e pela necessidade de melhoria. Podem ser semanais, quinzenais, ou após a acumulação de um número X de novos exemplos.
* **Otimização de Hiperparâmetros:** Pequenos ajustes nos hiperparâmetros de treinamento (e.g., learning rate, número de épocas) podem ser feitos em cada iteração para otimizar a convergência.

### 5.4 Avaliação Iterativa e Monitoramento de Progresso
* **Avaliação Pós-Treinamento:** Após cada ciclo de re-treinamento, o RV-Android Test Framework será utilizado novamente (conforme a Fase 4) para avaliar o modelo aprimorado usando o conjunto fixo de prompts de teste e, opcionalmente, novos prompts derivados dos casos problemáticos recém-adicionados.
* **Monitoramento:** As métricas de desempenho serão comparadas com a linha de base (Fase 4.6) e com as iterações anteriores para monitorar o progresso, identificar regressões e validar a eficácia dos novos dados de treinamento.
* **Relatórios de Progresso:** Geração de relatórios periódicos para documentar a melhoria do modelo ao longo do tempo.

### 5.5 Refinamento do Processo de Curadoria
Com o tempo, o processo de curadoria de dados dinâmicos pode ser aprimorado, talvez com ferramentas de anotação de UI ou scripts que pré-selecionem interações para revisão humana, tornando o ciclo de feedback mais eficiente.

## 6. Conclusão e Próximos Passos
Este plano detalha uma abordagem sistemática para otimizar LLMs para teste de aplicativos Android. Começando com uma triagem eficiente, passando por uma adaptação robusta ao domínio e instrução, e culminando em um ciclo contínuo de melhoria impulsionado por dados reais, o objetivo é alcançar um desempenho de teste superior e eficiente. Os próximos passos incluirão a implementação e execução da Fase de Pré-Seleção de Modelos e o desenvolvimento detalhado do pipeline de dados de treinamento conforme planejado.

## Apêndice A: Versão Simplificada do Treinamento com Dataset Externo em Etapas
### A.1 Visão Geral
Esta versão simplificada do treinamento em etapas se aplica quando não se deseja uma curadoria tão intensiva ou quando datasets complementares já estão disponíveis. A ideia é treinar o modelo sequencialmente em diferentes datasets, cada um adicionando uma camada de conhecimento ou especialização.

### A.2 Fase 1: Treinamento com Dataset A (e.g., Dados de Domínio)
* **Dataset:** Um dataset grande contendo dados textuais gerais relacionados ao domínio Android (documentação, códigos, relatórios).
* **Propósito:** Adaptar o vocabulário e a compreensão do modelo ao domínio de teste de aplicativos.
* **Técnica:** Utilização de PEFT (LoRA/QLoRA) sobre o modelo base (selecionado na triagem inicial). O modelo aprenderá a reconhecer padrões e terminologia do Android.
* **Saída:** Um modelo com adaptadores LoRA treinados em "Androidês".

### A.3 Fase 2: Treinamento com Dataset B (e.g., Dados de Instrução de Ações)
* **Dataset:** Um dataset menor e mais focado, contendo pares de `(contexto da UI + instrução) -> ação de teste desejada`. Este dataset complementa o conhecimento de domínio com a habilidade de seguir instruções específicas para a tarefa.
* **Propósito:** Ensinar o modelo a interpretar instruções e gerar ações de teste formatadas corretamente.
* **Técnica:** Continuação do treinamento do adaptador LoRA (ou um novo adaptador, dependendo da estratégia) do modelo da Fase 1, agora com o dataset de instrução. O modelo já tem um bom entendimento do domínio e agora aprende a aplicar esse conhecimento para responder a comandos de teste.
* **Saída:** O modelo final, especializado tanto no domínio quanto na tarefa de geração de ações.

### A.4 Considerações para o Pipeline de Dados
Nesta versão, o "Planejamento do Pipeline de Dados de Treinamento" (Seção 3.2 do plano principal) se concentraria em garantir que os Datasets A e B estejam disponíveis, limpos, no formato correto e tokenizados para cada estágio de treinamento. A curadoria manual dos 200 exemplos seria parte do Dataset B. A transição entre as fases seria a carga do modelo treinado da Fase 1 para continuar o treinamento na Fase 2. Este processo pode ser iterado com outros datasets (e.g., dados de segurança, dados de performance) se necessário.
