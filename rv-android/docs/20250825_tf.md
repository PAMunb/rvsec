# RV-Android Test Framework Architecture Plan

## Overview

This document outlines the architecture plan for the RV-Android Test Framework module (`rv-test-framework`), designed to evaluate different configurations of AI-driven Android testing tools within the RV-Android modular ecosystem.

## System Architecture Principles

### Core Design Decisions

- **Module Integration**: The test framework adapts to existing module interfaces without modifying business classes from other modules
- **Configuration Strategy**: Manual configuration definition provides precise control over test scenarios
- **Execution Model**: Parallel execution with intelligent grouping by LLM model to optimize GPU memory usage
- **Metrics Collection**: Post-execution parsing strategy for consistent data collection
- **Simplicity First**: User responsibility for configuration validation and resource management

### Integration Constraints

The test framework operates within the RV-Android modular architecture constraints:

- **No Business Class Modifications**: Existing domain models, services, and utilities remain unchanged
- **Interface Compatibility**: All integrations use existing module public interfaces
- **User Responsibility**: Users manage worker count (3-10) and configuration correctness
- **Error Handling**: Integrates with existing ErrorHandler infrastructure
- **Logging**: Uses LoggingManager with proper context propagation

## Execution Flow

### Test Execution Lifecycle

```
1. Configuration Loading and Task Creation
   ├── Load predefined configurations (user responsibility for correctness)
   ├── Convert to LLMConfig and ToolConfig objects
   ├── Create Task objects using rv-android-core TaskFactory
   └── Group Task objects by LLM model type

2. Model Group Execution using Existing Infrastructure
   ├── Execute first model group using TaskExecutor pool
   ├── Each worker runs TaskExecutor with Task and RVAndroidTool
   ├── Parallel execution (user-defined worker count 3-10)
   ├── Results automatically captured by PerformanceMonitor
   └── Individual task failures isolated to worker processes

3. Simple Model Transition
   ├── Wait for all tasks in current model group to complete
   ├── Execute ollama stop <model> command
   ├── Sleep for 30-60 seconds for VRAM cleanup
   └── Proceed to next model group

4. Results Processing using Existing Tools
   ├── Parse execution logs and traces using existing parsers
   ├── Extract metrics from PerformanceMonitor automatically
   ├── Calculate coverage using rv-coverage tools
   ├── Analyze action distributions from logcat files
   └── Generate reports using existing report generation

5. Analysis and Plateau Detection
   ├── Run plateau analysis on collected metrics
   ├── Generate timeout optimization recommendations
   └── Export results in standard formats
```

### Parallel Execution Strategy with Port Management

```python
"""
Worker process implementation using existing TaskExecutor infrastructure with emulator port allocation.

Each worker process executes a single Task object using the existing rv-platform TaskExecutor,
with unique emulator ports assigned to enable true parallel execution without conflicts.

### Process Isolation Strategy:
- **TaskExecutor Integration**: Uses existing rv-platform TaskExecutor for execution
- **Task Object Execution**: Executes Task objects with assigned emulator ports
- **Port Allocation**: Automatic emulator port assignment for parallel workers
- **Existing Infrastructure**: Leverages EmulatorManager, ToolFactory, error handling
- **Error Isolation**: Worker failures handled through existing ErrorHandler infrastructure

### Emulator Port Management:
- **Port Allocation**: Framework assigns unique ports [5554, 5556, 5558, 5560, 5562] for workers
- **Task Configuration**: Emulator port included in Task.additional_params
- **Automatic Assignment**: No manual port management - framework handles allocation
- **Conflict Prevention**: Each worker gets dedicated emulator port for isolation
"""

def allocate_emulator_ports(num_workers: int) -> List[str]:
    """
    Allocate unique emulator ports for parallel execution.
    
    Args:
        num_workers: Number of parallel workers requiring unique ports
        
    Returns:
        List of emulator device names: ['emulator-5554', 'emulator-5556', ...]
    """
    base_port = 5554
    return [f"emulator-{base_port + (i * 2)}" for i in range(num_workers)]

def execute_task(task: Task, worker_id: int, emulator_port: str, output_dir: str):
    """
    Execute single Task object using existing TaskExecutor with assigned emulator port.
    
    ### Execution Steps:
    1. Task includes emulator_port in additional_params configuration
    2. Create RVAndroidTool instance using existing ToolFactory
    3. RVAndroidTool extracts emulator_port from task configuration
    4. EmulatorManager uses assigned port for emulator operations
    5. TaskExecutor executes with port-isolated emulator
    6. Results automatically captured by PerformanceMonitor
    7. Clean up handled by existing infrastructure
    """
```

### 🛠️ Solution: ProcessCleaner Implementation

#### Key Features:
```python
class ProcessCleaner:
    def cleanup_emulator_processes(self, device_ports: List[int] = None) -> int:
        # Phase 1: Graceful termination (SIGTERM)
        for pid, command in target_processes:
            os.kill(pid, signal.SIGTERM)
            
        time.sleep(5)  # Wait for graceful shutdown
        
        # Phase 2: Force kill remaining processes (SIGKILL) 
        for pid, command in remaining_processes:
            os.kill(pid, signal.SIGKILL)
```

1. **parallel_manager.py**: Added ProcessCleaner to `finally` blocks
2. **Per-task cleanup**: Targets specific device ports
3. **Global cleanup**: Final sweep of all emulator processes
4. **Error handling**: Never fails the main task execution

def _save_results(self, summary: ExecutionSummary) -> None:
    # Save test framework format (for compatibility)
    summary_file = self.results_dir / "summary.json"  
    results_file = self.results_dir / "results.json"
    
    # Generate rv-platform standard result files 
    # using ResultProcessorComponent to match sequential execution
    if self.tasks:
        try:
            from rv_platform.components.result_processor import ResultProcessorComponent
            processor = ResultProcessorComponent(self.tasks, str(self.results_dir))
            processor.initialize({})
            processor.execute({})  # Generates coverage.csv, errors.csv, etc.
            processor.cleanup()
        except Exception as e:
            self.logger.warning(f"Failed to generate rv-platform result files: {e}")
