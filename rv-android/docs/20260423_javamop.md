# 20260423 — Funcionamento exato do JavaMOP e implicações para o protótipo dexlib2

## Contexto

Durante o planejamento do protótipo `prototipo-dexlib2`, surgiu a decisão sobre **como obter a informação de pointcuts/advices** que alimentará o weaver DEX-native. Duas alternativas foram avaliadas:

(a) **Parsear os arquivos `.aj`** já gerados pelo rv-monitor/JavaMOP (ANTLR/JavaCC/regex);
(b) **Hookar no gerador do JavaMOP** para emitir um descritor estruturado (JSON) em vez do texto `.aj`.

Este documento registra o funcionamento interno exato do JavaMOP, localizando os pontos de intervenção, e explica por que a opção **(b) é a escolhida** para o protótipo.

## 1. Arquitetura do JavaMOP — pipeline `.mop → .aj`

### 1.1 Entry point

Arquivo: `rvsec/javamop/src/main/java/javamop/JavaMOPMain.java`

```java
public static void processSpecFile(File file, String location) throws MOPException, IOException {
    MOPNameSpace.init();
    MOPSpecFile spec = SpecExtractor.parse(file);          // 1) Parser .mop → AST

    MOPProcessor processor = new MOPProcessor(options.aspectname);

    writeFile(processor.generateRVFile(spec),              // 2) Gera .rvm
              location, RVM_FILE_SUFFIX, null);

    writeFile(processor.generateAJFile(spec),              // 3) Gera .aj  ← nosso foco
              location, AJ_FILE_SUFFIX, options.aspectname);
}
```

### 1.2 Geração do `.aj` — `MOPProcessor.generateAJFile()`

```java
public String generateAJFile(MOPSpecFile mopSpecFile) throws MOPException, IOException {
    // ...registro/validação de variáveis e specs...
    String result = (new AspectJCode(name, mopSpecFile)).toString();
    result = Tool.changeIndentation(result, "", "\t");
    return result;
}
```

### 1.3 Cadeia de `toString()`

A emissão é feita **100% por concatenação de strings** em cascata, sem templates (Velocity/StringTemplate) e sem AST intermediário da saída:

```
AspectJCode.toString()
  ├── package + imports
  ├── aspect BaseAspect { pointcut notwithin() : ... }
  ├── (opcional) aspect <name>OrderAspect { declare precedence ... }
  └── CombinedAspect.toString()
         ├── public aspect <name> implements RVMObject {
         ├── constructor
         ├── LockManager.decl()
         ├── StatManager.advice()
         └── EventManager.advices()
                ├── pointcut MOP_CommonPointCut() : ...;
                └── para cada AdviceAndPointCut:
                       AdviceAndPointCut.toString()
                          ├── pointcut <NomeSpec>_<EventId>(<params>) : (<expr>) && MOP_CommonPointCut();
                          └── <pos> (<params>) [returning|throwing(<ret>)] :
                                 <NomeSpec>_<EventId>(<params>) {
                                     Monitor.<EventId>Event(<args>);
                                     ...
                              }
```

## 2. Estrutura interna — AST do JavaMOP

O JavaMOP mantém AST tipada para **pointcuts** (não para a saída `.aj`):

### 2.1 Hierarquia `PointCut`

`javamop.parser.ast.aspectj.PointCut` (classe base abstrata) com subclasses:

| Subclasse | Constructo AspectJ |
|---|---|
| `MethodPointCut` | `call(...)` / `execution(...)` |
| `FieldPointCut` | `get(...)` / `set(...)` |
| `CombinedPointCut` | combinações `&&` / `\|\|` |
| `NotPointCut` | `!` |
| `ArgsPointCut` | `args(...)` |
| `TargetPointCut` | `target(...)` |
| `ThisPointCut` | `this(...)` |
| `WithinPointCut` | `within(...)` |
| `IFPointCut` | `if(...)` |
| `ConditionPointCut` / `CountCondPointCut` | condições dinâmicas |
| `HandlerPointCut`, `EventPointCut` | extensões MOP |
| `MethodPattern`, `FieldPattern`, `TypePattern` | padrões auxiliares |

### 2.2 `AdviceAndPointCut` — estrutura operável

`javamop.output.combinedaspect.event.advice.AdviceAndPointCut` é **o ponto central** para o protótipo:

```java
public class AdviceAndPointCut {
    private final PointCut pointcut;          // AST do pointcut
    private final MOPVariable pointcutName;   // ex. "CipherSpec_g1"
    private final String pos;                 // "before" | "after" | "around"
    private final MOPParameters parameters;   // params capturados
    private final MOPParameters retVal;       // "returning(T r)"
    private final MOPParameters throwVal;     // "throwing(T e)"
    private final HashMap<EventDefinition, AdviceBody> advices;   // chamadas ao monitor

    public PointCut getPointCut() { return pointcut; }
    public String getPointCutName() { return pointcutName.getVarName(); }
}
```

Toda a informação que precisamos está aqui, tipada e navegável.

## 3. Parser `aspectj.jj` do JavaMOP — limites

Localização: `rvsec/javamop/src/main/javacc/javamop/parser/aspectj_parser/aspectj.jj` (3779 linhas).

Gera em build time: `AspectJParser.java` (commitado também em `src/main/java/javamop/parser/aspectj_parser/`).

Entry point:
```java
public static PointCut parse(File file) throws ParseException { ... }
```

**Limitação crítica**: `AspectJParser` parseia **apenas expressões de pointcut isoladas**. Não parseia arquivos `.aj` completos (não digere `aspect { ... }`, `pointcut name(): ...;`, `before/after(...) { body }`, imports, etc.).

Ou seja: se tentássemos fazer `AspectJParser.parse(arquivo.aj)`, falharia. Ele serve para parsear o **lado direito** de `pointcut nome() : <EXPRESSÃO>`, não o arquivo inteiro.

## 4. Regularidade do `.aj` gerado pelo rv-monitor/JavaMOP

Exemplo canônico (`MultiSpec_1MonitorAspect.aj`):

```java
// 4.1 — header fixo
package mop;
import ... ;

aspect BaseAspect {
    pointcut notwithin() :
        !within(sun..*) && !within(java..*) && !within(javax..*) &&
        !within(com.sun..*) && !within(mop..*) && !within(javamoprt..*) &&
        !within(rvmonitorrt..*) && !within(com.runtimeverification..*);
}

public aspect MultiSpec_1MonitorAspect implements com.runtimeverification.rvmonitor.java.rt.RVMObject {
    public MultiSpec_1MonitorAspect(){}

    static ReentrantLock MultiSpec_1_MOPLock = new ReentrantLock();
    static Condition MultiSpec_1_MOPLock_cond = MultiSpec_1_MOPLock.newCondition();

    pointcut MOP_CommonPointCut() :
        !within(com.runtimeverification.rvmonitor.java.rt.RVMObject+) &&
        !adviceexecution() &&
        BaseAspect.notwithin();

    // 4.2 — padrão "call + before"
    pointcut TrustManagerFactorySpec_init(TrustManagerFactory mf) :
        (( call(public void TrustManagerFactory.init(KeyStore))
         || call(public void TrustManagerFactory.init(ManagerFactoryParameters))
         ) && target(mf)
        ) && MOP_CommonPointCut();

    before (TrustManagerFactory mf) : TrustManagerFactorySpec_init(mf) {
        MultiSpec_1RuntimeMonitor.TrustManagerFactorySpec_initEvent(mf);
    }

    // 4.3 — padrão "call + after returning" (pode disparar múltiplos eventos)
    pointcut CipherSpec_g1(String transformation) :
        (call(public static Cipher Cipher.getInstance(String)) && args(transformation))
        && MOP_CommonPointCut();

    after (String transformation) returning (Cipher c) : CipherSpec_g1(transformation) {
        //CipherSpec_g1
        MultiSpec_1RuntimeMonitor.CipherSpec_g1Event(transformation, c);
        //CipherSpec_g3
        MultiSpec_1RuntimeMonitor.CipherSpec_g3Event(transformation, c);
    }
}
```

**Invariantes do formato gerado:**

1. Cada `pointcut <NomeSpec>_<EventId>(<params>) : (<expr>) && MOP_CommonPointCut();`
2. Cada advice tem a forma `<pos> (<params>) [returning|throwing(<ret>)] : <NomeSpec>_<EventId>(<params>) { ... }`
3. O **corpo do advice é puro pass-through** — apenas chamadas `Monitor.<EventId>Event(args);` (ocasionalmente `Thread t = Thread.currentThread();` para pointcuts com thread-var)
4. Um único advice pode disparar **múltiplos eventos** do monitor (comentário `//EventId` marca cada um)
5. Nenhum uso de `proceed()` / `around()` nos `.aj` do `rv-android` em JCA/generic_new/Coverage
6. `MOP_CommonPointCut()` aplicado universalmente como filtro de escopo

## 5. Avaliação das opções de parser (descartadas)

| Opção | Veredito | Razão |
|---|---|---|
| `aspectj.jj` do JavaMOP como parser de `.aj` | ❌ | Parseia apenas expressões de pointcut isoladas; não lê arquivo `.aj` |
| ANTLR4 grammars-v4/aspectj | ⚠️ | Grammar completa mas acrescenta build-time ANTLR + manutenção da grammar; desnecessário se temos o gerador na mão |
| `org.aspectj.weaver.tools.PointcutParser` | ❌ | Limitado: não suporta `if`, `cflow`, `cflowbelow`, só pointcuts self-contained e anônimos; não parseia `.aj` inteiros |
| `aspectjtools.jar` (AJC real, baseado em Eclipse JDT) | ❌ | APIs internas, não públicas; acoplar ao AJC reintroduz a complexidade que queríamos eliminar |
| Regex sobre `.aj` | ❌ | Frágil; rejeitado pelo usuário explicitamente |
| **Hook no gerador JavaMOP** (opção b) | ✅ | Acesso direto à AST tipada, zero overhead de parser, determinístico |

## 6. Decisão: interceptar o gerador (opção b)

### 6.1 Onde interceptar

Três alternativas, em ordem crescente de isolamento:

**Alt 1 — `AdviceAndPointCut.toJSON()` paralelo ao `toString()`** *(recomendado)*

Adicionar um método `toJSON()` na classe `AdviceAndPointCut` que emite a mesma informação do `toString()` em JSON estruturado. Vantagem: mínima invasão, reusa 100% dos campos tipados já existentes.

**Alt 2 — Novo formatter em `AspectJCode`**

Criar `AspectJCode.toJSON()` paralelo ao `toString()`. Iterar `CombinedAspect → EventManager → List<AdviceAndPointCut>` e compor descritor. Vantagem: produz documento por arquivo `.aj` completo, incluindo package/imports/BaseAspect.

**Alt 3 — Novo `MOPProcessor.generateDescriptorFile()`**

Adicionar método irmão de `generateAJFile()`. Produz `.aj` E `.json` na mesma execução. Vantagem: não modifica classes existentes.

### 6.2 Estratégia escolhida

**Combinar Alt 2 + Alt 3**: novo método `generateDescriptorFile()` em `MOPProcessor` que delega a um novo `AspectJDescriptor(name, mopSpecFile).toJSON()` (espelho de `AspectJCode`). O protótipo dexlib2 consome o JSON em vez do `.aj`.

### 6.3 Formato do descritor

```json
{
  "aspect": "MultiSpec_1MonitorAspect",
  "package": "mop",
  "imports": ["javax.crypto.Cipher", "..."],
  "baseAspect": {
    "notwithin": ["sun..*", "java..*", "javax..*", "com.sun..*",
                   "mop..*", "javamoprt..*", "rvmonitorrt..*",
                   "com.runtimeverification..*"]
  },
  "commonPointcut": "!within(RVMObject+) && !adviceexecution() && BaseAspect.notwithin()",
  "pointcuts": [
    {
      "name": "CipherSpec_g1",
      "parameters": [{"type": "java.lang.String", "name": "transformation"}],
      "expression": {
        "kind": "and",
        "left": {
          "kind": "call",
          "modifiers": ["public", "static"],
          "returnType": "javax.crypto.Cipher",
          "declaringType": "javax.crypto.Cipher",
          "methodName": "getInstance",
          "argTypes": ["java.lang.String"]
        },
        "right": {"kind": "args", "names": ["transformation"]}
      },
      "advices": [
        {
          "position": "after",
          "returning": {"type": "javax.crypto.Cipher", "name": "c"},
          "throwing": null,
          "monitorCalls": [
            {
              "target": "MultiSpec_1RuntimeMonitor",
              "method": "CipherSpec_g1Event",
              "args": ["transformation", "c"]
            },
            {
              "target": "MultiSpec_1RuntimeMonitor",
              "method": "CipherSpec_g3Event",
              "args": ["transformation", "c"]
            }
          ]
        }
      ]
    }
  ]
}
```

O campo `expression` é a serialização direta da AST `PointCut`, preservando `call`/`execution`/`and`/`or`/`not`/`target`/`args`/`within`/... em forma recursiva. Cada subclasse de `PointCut` contribui com seu `toJSON()`.

## 7. Implicações para o protótipo `prototipo-dexlib2`

### 7.1 Fluxo revisado

```
.mop  ──┬──► JavaMOP (gera .rvm)
        │
        ├──► JavaMOP patched (gera .aj como hoje)
        │
        └──► JavaMOP patched (gera .json descriptor) ← NOVO
                                                      │
prototipo-dexlib2/aj-parser reads .json  ◄────────────┘
        │
        ├──► dex-weaver (dexlib2, sem parser textual)
        ├──► monitor-builder (d8)
        └──► multidex-merger (+ sign + install)
```

### 7.2 Redução de complexidade no protótipo

Sem parser textual → elimina:
- Módulo `aj-parser` precisa apenas de **JSON reader (Jackson/Gson)**, não de parser.
- Zero risco de divergência semântica entre o que rv-monitor emite e o que o weaver interpreta (mesma fonte, mesma AST).
- Testes: descritor JSON é checkable, diffável, versionável.

### 7.3 Esforço no JavaMOP

Modificação pequena (~300-500 linhas adicionais) ao JavaMOP:
- `toJSON()` em cada subclasse de `PointCut` (visitor ou método na classe)
- `toJSON()` em `AdviceAndPointCut`
- Novo `AspectJDescriptor` (irmão de `AspectJCode`)
- Novo `generateDescriptorFile()` em `MOPProcessor`
- Nova flag CLI `--emit-descriptor`

### 7.4 Alternativa de fallback

Se por alguma razão não pudermos modificar JavaMOP (upstream restrictivo, manutenção de fork indesejável), **caminho B**: usar ANTLR4 grammars-v4/aspectj como parser externo dos `.aj`. Custo: +1 dependência ANTLR, +1 módulo parser, risco de divergência com a emissão do JavaMOP. Mantém o protótipo isolado do JavaMOP.
