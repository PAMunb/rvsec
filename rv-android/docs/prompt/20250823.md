# Relatório de Desenvolvimento - Sistema de Automação Android com Visão
**Data:** 23/08/2025  
**Projeto:** RVAndroid - Automação de Testes Android com LLMs Multimodais

## 1. Contexto e Objetivo

### Problema Inicial
O sistema de automação Android utilizando Spring AI + Ollama funcionava perfeitamente com Claude (API paga), mas falhava completamente com modelos locais Ollama para:
- Tool calling nativo
- Processamento de imagens (multimodal)
- Execução de ações na interface Android

### Objetivo
Fazer o sistema funcionar com modelos locais Ollama para reduzir custos e permitir execução offline.

## 2. Problemas Identificados

### 2.1 Spring AI Tool Calling com Ollama
**Problema:** Modelos Ollama não suportam o formato de tool calling do Spring AI (OpenAI Function Calling format).

**Evidência:**
```java
// Spring AI esperava:
{
  "tool_calls": [{
    "function": {
      "name": "tap",
      "arguments": {"x": 540, "y": 960}
    }
  }]
}

// Ollama retornava:
"I should tap on the button at coordinates 540, 960"
```

**Solução Implementada:** TextBasedToolExecutor com parsing de tags
```java
// Novo formato aceito:
<action>tap(x=540, y=960)</action>
// ou
<action>tap(540, 960)</action>
```

### 2.2 Spring AI Multimodal com Ollama
**Problema:** Spring AI corrompia ou não enviava corretamente imagens para Ollama.

**Evidências:**
- Modelos "viam" conteúdo incorreto (Bitcoin wallet ao invés de Crypto App)
- Mesma imagem funcionava via protocolo nativo Ollama
- Spring AI funcionava com Claude mas não com Ollama

**Testes Realizados:**

### 2.3 Coordenadas Incorretas dos Modelos
**Problema:** Modelos enviavam coordenadas fora da área útil da tela.

**Evidências:**
```

Botão MESSAGE DIGEST real: y=~207

```

```
- Second button: (540, 480)
```

3. **Validação e Ajuste de Coordenadas:**

## 3. Arquitetura Final Implementada

### 3.1 Fluxo de Processamento

```
Screenshot → Base64 → OllamaDirectClient (bypass) → Modelo Ollama
                              ↓
                     Resposta com <action> tag
                              ↓
                    TextBasedToolExecutor (parser)
                              ↓
                     AndroidUIAutomatorWrapper
                              ↓
                         ADB Command
```

### 3.2 Componentes Principais

#### OllamaDirectClient
- **Função:** Bypass do Spring AI para multimodal
- **Protocolo:** Nativo Ollama `/api/chat`
- **Suporta:** Imagens base64 diretamente

#### TextBasedToolExecutor
- **Função:** Parser de ações em formato texto
- **Formatos aceitos:**
  - `<action>tap(x=540, y=960)</action>`
  - `<action>tap(540, 960)</action>`
  - `<action>typeText(Hello World)</action>`
  - `<action>scroll(down)</action>`

#### AndroidUIAutomatorWrapper
- **Melhorias:**
  - Detecção dinâmica de resolução
  - Delay aumentado (500ms → 1000ms)
  - Logs detalhados de execução

#### PromptService
- **Função:** Injeção dinâmica de variáveis no prompt
- **Variáveis:** Resolução, regiões da tela, exemplos de coordenadas

## 5. Limitações Identificadas

### 5.1 Limitações dos Modelos Locais
- **Precisão de coordenadas:** Modelos não são treinados para estimar coordenadas pixel-perfect
- **Compreensão de contexto:** Dificuldade em entender workflows completos
- **Consistência:** Respostas variam muito entre execuções
- **Alucinações:** Frequentemente "veem" elementos que não existem

### 5.2 Limitações da Abordagem
- **Dependência 100% de visão:** Sem fallback para detecção precisa
- **Contexto acumulado:** Muitas interações confundem o modelo
- **Prompt engineering:** Difícil criar prompt genérico que funcione para todos apps

## 6. Nova Descoberta: Tools Funcionam com Modelos Não-Multimodais

### 6.1 Teste com llama3.2:3b

**Descoberta Crítica:** Executamos teste específico com `llama3.2:3b` (modelo sem visão) e descobrimos que **Ollama SUPORTA tools nativo perfeitamente**!

**Resultados do Teste:**
```python
# ✅ API nativa Ollama funcionou
POST /api/chat
{
  "model": "llama3.2:3b",
  "tools": [...],
  "messages": [{"role": "user", "content": "Tap at 540, 300"}]
}

# Resposta:
{
  "message": {
    "tool_calls": [
      {
        "function": {
          "name": "tap",
          "arguments": {"x": 540, "y": 300}
        }
      }
    ]
  }
}

# ✅ Endpoint OpenAI-compatible também funcionou
POST /v1/chat/completions - Retornou tool_calls corretas
```

### 6.2 Análise do Problema Real

O problema **NÃO é do Ollama ou Spring AI**, mas sim uma **limitação específica dos modelos multimodais**:

- **llama3.2:3b** (text-only): ✅ Suporta tools nativo
- **llama3.2-vision:11b** (multimodal): ❌ "does not support tools"
- **gemma3:4b** (multimodal): ❌ "does not support tools"

**Conclusão:** Modelos multimodais do Ollama não suportam function calling, mas modelos text-only suportam perfeitamente.

## 7. Recomendações para Produção

### 7.1 Arquitetura Dual-Model (Recomendada)

```
Screenshot → llama3.2-vision:11b → "Vejo botão LOGIN centralizado, campo email vazio"
                    ↓
           Sistema extrai intenção
                    ↓
llama3.2:3b + tools → tool_call: tap(540, 300)
                    ↓
        AndroidUIAutomatorWrapper
```

**Vantagens:**
- **100% tool calling nativo** (sem parsing de texto)
- **Visão confiável** para análise de tela
- **Separação de responsabilidades**
- **Compatível com Spring AI**

### 7.2 Implementação Dual-Model

```java
@Service
public class DualModelAutomation {
    
    // Modelo para visão (análise de tela)
    @Qualifier("visionModel")
    private ChatModel visionModel; // llama3.2-vision:11b
    
    // Modelo para ações (tool calling)
    @Qualifier("toolModel") 
    private ChatModel toolModel;   // llama3.2:3b
    
    public void processScreen(String screenshot) {
        // 1. Análise visual
        String analysis = visionModel.call("Analyze this screen: " + screenshot);
        
        // 2. Decisão de ação baseada na análise
        String actionDecision = extractActionFromAnalysis(analysis);
        
        // 3. Tool calling nativo
        ChatResponse response = toolModel.call(
            new Prompt(actionDecision, ollamaOptions().withTools(tools))
        );
        
        // 4. Execução via Spring AI tools (funciona!)
        executeToolCalls(response.getToolCalls());
    }
}
```

### Proposta 1: Monitor-Driven LLM Property Discovery (Python + JavaMOP)

#### 1.1 Conceito Fundamental
Sistema que usa LLMs para **descobrir e gerar propriedades JavaMOP** dinamicamente, baseado em análise estática e comportamento runtime.

**Diferenciação:** Primeira ferramenta que usa IA para **síntese automática de propriedades formais** ao invés de apenas testes UI.

#### 1.2 Arquitetura
```
Análise Estática (GATOR/GESDA/REACH) → LLM Property Synthesizer → 
JavaMOP Generation → AspectJ Instrumentation → Runtime Verification →
Violation Analysis → Property Refinement → New JavaMOP Properties
```

#### 1.3 Componente Python (rv-property-synthesizer)
```python
class PropertySynthesizer:
    def synthesize_properties(self, static_data: StaticAnalysisData) -> List[JavaMOPProperty]:
        # Analisa static data usando LLM
        patterns = self.llm.analyze_security_patterns(
            gator_data=static_data.gator,
            gesda_results=static_data.gesda,
            reach_analysis=static_data.reach
        )
        
        # Gera propriedades JavaMOP
        properties = []
        for pattern in patterns:
            javamop_property = self.generate_javamop_property(pattern)
            properties.append(javamop_property)
        
        return properties
    
    def generate_javamop_property(self, pattern: SecurityPattern) -> JavaMOPProperty:
        # LLM gera especificação JavaMOP
        spec = self.llm.generate_javamop_spec(
            pattern_type=pattern.type,
            methods=pattern.involved_methods,
            temporal_logic=pattern.temporal_requirements
        )
        
        return JavaMOPProperty(
            name=pattern.name,
            specification=spec,
            pointcuts=pattern.aspectj_pointcuts
        )
```

#### 1.4 Resultado Esperado
- **Descoberta automática** de 50+ novas propriedades de segurança por app
- **Primeira ferramenta** a combinar LLM + verificação formal
- **Integração nativa** com rv-monitor-generator
- **Contribuição científica:** Nova categoria de tools (Property Synthesizers)

### Proposta 2: Hierarchical Property Composition (Python + JavaMOP)

#### 2.1 Conceito Fundamental
Sistema de **composição hierárquica** de propriedades JavaMOP, onde propriedades complexas são compostas dinamicamente a partir de propriedades base.

#### 2.2 Arquitetura Hierárquica
```
Base Properties (manual JavaMOP)
├── Derived Properties (LLM-composed)
├── Contextual Properties (environment-aware) 
└── Emergent Properties (learned from violations)
```

#### 2.3 Componente Python (rv-property-composer)
```python
class HierarchicalPropertyComposer:
    def compose_complex_property(self, base_properties: List[JavaMOPProperty]) -> JavaMOPProperty:
        # LLM identifica relações entre propriedades
        relationships = self.llm.analyze_property_relationships(base_properties)
        
        # Compõe nova propriedade hierárquica
        composed_spec = self.llm.generate_hierarchical_spec(
            base_specs=[p.specification for p in base_properties],
            relationships=relationships,
            composition_strategy="temporal_sequence"
        )
        
        return JavaMOPProperty(
            name=f"Composed_{hash(composed_spec)}",
            specification=composed_spec,
            dependencies=base_properties,
            composition_type="hierarchical"
        )
```

#### 2.4 Vantagens Arquiteturais
- **Reutilização** de propriedades existentes
- **Escalabilidade** através de composição
- **Flexibilidade** para diferentes tipos de app
- **Evolução** de propriedades baseada em violações

### Proposta 3: Monitor Violation Learning Loop (Python + JavaMOP)

#### 3.1 Conceito Fundamental
Sistema que **aprende com violações** de monitores para refinar propriedades JavaMOP dinamicamente.

#### 3.2 Ciclo de Aprendizado
```
Monitor Violation → Context Analysis → LLM Refinement → 
New JavaMOP Property → Deploy Monitor → Runtime Verification → 
Monitor Violation (refined)
```

#### 3.3 Componente Python (rv-violation-learner)
```python
class ViolationLearner:
    def process_violation(self, violation: MonitorViolation):
        # Extrai contexto da violação
        context = self.extract_violation_context(violation)
        
        # LLM analisa causa raiz
        root_cause = self.llm.analyze_violation_cause(
            original_property=violation.property,
            violation_context=context,
            app_static_data=self.static_data
        )
        
        # Gera propriedade refinada
        refined_property = self.llm.refine_property(
            original_spec=violation.property.specification,
            root_cause=root_cause,
            similar_violations=self.get_similar_violations(violation)
        )
        
        # Deploy nova versão
        self.deploy_refined_monitor(refined_property)
```

#### 3.4 Contribuição Científica
- **Primeira abordagem** de auto-refinamento de propriedades formais
- **Learning loop** para verificação runtime
- **Evolução automática** de especificações JavaMOP

### Proposta 4: Specification Mining Enhancement (Python + JavaMOP)

#### 4.1 Conceito Fundamental
Aprimoramento do **specification mining** tradicional com capacidades LLM para identificar padrões sutis que análise estática não detecta.

#### 4.2 Pipeline Aprimorado

```python
class EnhancedSpecificationMiner:
    def mine_enhanced_specifications(self, app_data: AppData) -> List[JavaMOPProperty]:
        # Análise tradicional
        static_patterns = self.traditional_mining(app_data.static_data)
        
        # LLM identifica padrões adicionais
        llm_patterns = self.llm.discover_subtle_patterns(
            static_patterns=static_patterns,

        all_patterns = static_patterns + llm_patterns
        
        # Gera propriedades JavaMOP

        for pattern in all_patterns:
            javamop_prop = self.generate_javamop_from_pattern(pattern)
            properties.append(javamop_prop)
        
        return self.rank_properties_by_importance(properties)
```

### Proposta 5: Adaptive Monitor Orchestration (Python + JavaMOP)

#### 5.1 Conceito Fundamental  
Sistema de **orquestração adaptativa** onde LLM gerencia interações entre monitores JavaMOP ao invés de controlar UI.

#### 5.2 Arquitetura em Camadas
```
┌─────────────────────┐
│ LLM Orchestrator    │ ← Coordena interações entre monitores
├─────────────────────┤
│ Context Monitors    │ ← Propriedades JavaMOP contextuais
├─────────────────────┤  
│ Security Monitors   │ ← Propriedades JavaMOP de segurança
├─────────────────────┤
│ Base Monitors       │ ← Propriedades JavaMOP tradicionais
└─────────────────────┘
```

#### 5.3 Componente Python (rv-monitor-orchestrator)
```python
class MonitorOrchestrator:
    def orchestrate_monitors(self, app_context: AppContext):
        # LLM decide quais monitores ativar
        active_monitors = self.llm.select_monitors(
            app_type=app_context.app_type,
            security_level=app_context.security_requirements,
            available_monitors=self.monitor_registry.get_all()
        )
        
        # Configura dependências entre monitores
        monitor_graph = self.llm.create_monitor_dependency_graph(active_monitors)
        
        # Ativa monitores na ordem correta
        for monitor in monitor_graph.topological_sort():
            self.activate_monitor(monitor)
            
        # Monitora interações entre monitores
        self.monitor_interactions(active_monitors)
```

## Conclusão

Este relatório documenta o trabalho técnico realizado no sistema Spring AI + Ollama e identifica as principais descobertas:

### Descobertas Técnicas
1. **Spring AI é incompatível** com multimodal Ollama (imagens corrompidas)
2. **Modelos multimodais não suportam tools** nativo (llama3.2-vision:11b)  
3. **Modelos text-only suportam tools** perfeitamente (llama3.2:3b)
4. **OllamaDirectClient resolve** o problema multimodal
5. **TextBasedToolExecutor** permite usar modelos sem tool support

### Limitações da Abordagem Atual
- **Tempo de inferência inviável** (5-10s por ação)
- **Sobreposição total** com RVAndroid existente
- **Diferenciação insuficiente** para contribuição científica
