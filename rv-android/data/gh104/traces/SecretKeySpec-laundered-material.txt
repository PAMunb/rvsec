# The control that decides the read at SecretKeySpec.mop's `e1`, and the only program that
# can decide it.
#
# api30 SecretKey states an ENSURES and no REQUIRES section at all, so the literal shape of
# the rule writes `preparedKeyMaterial` on every encoding, unconditionally. Measured over
# the whole corpus, keeping the read and deleting it are indistinguishable -- every other
# trace answers the same, report for report -- because no other trace feeds one
# SecretKeySpec's encoding into another.
#
# This one does, and it is written so that only the second construction can speak. The key
# whose encoding is laundered is bound silently: performing `new SecretKeySpec(km, "AES")`
# through the specification's own event would put SECRETKEYSPEC-NOBS-00 in the envelope for
# the first construction, and the harness classifies by the set of accusing events, not by
# their number (finding 14) -- so a trace that accused at both ends would read the same with
# the guard and without it. Bound silently, the first key carries no `generatedKey`, which
# is exactly the state the guard is about. It is the same device MacSpec-ungenerated-key.txt
# uses, for the same reason.
#
# With the read, `e1` finds nothing to carry, the encoding reaches the second constructor
# unmarked, and SECRETKEYSPEC-NOBS-00 fires. Without it, the encoding is marked prepared and
# the second construction goes silent: material whose origin the set never observed is
# laundered into prepared key material by a copy. That difference is the whole reason the
# read stays (tasks 5.10 and 6.1, researcher decision 2026-08-22).
bind km = bytes(16)
bind k1 = new SecretKeySpec(km, "AES")
k1.getEncoded() -> enc
new SecretKeySpec(enc, "AES") -> k2
