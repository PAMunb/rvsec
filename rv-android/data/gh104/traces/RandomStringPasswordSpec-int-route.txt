# The other half of the same measurement: the one source type whose conversion is
# faithful, and which the bridge still fails to carry.
#
# `String.valueOf(Object)` on an Integer returns its decimal digits, so unlike the
# byte[] route this char[] really does hold the random value. It is the control the
# byte[] trace needs -- a route where the predicate would be true.
#
# It does not survive either, and for a different reason: PredicateStore keys a bound
# object by identity, `SecureRandom.nextInt()` boxes its result at the ensure and the
# call site boxes it again, and two boxes of the same value are the same object only
# inside the Integer cache (-128..127). Measured: outside the cache the read at the
# bridge answers NOT_OBSERVED. So of the three source types the set can put into this
# bridge -- byte[], the SecureRandom itself, and Integer -- the two that propagate
# carry no randomness and the one that carries randomness does not propagate.
#
# This trace was unreplayable when it was written: `fitsPointcut` refused an Integer
# against a declared `Object`, so the `String.valueOf` line resolved to nothing and
# the outcome read "not accused" where the truth was "not replayed". That is repaired
# in the same commit.
SecureRandom.getInstance("SHA1PRNG") -> r
r.nextInt() -> n
String.valueOf(n) -> s
s.toCharArray() -> pw
r.generateSeed(16) -> salt
new PBEKeySpec(pw, salt, 10000, 128) -> spec
spec.clearPassword()
