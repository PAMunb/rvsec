# gh109 task 4.R, the FORBIDDEN shape of group G4 (task 4.3). `KeyAgreement.crysl:41` states
# `noCallTo[gs3]`, and `gs3` is `generateSecret(String)` -- the overload that derives a named
# symmetric key from the agreement. The call draws KEYAGREEMENT-FORB-00 under
# ErrorType.ForbiddenMethod, not under InvalidSequenceOfMethodCalls, which would send the
# reader hunting for a missing call.
#
# The other half of what the trace shows is the automaton. The forbidden event is a SELF-LOOP
# at every state, so the `generateSecret()` that follows still reaches the accepting state and
# draws no ORDER code on top of the FORB one: this program's ordering is exactly the one the
# rule states, and its defect is the call the rule forbids. Realising `gs3` as an alternative
# position of the ordering -- which is how the rule's own `GenSecret := gs3 | GenSecretBuffer`
# alias at `:34` reads if transcribed -- would report a sequencing defect where there is none,
# and that is the reading `SSLContextSpec.getDefault` and `PBEKeySpecSpec` already refused.
#
# The residue this trace also fixes in place: `gs3` sets the conformance flag false, so the
# `generateSecret()` after it writes no `preparedKeyMaterial`. A `gs3` arriving AFTER the
# buffer was generated would clear the flag too late to gate a write already made; that
# direction is recorded in `divergence_record.csv` and in the graph, and withdrawing the
# predicate would need a NEGATES the rule does not state.
KeyPairGenerator.getInstance("DH") -> kpg
kpg.initialize(2048)
kpg.generateKeyPair() -> kp
kp.getPrivate() -> priv
kp.getPublic() -> pub
KeyAgreement.getInstance("DH") -> ka
ka.init(priv)
ka.doPhase(pub, true)
ka.generateSecret("AES")
ka.generateSecret()
