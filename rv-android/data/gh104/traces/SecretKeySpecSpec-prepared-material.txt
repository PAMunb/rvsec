# The chain api30 actually admits, and the corpus had no trace of it.
#
# SecretKeySpec REQUIRES `preparedKeyMaterial[keyMaterial]` (SecretKeySpec.cryptsl:34) and
# the whole oracle ENSURES that predicate at two events only, `Key.getEncoded()` and
# `SecretKey.getEncoded()` (Key.cryptsl:23, SecretKey.cryptsl:25). So the only construction
# of a SecretKeySpec the rule accepts is one whose material another key's encoding
# produced -- not one filled from a SecureRandom, which is what every other trace of this
# specification does and what the seed's conflation of the two predicates had made silent.
#
# This is that construction, observed end to end: KeyGenerator produces the key,
# SecretKeySpec.mop's `e1` carries the predicate across the copy `getEncoded()` makes, and
# the constructor reads it and says nothing. It is the silence the un-conflation has to
# preserve, and it is the reason a read that accuses fifteen other traces is a repair and
# not a regression: the set can still tell the two idioms apart, and now it tells them
# apart the way the rule does.
#
# Measured before the edit as well as after: on the tree that still conflated the two
# predicates this program was silent too, for the other reason -- the encoding carried
# `randomized`. Silent on both sides, and the reason for the silence is what changed.
KeyGenerator.getInstance("AES") -> kg
kg.init(128)
kg.generateKey() -> key
key.getEncoded() -> enc
new SecretKeySpec(enc, "AES") -> spec
