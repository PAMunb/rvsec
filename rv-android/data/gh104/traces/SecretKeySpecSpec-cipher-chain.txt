# The chain no trace of the corpus observed at both ends. Every Cipher trace binds its
# key silently (`bind k = new SecretKeySpec(...)`), so SecretKeySpecSpec's construction
# event never fires in them and the key origin Cipher.init asks about is never
# established by anything the monitor saw.
#
# Here both ends are observed. api30 SecretKeySpec ENSURES generatedKey[this, alg]
# (SecretKeySpec.cryptsl:41) and api30 Cipher REQUIRES it at Cipher.init, which is
# ledger clause #5. The Cipher half of the program breaks no clause -- the transformation
# is one the api30 table admits -- but the construction of the key does, and this trace
# stopped being silent at task 5.10: the material comes from a SecureRandom, and
# SecretKeySpec REQUIRES `preparedKeyMaterial[keyMaterial]`, which only a getEncoded()
# ensures. So SECRETKEYSPEC-NOBS-00 fires here, no `generatedKey` is ensured for a
# construction that broke the rule, and CIPHER-NOBS-00 follows downstream. Both are what
# api30 states. SecretKeySpecSpec-prepared-material.txt carries the same chain through
# from silence.
#
# What it measures is the second window task 4.10 closes. `CipherSpec.i2` moved to the
# new store at task 4.1 and this producer had not, so the read answered NOT_OBSERVED --
# indistinguishable from a key that came from nowhere -- and accused CIPHER-NOBS-00.
# With the write on the same store the read answers SATISFIED and the trace is silent.
#
# It is also what pins the arity decision: the write stays at arity 1 here and rises at
# task 5.6 with the consumer. Were it raised alone, this same conforming program would
# draw CIPHER-CONSTR-00 instead -- `validate` compares the value tuple, so an arity-2
# write read by an arity-1 validate returns VIOLATED, not NOT_OBSERVED.
bind km = bytes(32)
SecureRandom.getInstance("SHA1PRNG") -> r
r.nextBytes(km)
new SecretKeySpec(km, "AES") -> k
Cipher.getInstance("AES/CBC/PKCS5Padding") -> c
c.init(1, k)
c.doFinal(bytes)
