### 0.2 What the "lines" counts mean
`ErrorCollector` (`/pedro/desenvolvimento/workspaces/workspaces-doutorado/workspace-rv/rvsec/rvsec/rvsec-android/rvsec-logger-logcat/src/main/java/br/unb/cic/mop/eh/ErrorCollector.java:26,51-54`) keeps a `HashSet<ErrorDescription>` and logs a line only when `errors.add(err)` is true; `ErrorDescription.equals` compares the `ErrorSummary` (spec, error type, class, method, location, code, event — `ErrorDescription.java:166-173`, `ErrorSummary.java:106-136`). So a (site, code) pair is written **once per process lifetime**, never per call. This is why `PrfAesCmac.compute` has 967 lines although `AesSiv.s2v` calls `compute` three times per encryption (AesSiv.java:87,95,103 in 1.8.0), and why a "line" count should be read as "process lifetimes that reached the site".

### 0.3 The key chain every site below hangs on (read in 1.8.0; 1.5.0 and 1.19.0 cited where they differ)
1. `EncryptedSharedPreferences.create` builds two `AndroidKeysetManager`s with `withMasterKeyUri("android-keystore://" + alias)` and gets the primitives (`SRC/security-crypto-1.1.0/androidx/security/crypto/EncryptedSharedPreferences.java:165-177`; 1.0.0: `:119-131`; encryptedprefs fork: `.../dev/spght/encryptedprefs/EncryptedSharedPreferences.java:167-182`). `EncryptedFile` does the same for `StreamingAead` (`security-crypto-1.1.0/.../EncryptedFile.java:225-240`).
2. 3. `KeysetHandle.decrypt` → `Keyset.parseFrom(masterKey.decrypt(encryptedKeyset.getEncryptedKeyset().toByteArray(), aad))` (`KeysetHandle.java:913-919` in 1.8.0, `:1104-1105` in 1.19.0, `:184-185,205-206` in 1.5.0). The decrypt is `AndroidKeystoreAesGcm.decryptInternal` (site 1) and the master key is the AndroidKeyStore `SecretKey` fetched by `keyStore.getKey(keyId, null)` (`AndroidKeystoreAesGcm.java:49-51`; `AndroidKeystore.java:137` in 1.19.0).
4. The primitive's key bytes are a **protobuf copy** of the parsed keyset: `new AesSiv(key.getKeyValue().toByteArray())` (`daead/AesSivKeyManager.java:53` in 1.8.0, `:47` in 1.5.0), `new AesGcmJce(key.getKeyValue().toByteArray())` (`aead/AesGcmKeyManager.java:52` / `:47`), `new AesGcmHkdfStreaming(key.getKeyValue().toByteArray(), ...)` (`streamingaead/AesGcmHkdfStreamingKeyManager.java:54-55`). In 1.19.0: `AesSiv.create` → `key.getKeyBytes().toByteArray(InsecureSecretKeyAccess.get())` (`subtle/AesSiv.java:76-77`), `SecretBytes.toByteArray` → `bytes.toByteArray()` (`util/SecretBytes.java:55-59`, a copy).
5. On first run the keyset is generated with `ByteString.copyFrom(Random.randBytes(format.getKeySize()))` (`AesSivKeyManager.java:117`, `AesGcmKeyManager.java:100`, `AesGcmHkdfStreamingKeyManager.java:118`; 1.19.0 `SecretBytes.randomBytes` → `Bytes.copyFrom(Random.randBytes(length))`, `SecretBytes.java:46-47`): the `SecureRandom.nextBytes` array is credited `randomized` by `SecureRandomSpec.next2/@match2` (`MOP/SecureRandomSpec.mop:289-294,397-399`) but is immediately copied into a `ByteString`, and the primitive later receives yet another copy (`toByteArray()`).

Consequence read off the specs: `SecretKeySpecSpec.c1` asks `PREPARED_KEY_MATERIAL` on the exact array (`MOP/SecretKeySpecSpec.mop:110-120`); that predicate is ensured only by `SecretKey+.getEncoded()` / `Key+.getEncoded()` (`MOP/SecretKeySpec.mop:119-127,143-148`; `MOP/KeySpec.mop:75-85,103-108`) and by `KeyAgreement` (`MOP/KeyAgreementSpec.mop:298,315`). Tink never calls `getEncoded()` on these keys and never hands the same array object to `SecretKeySpec`, so every `SecretKeySpec` construction in tink answers NOT_OBSERVED, its `@match` writes no `generatedKey` (`SecretKeySpecSpec.mop:121-124,255-258`), and every `Cipher.init`/`Mac.init` on that key answers NOT_OBSERVED in turn (`MOP/CipherSpec.mop:199-233`, `MOP/MacSpec.mop:179-187`). The `.mop` itself records that "fill a byte[] from an observed SecureRandom and construct a SecretKeySpec from it — does not satisfy the clause" (`SecretKeySpecSpec.mop:79-91`, researcher decision 2026-08-22).

## (c) Anomalies and other observations

- **A1. Count asymmetry at AesSiv.java:119 (1.8.0).** `SECRETKEYSPEC-NOBS-00` has 966 lines at :119 but `CIPHER-NOBS-00`, `IVPARAMETERSPEC-NOBS-00` and `IVCHAINJUNCTION-NOBS-00` have 965 each at the same statement. The four advices run in one expression (`SecretKeySpec` constructor first, then `IvParameterSpec`, then `init`), so one process lifetime logged the first and none of the other three: either the process died between the first constructor's `after` advice and the second constructor (arguments are evaluated left to right), or a logcat line was lost. Not resolvable from the batch; no spec-side explanation exists.
- **A2. `__LOC` maps to the statement's first line**, not the call's line (examples in 0.1). Not an error, but a reader matching `:113` against `new GCMParameterSpec` on `:114` should know it.
- **A3. Observable-but-not-admitted material (design of the oracle, not of the monitor).** Two arrays in this batch *are* produced by a JCA call in woven code and credited by a producer of the set: the HKDF salt on the encrypt path (`Random.randBytes` → `SecureRandom.nextBytes`, credited `randomized`) at `Hkdf.java:59`, and — before its copy — every tink key at generation time (`AesSivKeyManager.java:117` etc.). `SecretKeySpecSpec.c1` asks `preparedKeyMaterial` (SecretKeySpec.crysl:23), which only `getEncoded()` ensures; the `.mop` records the cost of that reading explicitly (`MOP/SecretKeySpecSpec.mop:79-91`). I classified these LEGIT_UNOBSERVABLE because the accusation follows the recorded oracle decision, not a missing producer; flagging so the reader can decide whether "random bytes used directly as an HMAC key" is meant to be accused.
- **A4. ECB as a CMAC block-cipher primitive.** `PrfAesCmac` instantiates `AES/ECB/NoPadding` (`:51`) as the raw PRP of CMAC (RFC 4493), not as a data-encryption mode. The non-NOBS table (`briefs/NONNOBS_table.txt`) shows `CIPHER-ALG-01` and `CIPHER-ORDER-00` (at both `i2` and `f2`) at the same `init`/`doFinal` sites (`PrfAesCmac.java:69/103/110`, 1.19.0 `:106/142/155`). So each CMAC init draws three reports: ALG-01 (ECB), ORDER-00 (the `unsafeAlg` sink has no `i2` row, `MOP/CipherSpec.mop:425-429`, so the init fails and `__RESET`s, and the following `doFinal` fails again from `start`), and NOBS-00. Whether a CMAC's ECB primitive counts as the misuse the transformation clause targets is an oracle question; recorded here because the NOBS is the third accusation on an already-accused site.
- **A5. Reused Cipher objects draw ORDER accusations beside the NOBS.** `InsecureNonceAesGcmJce` (`:44-54`, ThreadLocal), 1.19.0 `AesSiv`/`PrfAesCmac`/`AesGcmJceUtil` (ThreadLocal) and `AesGcmHkdfStreamEncrypter.cipher` (`:209`, one Cipher for all segments) re-`init` after `doFinal`. `CipherSpec`'s `end` state has no `i1/i2` row (`MOP/CipherSpec.mop:461-472`), refused deliberately (`:414-418`), so the non-NOBS table shows `CIPHER-ORDER-00` at `i2` for `InsecureNonceAesGcmJce.java:93/:136` and `AesSiv.java:191` (1.19.0). Also `Hkdf.java:65` re-`init`s the same `Mac` (RFC 5869 expand step) and the table shows `MAC-ORDER-00` at `i1 :65`, `update :68/:70` and `f1 :71` — `Mac.crysl`'s ORDER has no loop back to `Init`. Outside this batch's categories; noted because the tink sites are accused for ordering by the rule's own transcription, in addition to NOBS.
- **A6. Positive evidence that two chains compose through tink** (from absence of codes in the batch): (i) `KeyStore.getKey` → `generatedKey` → `Cipher.init` (no `CIPHER-NOBS-00` at `AndroidKeystoreAesGcm.java:116` or `AndroidKeystore.java:178`); (ii) `SecureRandom.nextBytes` → `randomized` → `GCMParameterSpec` → `preparedGCM` → `Cipher.init` (no GCM/IVCHAIN NOBS at `InsecureNonceAesGcmJce.java:93` or 1.5.0 `AesGcmJce.java:73`). The `getParams` NOBS count (463) equalling the decrypt count (463) is consistent with (ii). In 1.19.0 `internal/Random.create` uses `SecureRandom.getInstance("SHA1PRNG", conscryptProvider)` (`:39`), which `SecureRandomSpec.g2` admits — but no encrypt site exists for the 1.19.0 APK, so (ii) is not measured there.
- **A7. `decryptDeterministically` shows `IVPARAMETERSPEC-NOBS-00` without `IVCHAINJUNCTION-NOBS-00`** — expected: the IV clause's antecedent requires `encmode == 1` (`IvChainJunction.mop:156-158`). Consistent with the spec.
- **A8. Observed `val`s match the code**: `AES/GCM/NoPadding`, `AES/CTR/NoPadding` (transformation strings from `c.getAlgorithm()`), `HmacSha256` at `Mac.init`; the empty `val` on the SecretKeySpec/GCM/IvParameterSpec codes is the spec's literal `val=''`.
- **A9. Deku's use is in a bundled library.** `REPOS/com.afkanerd.deku_83.apk` contains no `EncryptedSharedPreferences` call; it comes from `lib_smsmms_android` (`Security.kt:24-34`, `MasterKey.KeyScheme.AES256_GCM`, `AES256_SIV`/`AES256_GCM`). The app-side `Cryptography.kt:34-37,65-110` also does its own AndroidKeyStore AES/GCM (not in this batch).
- **A10. Coverage pattern across APKs (inferred from the site lists, not from traces):** bravedns only decrypts the keyset (`EncryptedFile.Builder.build()`), never streams; quicksearch builds the primitives and computes key names (`encryptDeterministically`) but never encrypts/decrypts a value; nextcloudpasswords builds the AEAD 264 times (`AesGcmJceUtil.getSecretKey`) and encrypts key names but has no AEAD encrypt/decrypt site in either table — consistent with `getString` on an absent value (`EncryptedSharedPreferences.java:539-546`: lookup by encrypted key, no decrypt when null).
- **A11. Line counts vs. calls.** With per-process dedup (0.2), `PrfAesCmac.<init>` (1180) > `compute` (967) although every SIV encryption calls `compute` three times: some process lifetimes create the prefs and never touch a key. `runkeys` in the non-NOBS table (546 for 1180 lines) shows more than one process lifetime per run for these apps.

## (d) What I could not verify

- The exact byte source of the 1.19.0 `AesGcmJce(byte[], Bytes)` constructor argument (`subtle/AesGcmJce.java:78-80`, the `create(AesGcmKey)` body) was not read line by line; the category does not depend on it (every entry is a `SecretBytes`/proto copy), only the citation.
- A1's cause (process death vs. dropped logcat line) — would need the raw per-run logs.
- A10's behavioural inferences (which prefs were read, whether values existed) — would need the app traces; only the site lists were used.
- I did not re-run `dexdump` on the instrumented APKs: no claim of unwoven advice is made, and the NOBS lines at every tink site are themselves evidence the advices are woven.
- The app repos are snapshots at a commit that may differ from the APK build (e.g. deku's `build.gradle` shows a commented-out tink pin); the tink version was therefore fixed by the `security-crypto` pom pins **and** by the recorded line numbers matching the 1.5.0/1.8.0/1.19.0 sources, which agree for every site.
