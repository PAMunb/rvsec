# Risk Categories

Systematic categorization of software project risks with examples.

---

## Risk Categories Overview

| Category | Focus | Affects |
|----------|-------|---------|
| **Project Risks** | Schedule, resources, process | Project delivery |
| **Product Risks** | Quality, performance, functionality | Software being built |
| **Business Risks** | Organization, market, strategy | Business outcomes |

---

## Risk Types

### Technology Risks

Risks from software/hardware technologies used in development.

| Risk | Description | Example |
|------|-------------|---------|
| Performance | System doesn't meet performance requirements | Database can't handle transaction volume |
| Compatibility | Components don't work together | Library versions conflict |
| Scalability | System doesn't scale as expected | Memory usage grows exponentially |
| Security | Vulnerabilities in technology stack | Dependency has known CVE |
| Obsolescence | Technology becomes outdated | Framework no longer maintained |
| Learning curve | Team can't master technology quickly | New language delays development |

**Common Technology Risks**:
- [ ] Database cannot process expected transaction volume
- [ ] Reusable components contain defects
- [ ] Third-party API changes break integration
- [ ] Cloud service availability issues
- [ ] Hardware delivery delays

### People Risks

Risks associated with the development team.

| Risk | Description | Example |
|------|-------------|---------|
| Turnover | Key staff leave project | Lead architect resigns |
| Illness | Staff unavailable at critical times | Illness during release week |
| Skills gap | Team lacks required expertise | No one knows legacy system |
| Availability | Team members overcommitted | Shared between projects |
| Conflicts | Team members don't work well together | Disagreements block progress |
| Training | Required training not available | No courses for new framework |

**Common People Risks**:
- [ ] Cannot recruit staff with required skills
- [ ] Key staff ill at critical times
- [ ] Required training not available
- [ ] Team members leave project
- [ ] Domain expert unavailable

### Organizational Risks

Risks from the organizational environment.

| Risk | Description | Example |
|------|-------------|---------|
| Restructuring | Organization changes affect project | New management has different priorities |
| Budget | Funding reduced or eliminated | Budget cuts force scope reduction |
| Priority | Project priority changes | Other project takes precedence |
| Policy | Organizational policies conflict | Security policy blocks required tool |
| Politics | Internal politics affect decisions | Stakeholder conflict delays approval |
| Merger/acquisition | Company changes affect project | Acquiring company has different tech stack |

**Common Organizational Risks**:
- [ ] Organization restructured, new management
- [ ] Organizational financial problems reduce budget
- [ ] Project sponsor leaves organization
- [ ] Corporate strategy changes
- [ ] Compliance requirements change

### Tools Risks

Risks from development tools and support software.

| Risk | Description | Example |
|------|-------------|---------|
| Performance | Tools don't perform as expected | IDE crashes with large codebase |
| Integration | Tools don't work together | CI/CD pipeline integration issues |
| Licensing | License issues affect availability | Enterprise license expires |
| Learning | Team struggles with tools | Complex tool requires extensive training |
| Vendor | Tool vendor goes out of business | No support or updates available |
| Generated code | Generated code is inefficient | Code generator produces slow output |

**Common Tools Risks**:
- [ ] Code generated by tools is inefficient
- [ ] Software tools cannot be integrated
- [ ] Tool vendor discontinues product
- [ ] Tool doesn't scale to project size
- [ ] Security vulnerabilities in tools

### Requirements Risks

Risks from customer requirements and change management.

| Risk | Description | Example |
|------|-------------|---------|
| Volatility | Requirements change frequently | Customer changes mind repeatedly |
| Ambiguity | Requirements are unclear | Multiple interpretations possible |
| Completeness | Requirements are incomplete | Edge cases not specified |
| Conflict | Requirements contradict each other | Performance vs. security tradeoff |
| Understanding | Stakeholders don't understand impact | Change request affects architecture |
| Validation | Requirements don't reflect real needs | Built wrong thing |

**Common Requirements Risks**:
- [ ] Major design rework required due to changes
- [ ] Customers don't understand change impact
- [ ] Specifications of interfaces not available on schedule
- [ ] Requirements conflict discovered late
- [ ] Hidden requirements emerge during testing

### Estimation Risks

Risks from management estimates of resources.

| Risk | Description | Example |
|------|-------------|---------|
| Time | Development time underestimated | Complex feature takes 3x longer |
| Size | System size underestimated | Codebase grows beyond expectations |
| Complexity | Technical complexity underestimated | Integration harder than expected |
| Defects | Defect rate underestimated | More bugs than planned for |
| Resources | Resource needs underestimated | Need more developers |
| Dependencies | External dependencies underestimated | Waiting on other teams |

**Common Estimation Risks**:
- [ ] Time to develop underestimated
- [ ] Rate of defect repair underestimated
- [ ] Size of software underestimated
- [ ] Complexity of integration underestimated
- [ ] Testing effort underestimated

## Risk Identification Checklist

Use this checklist when identifying risks for a project:

### Technology
- [ ] Are we using new/unproven technology?
- [ ] Are there performance requirements we might not meet?
- [ ] Are there dependencies on external systems?
- [ ] Are there security concerns with our stack?
- [ ] Is any technology approaching end-of-life?

### People
- [ ] Do we have single points of failure (one person with critical knowledge)?
- [ ] Is the team experienced with the required technologies?
- [ ] Are team members dedicated or shared with other projects?
- [ ] Is the team geographically distributed?
- [ ] Are there any known conflicts or issues?

### Organizational
- [ ] Is the project sponsor stable?
- [ ] Is the budget secure?
- [ ] Are there organizational changes expected?
- [ ] Are there competing projects?
- [ ] Are there compliance/regulatory concerns?

### Tools
- [ ] Are we using the right tools for the job?
- [ ] Do our tools integrate well?
- [ ] Are there licensing concerns?
- [ ] Is the team proficient with the tools?
- [ ] Are there alternatives if tools fail?

### Requirements
- [ ] Are requirements complete and clear?
- [ ] How likely are requirements to change?
- [ ] Do stakeholders understand the requirements?
- [ ] Are there conflicting requirements?
- [ ] Is there a change management process?

### Estimation
- [ ] Are estimates based on historical data?
- [ ] Have we estimated similar projects before?
- [ ] Is there contingency in the schedule?
- [ ] Are dependencies accounted for?
- [ ] Have we validated estimates with the team?
