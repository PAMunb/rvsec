# Sync Documentation: $ARGUMENTS

Documentation orchestrator that detects code changes since each document was last updated and
updates, validates, or flags the document accordingly.

## Documentation Principles

Apply `.claude/documentation-principles.md` to every section this skill writes.

## Managed Documentation

| Document | Location | Covered code | Sync action |
|----------|----------|--------------|-------------|
| Module CLAUDE.md | `modules/<module>/CLAUDE.md` | `modules/<module>/src`, `modules/<module>/pyproject.toml` | Update sections in place |
| Module architecture | `modules/<module>/docs/architecture.md` | same as above | Update sections in place, or regenerate via `/rv-doc-architecture` |
| ADRs | `docs/adr/NNNN-*.md` (index in `docs/adr/README.md`) | code paths the ADR cites | Validate and report; never edit |
| Views-and-Beyond docs | `docs/architecture/*.md` | the target's paths (see Step 2) | Detect staleness and recommend `/rv-doc-arch <target>`; never edit |

Scope by argument:
- **`<module-name>`**: that module's CLAUDE.md, architecture.md and ADRs, plus every
  `docs/architecture/*.md` and `docs/adr/*.md` whose covered code includes the module.
- **`all`**: every document in the table. The workspace modules are listed in the root
  `CLAUDE.md` ("Module map"); `modules/rvsmart-tool` is excluded from the workspace and skipped.

The documents in `docs/architecture/` are generated by the `rv-doc-arch` suite from an
architecture model. A hand edit drifts from that model and is lost at the next regeneration,
so this skill reports them as stale and leaves the regeneration to `/rv-doc-arch`.

## Steps

### 1. List Documents in Scope

```bash
ls modules/<module>/CLAUDE.md modules/<module>/docs/architecture.md 2>/dev/null
ls docs/architecture/*.md docs/adr/[0-9]*.md
```

### 2. Resolve Covered Code

- **Module docs**: `modules/<module>/src` and `modules/<module>/pyproject.toml`.
- **`docs/architecture/<doc>.md`**: read the header line that `rv-doc-arch-generate` writes,
  `> Target: <target-slug> · Regenerate with: /rv-doc-arch <target>`, matched by
  `^> Target: (system|module-[A-Za-z0-9_-]+|subsystem-[A-Za-z0-9_-]+) · Regenerate with: /rv-doc-arch (\S+)\s*$`
  (the separator is U+00B7). The slug names the target, and the target names the paths:

  | Slug | `/rv-doc-arch` target | Covered code |
  |------|-----------------------|--------------|
  | `system` | `system` | `modules/*/src`, `modules/*/pyproject.toml` (workspace members) |
  | `module-<name>` | `module:<name>` | `modules/<name>` |
  | `subsystem-<name>` | `subsystem:<name>` | every path listed under key `<name>` in `.claude/skills/rv-doc-arch/subsystems.yaml` (all of its lists: `python:`, `java:`, `shell:`, `docker:`) |

  The `java:` paths point into the sibling rvsec tree (`../rvsec/...`); the git repository root
  is the rvsec directory, so `git log` resolves them from the rv-android directory. A document
  without the `> Target:` line has no machine-readable target: report it as stale
  with "regenerate with `/rv-doc-arch <target>`", naming the target from its file name, instead
  of guessing its coverage.
- **ADRs**: the code paths cited in the ADR (Context, Decision and References sections) that
  still exist. When an ADR cites no path, validate it by reading only.

### 3. Detect Code Changes

The baseline of each document is its own last commit, not `HEAD~1`: a document is stale when
covered code changed after the document was last committed, however many commits ago that was.

```bash
DOC=docs/architecture/rv-platform.md
BASE=$(git log -1 --format=%H -- "$DOC")

# Commits to covered code after the document's last commit
git log --oneline "$BASE"..HEAD -- <covered paths>

# Files changed in those commits (Python sources for module docs)
git diff --name-only "$BASE"..HEAD -- <covered paths>

# Uncommitted changes to covered code and to the document itself
git status --porcelain -- <covered paths> "$DOC"
```

- When `BASE` is empty (the document was never committed), report "no baseline" and compare the
  document with the current code by reading.
- When the document itself has uncommitted edits, report it: those edits are newer than `BASE`
  and are part of what the user reviews.

### 4. Assess Change Severity

For each document, categorize the changes found in Step 3:

| Severity | Criteria | Action |
|----------|----------|--------|
| **ARCHITECTURE** | Added/deleted files, renamed modules, added or removed dependencies | Regenerate (module docs) or flag (docs/architecture) |
| **STRUCTURAL** | Added classes, changed public APIs | Update affected sections (module docs) or flag (docs/architecture) |
| **BEHAVIORAL** | Modified logic, bug fixes | Update Gotchas if applicable; check ADR decisions still hold |
| **MINOR** | Formatting, comments, internal refactoring | No update needed |

### 5. Update, Validate or Flag

**Module CLAUDE.md and architecture.md, ARCHITECTURE changes** - use the **Skill tool**:
```
Skill tool: skill="rv-doc-generate-claude-md", args="[module]"
Skill tool: skill="rv-doc-architecture", args="[module]"  # If architecture.md exists
```

**Module CLAUDE.md and architecture.md, STRUCTURAL changes** - update specific sections:
- Key Components table (CLAUDE.md)
- Component Architecture section (architecture.md)
- Dependencies list (both)

**Module CLAUDE.md, BEHAVIORAL changes** - check whether the Gotchas section needs an update.

For each in-place update:
1. Read the current document
2. Identify the sections to update
3. Preserve custom content (see "Custom Content Markers")
4. Write the updated file

**`docs/architecture/*.md`** - when Step 4 finds ARCHITECTURE or STRUCTURAL changes, list the
document as stale with the commits that made it stale, and recommend `/rv-doc-arch <target>`
with the target from Step 2. Do not edit the document.

**ADRs** - for each ADR whose cited code changed, read the decision and the changed code. When
the code no longer follows the decision, report the ADR with the conflicting commit and
recommend `/rv-doc-adr`; do not edit the ADR. For `docs/adr/`, also check that every
`NNNN-*.md` file appears in the index of `docs/adr/README.md` and that each status in the index
matches the status line of the file.

### 6. Verify Consistency

Cross-check:
- [ ] Every workspace module has a CLAUDE.md
- [ ] architecture.md matches current structure (if it exists)
- [ ] ADRs still hold against the code they cite
- [ ] `docs/adr/README.md` index lists every workspace ADR with its current status
- [ ] Dependencies match pyproject.toml
- [ ] Entry points are accurate
- [ ] Test paths are correct

## Special Handling

### When to Regenerate Full CLAUDE.md

- Module added
- Module renamed
- Major architectural change
- Dependencies significantly changed
- More than 5 files changed in module

### When to Skip

- Only test files changed
- Only comments/docstrings changed
- Changes in `backup/` directory
- Changes in `__pycache__/`

### Custom Content Markers

Preserve content between these markers verbatim on every update and regeneration:
```markdown
<!-- CUSTOM:START -->
User-added content that must not be overwritten
<!-- CUSTOM:END -->
```

## Rules

1. **DETECT before updating** - Don't regenerate unnecessarily
2. **Baseline per document** - Compare against the document's last commit, never `HEAD~1`
3. **PRESERVE custom content** - Never overwrite content between the custom markers
4. **Flag, don't edit, generated and decision records** - `docs/architecture/*.md` go to `/rv-doc-arch`; ADRs go to `/rv-doc-adr`
5. **VERIFY consistency** - Check docs match code
6. **REPORT all actions** - Document what was changed and what was flagged
7. **MINIMAL updates** - Only update affected sections
